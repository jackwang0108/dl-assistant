# 挖方法阶段（Step 9-14）打法

挖方法阶段只对讨论①选定的**一个方向**做（多方向就**串行**各跑一轮，`layer2-<方向slug>/` 互不覆盖）。产物是 **2-3 条"最小可执行路线"（v1 实验方案）+ 挑错漏洞清单**，喂主会话跟用户一起打磨 v1 方案。本份只讲**怎么干活（流程）**；三个落盘文件（note.md、路线N-main.md、挑错-<视角>.md）的 schema 在 `templates/`（method-note / method-route / method-faultfind）。目录树 / 落盘次序见 `output-contract.md`。

**分工原则（和找方向阶段对称）**：**深读 PDF 取证是体力活 → 派发给子 agent 且落盘**；**生成路线是创造性判断 → 留主会话且全局**（避免路线与已有工作重合）；**细化单条路线可派发**；**独立验证靠独立检查方案**。

> **本阶段第一原理——产 v1 实验方案，不产完整方法**：idea 要尽快动手跑起来、用实验结果迭代方案，而不是坐下设计出完整、能写进论文的方法部分。实验结果本身不确定——基于"效果会好/不好"的预定假设设计出完整方案，一旦结果不符预期，整个方案作废、iteration 推倒重来。所以每条路线的形态 = **检验核心假设所需的最小实现和成本最低的首个验证实验**；**v1 默认分析先行**——核心假设尚未经验证时（多论文 insight 组合的 idea 尤其如此），首个验证实验是检验假设的分析实验，"赢"= 假设被干净证实 / 证伪，不是指标涨。完整方法形态是 execution → iterate 几轮迭代收敛后的产物，v1 阶段不许预设计。
>
> **一次只挖一个方向（负载纪律）**：讨论①多选方向时，挖方法默认串行——先跑用户最想做的一个方向（Step 9-14 完整一轮），讨论②收敛后再跑下一个。**不允许 2 方向 × N 路线同时进讨论②**——5 条路线、几十条漏洞一次性摆出来，用户来不及消化，一起打磨就退化成点头（真实踩过的坑）。
>
> **这一阶段是解决"方法泛泛而谈"的核心**：方法必须**深读 PDF 全文驱动**——每一步都要落在读到的具体证据上（某节/某图/某式/明说的 limitation），而不是只看摘要拍脑袋的抽象直觉。
>
> **Step 10 先核对路线是否满足基本要求**。四问答齐才能写入文件。先例自检通过才能列为主路线。写清首个验证实验后才能细化。Step 12 的独立检查用于发现遗漏。若到检查时才发现核心假设与已有证据相反，应回看 Step 10 的路线设计是否遗漏了已有证据。
>
> **独立检查关注 v1 能否验证核心假设**：它检查的是路线的核心假设、被忽略的对照 / sanity 验证、验证闭环的断点、和最接近工作的差异——"论文里还该有什么实验"是 iterate 的活，不在这里补；文献新不新、全不全由 Step 3 的文献检索负责，独立检查阶段不复查文献覆盖。
>
> **派子 agent 的类型**：深读 / 细化 / 挑错这些要落盘的活，派**有写权限的 agent**（`general-purpose`）——不要派 `Explore`（只读，写不了文件）。
>
> **发起前先请用户确认**：每次派发（深读、每路线的细化、挑错）之前先请用户确认——纪律见 SKILL.md「派子 agent 两条规矩」。

> **让用户跟得上（贯穿本阶段）**：深读子 agent 会抽出大量用户没读过的论文细节——对用户全是新信息。若攒到讨论环节一次性倾倒，用户来不及消化，一起打磨就退化成点头。所以主会话在**每次派发前后的停顿**上，顺手用白话把刚拿到的东西讲给用户听（提到任何论文/术语默认用户没读过，顺带一句它是什么），让用户的上下文跟着深读一起长；到讨论②时用户已经有背景。**一切摆给用户看的汇报遵守 SKILL.md「讨论汇报硬格式」**：一卡一件事（≤5 行）、新术语 ≤5 个且首次出现必跟白话、每次只确认一个决定。具体见下面各步的「边查边讲」提示和 Step 14 的按需展开式讨论。

## Step 9 深读 PDF 取证（N 个深读子 agent，一篇一个 → papers/<论文>/<论文>-note.md）

**一篇 PDF 一个深读子 agent**（并行、各写各的笔记、不冲突）。取证是体力活、且吃 token（读全文），交给子 agent 并行读、各自落盘、只回传摘要——主会话上下文不被 PDF 全文撑爆，证据全在盘上随时回取。

每个深读子 agent：

- 首选 tex-mcp：`tex_open` 打开固定版本 → `tex_outline` 看结构 → `tex_read` 按节读关键节；源码不可用降级 pdf-mcp：`pdf_open` 取得固定快照 → `pdf_outline` 看结构 → `pdf_read` 按页读关键节，**别一次性读全文**烧 token。
- **面向"接下来要设计方法"抽带出处的证据**（不是全文泛述）：核心机制（凭什么有效）、关键公式/结构、实验设置、作者明说的 limitation。每条标出处（第几节/图几/式几）。
- 写进 `papers/<论文-slug>/<论文-slug>-note.md`（和同目录的 `.pdf` 一一对应；schema 见 `templates/method-note.md`）。

**回传主会话**：精简摘要 = "一句话这篇能支撑什么" + 2-3 条最关键证据，**不含逐条出处细节**（那些在笔记里）。

> **复用**：`papers/` 一论文一子目录、笔记随 PDF 落盘，换方向做挖方法时同一篇论文的笔记直接复用——已落盘的不重读。派深读子 agent 前，主会话先看 `papers/<论文>/` 里哪些已有 note，只对没深读过的派 agent。

> **边查边讲（深读 agent 回来后，生成路线前）**：主会话先用**白话给用户讲一段"这几篇到底做了什么、给方法设计留了什么证据或线索"**——每篇一两句（它的核心机制、它自己承认的短板），把散落的深读发现收拢成用户一眼看懂的样子。这段不落盘、不是讨论环节，纯粹是让用户在看路线之前先认识这些论文，避免路线一出来就撞见一堆陌生名词。

## Step 10 主会话全局生成路线骨架（主会话，不派子 agent → 写 路线N-<slug>-main.md）

**这一步是判断，留主会话。** 主会话读各深读子 agent 回传的**证据摘要**（全局视角），自己生成 **2-3 条技术路线骨架**——只有主会话同时看到全部证据，才能让几条路线**彼此不同，覆盖不同思路**。若派发给子 agent 各出一条，它们各自只读了自己那摊、没有全局，会重叠冲突（这正是找方向阶段方向成型也留主会话的原因，挖方法同理）。

**用已有证据和线索支持每条技术路线。** 结合用户对路线的构想，按以下步骤设计。

**① 开工先盘点证据或线索 + 先征集用户的想法。** 读证据摘要时顺手建一张「可用于设计路线的线索」——各篇笔记里作者明说的 limitation、future work、"we tried X"式失败自述、可替换组件（起点有 paper-card 时 `swappable_components` 直接进清单）、`literature.json` 里 `cross_domain` 的迁移线索。**整理好线索后先给用户看，等用户先说自己的路线构想**（"这些论文留了这些线索——你自己有没有想走的路线？半句话也行"；不要先给备选方案再问用户，手法见 `code-idea-iterate/references/research-dialogue.md` 手法五）；尽量按用户的原话记录，再直接写成路线提纲（来源: 用户），用户说"没有，你来"不阻塞。**路线的合法出发点 = 用户路线 + 这些线索 + 该方向可利用的资源与专长**；主会话补充的路线找不到证据或线索的打回、来源标「补丁候选」。这条把"深读驱动"和"用户先行"从口号变成可检查的纪律。

**② 每条路线回答四问**（这就是「技术直觉」字段的写法）：**在哪动手**（改哪个环节 / 组件）？**用什么机制**（核心 idea 一句话）？**预期改进及成功判据**（与哪个具体 baseline 比较、哪个指标、预计为什么会有改进、达到多大改进才算成功）？**凭什么信能成**（依据哪条证据或线索，指回哪篇笔记的哪条证据）？四问答不全的骨架不许落盘——**尤其"预期改进及成功判据"，答不出具体名字的路线是假大空，打回**。方向的「主表预览」是这条路线的天花板：路线的"预期改进及成功判据"必须能填进方向的主表，填不进说明路线跑偏了。

**③ 先例自检（硬纪律）**：每条路线的核心假设（预期哪种机制或方向有效）必须对照 `papers/` 里**已深读的最近邻**——先例的结论方向跟假设相反的，要么调整假设，要么显式降级为**高风险路线**（标注要验证什么假设、假设不成立时怎么调整），**不许当主线**。"零先例的核心直觉"同样只许当高风险路线。这条防的是：主会话被自己的论证说服，把已有证据反驳的猜测或缺少先例的直觉当作核心假设，直到独立检查才发现问题（真实踩过的坑：核心直觉"对抗 ⇒ 簇状"零先例，而刚深读过的两篇最近邻的 minimax 结论都是"平"的——生成时没人做这个对照）。

**④ 首个验证实验的要求（硬纪律）**：每条路线必写「**首个验证实验**」——能**判断核心假设是否成立**且成本最低的实验：做什么、查看哪些指标或观测值、什么结果算证实 / 证伪、成本多少，且成本必须在 `idea-seed.json` 的用户资源约束内。**主线的首个验证实验必须天-周级可启动**。**v1 默认分析先行**：idea 的核心假设通常还有待验证（多论文 insight 组合的 idea 尤其如此——"A 的洞察在 B 的场景成立吗"本身就是假设），所以首个验证实验通常是**检验假设的分析或诊断实验**（探表征、测分布、干预变量），以能明确支持或反驳假设为成功判据。与「门控预实验」的界限：检验假设的实验有明确证伪线和归因设计、是路线的一等主结构；缺少判据的探索性预实验没有判定假设是否成立的设计，仍只许当高风险路线的附加步骤。只有当核心假设已有强先例支撑时，首个验证实验才可以直接是与 baseline 比较以检验初步效果的实验（小规模正面结果）。

**⑤ 最小性（硬纪律）**：路线只设计**验证核心假设所需的最小实现**——一个核心机制、跑通首个验证实验为止。两种反模式直接做基线对比回：**为假想完整方法补全组件**（"论文里大概还需要 X 模块"——v1 不需要就不设计）；**基于实验结果的预定假设做设计**（"如果 refine 有效就再加 Y"——Y 是 iterate 拿到 refine 证据后的活）。设计 / 讨论中冒出的 v1 之外的想法，写进路线文件「v1 之外（留 iterate）」节留痕，不进设计正文。

**⑥ 互斥判据 + 数量纪律**：几条路线的差异必须落在**核心机制或动手环节**上——"把 A 组件换成 B 就变过去"的是同一条路线的变体，不拿来凑数。覆盖策略：**一条最有把握的主线 + 一条不同机制的对比路线**；**高风险高回报路线最多 1 条**（且必须过先例自检的降级标注、用户 Step 1 的资源约束允许）——别三条都是同一思想的微调，也别三条都是赌博。

**⑦ 核心假设怎么写**：每条路线 1-2 个"不成立时路线无法成立"的前提；写每条假设时顺手想"**什么证据 / 实验能证伪它**"——这句话直接是 Step 12 独立检查的重点，也是阶段三 spec 失败解读表的雏形。

**⑧ 骨架先请用户确认再细化**：把 2-3 个骨架摆给用户看一眼（衔接「派发前请用户确认」纪律，遵守汇报硬格式——一条路线一张卡），用户一句话毙掉一条，就省一轮细化和独立检查——比 Step 12 挑完再死便宜得多。

**读取纪律**：主会话默认只读摘要建全局图景；**需要某篇的精确出处/公式/实测数字时，才 `Read` 对应的 `papers/<论文>/<论文>-note.md`**。不要一上来把所有完整笔记拉进上下文——那样子 agent 落盘就白做了、token 照样爆。摘要是索引，全文是仓库，用到哪取哪。

每条路线骨架各建 `路线N-<slug>/` 子目录、写 `路线N-<slug>-main.md`（schema 见 `templates/method-route.md`），此刻主会话填骨架部分：技术直觉（四问）、核心假设（成立前提，不成立时路线无法成立 + 什么证据能证伪它）、首个验证实验（做什么 / 查看哪些指标或观测值 / 什么结果算证实·证伪 / 成本）。

## Step 11 细化路线（每路线 1 个细化子 agent 并行 → 更新 路线N-<slug>-main.md）

主会话把路线骨架写好后，**对每条路线各派 1 个细化子 agent**（并行、各管一条、不冲突）。细化单条路线不需要全局（做实 r1 不用知道 r2 长啥样），所以可以派发出去。

**任务书输入**（派时写清）：读本路线 `路线N-<slug>-main.md` 骨架 + 主会话点名的相关笔记清单（`papers/<论文>/<论文>-note.md`，主会话最知道哪几篇跟这条路线相关）+ `literature.json` 的最接近工作部分 + **`idea-seed.json` 的 venue / 资源约束**（细化不许设计出超出用户资源的方案——资源约束在 Step 1 收集了就必须在每个下游环节生效）。工具：paper-search / pdf-mcp / GitHub。补读论文内容时首选 tex-mcp（读 arXiv 论文章节/图/表，`tex_open` 打开固定版本失败才降级 pdf-mcp），PDF 文件本身操作仍走 pdf-mcp。

**细化到什么颗粒度**：目标是**一个工程师读这份文件能把 v1 最小实现写出来，不用再问设计意图**——核心机制拆成几步 pipeline、每步的输入/输出/操作、关键结构/目标函数、训练和推理各怎么走。**细化范围锁死在 v1**：只写跑通首个验证实验 + 判断核心假设是否成立所需的实现，不为假想完整方法补全组件——v1 之外的组件 / 变体想法记进路线文件的「v1 之外（留 iterate）」节，不进设计正文。两条不过界的线照旧：**不写实验设计**（实验总览是阶段三 plan 的活）、**不写 file:line**（那是 execution 读代码后填的）。

**工作顺序**：先把骨架四问展开成 pipeline（几步、每步干嘛），再逐步填实现。遇到**设计抉择岔路口**（组件选 A 还是 B、损失怎么构造）留痕——选了什么、为什么、放弃了什么。讨论②用户可能推翻某个抉择，留痕让推翻成本低。

**证据纪律**（每个设计决策三态标注，不许含糊）：

- **直接证据**：某篇做过同类组件、实测有效——引笔记出处（第几节/图几）。
- **间接证据**：机制在别处被验证过——引出处并说清"别处"和本路线的距离。
- **无证据·假设**：必须显式标注——这些标注就是核心假设的细化版，是 Step 12 独立检查时优先验证的假设。不许把"我觉得合理"混进前两种。

**补检索的边界**：围绕本路线的**具体缺口**查（某组件有没有现成实现、某机制有没有人试过），不是泛泛再调研一轮。补下的新 PDF 进 `papers/<论文>/`、新证据追加进对应 `-note.md` 的规矩照旧。

**三项自查怎么填**（更新回 `路线N-<slug>-main.md` 的「方法层自查」表）：

- **技术可行性**：核心组件逐个问"有没有可靠实现"（官方 repo / 知名库 / 社区复现报告），没有的说清要自己写多少。
- **与现有工作不重叠**：和最接近工作**逐点对比核心 claim**（不是一句"我们不同"），差异点对应「与现有工作的关键区别」节。
- **风险可控**：把骨架的每个核心假设展开成"成立依据 / 有无反证 / 建议的预实验"。

**预期改进怎么填**（硬要求）：打赢了是什么样——**具体数字锚定**：baseline 在 benchmark 上是多少（引笔记里的实测数）、我们目标多少、参照系是哪篇的实测。不许写"预期增益点在 X 指标"这种空话；不许写自我参照的靶子（"达到自己设定的 80%"不是赢）。

**软肋必写**：细化 agent 必须在文件里如实写「**这条路线的软肋**」——自己觉得最站不住的 1-2 处。藏软肋的路线文件，讨论②就没料可磨。

> **细化 agent 有确认偏误**（帮自己那条路线说话）——所以细化之后必须过独立检查方案，不能只靠它自查。

## Step 12 独立检查方案（1-3 个负责检查的 agent，按视角 → layer2-<方向slug>/挑错/挑错-<视角>.md）

这是挖方法阶段的验证环节，也是"一起打磨不退化成选择题"的关键。挑错治的是"验证不足"，和细化 agent（治"泛泛而谈"）分工不同、缺一不可。

**挑错按视角切、检查全部路线**（不按路线切——漏洞类型是正交的，同一条路线要被不同视角都扫一遍；按路线切会丢掉跨路线对比。所以挑错产物放 `挑错/` 目录，不塞进任一路线子目录）。四种视角：

- **检查可行性（feasibility）**：核心组件有没有可靠实现、算力/数据够不够（对照 `idea-seed.json` 的用户约束）、工程能不能落地。
- **检查创新性**：核心 claim 是不是已被某篇覆盖、跟最接近的工作差异够不够（专找"与已有工作重合"）。
- **检查核心假设（assumption）**：每条路线的核心假设有没有先验支持、有没有论文实测数据反驳（最吃 PDF 实证）。
- **检查验证是否充分（必查）**：拿"**v1 跑完能不能判断核心假设是否成立**"逐条检查路线——每条核心假设有没有对应的便宜验证实验（没有 = 缺少能验证假设的步骤）；该做的对照 / sanity 检查有没有被忽略（没对照就无法归因，结果出来也白跑）；kill 信号查看哪些指标或观测值、阈值清不清楚；某个假设能不能用更便宜的实验先验掉（能在 v1 前花一天检验的风险，不许留到 v1 跑完）。这条视角检查的不是"论文里还缺什么实验"，是 **v1 的验证闭环完不完备**。

**视角数随路线数/会议档次伸缩**（主会话按需定，别硬堆）：

- 路线少（2 条）或目标会议一般 → **1 个综合检查**，一份清单把四类都过一遍（验证完备性不许省）。
- 路线多（3 条）或冲顶会（NeurIPS/CVPR 级，查重和假设要求高）→ 拆 **2-3 个视角挑错**并行检查全部路线；验证完备性可并入其中一份，但任务书里必须显式列出。

每个负责检查的 agent：**拿真实证据逐条检查路线的问题**（重点查核心假设——那是"不成立时路线无法成立"的地方）。**可自主找反证**（发起 paper-search、深读、网搜，找"实测数据不支持某假设"的证据，落进笔记标出处）。写进 `layer2-<方向slug>/挑错/挑错-<视角>.md`。

**任务书输入**（派时写清）：读全部 `路线N-<slug>-main.md` + 相关 `papers/<论文>/<论文>-note.md` + `literature.json` 的最接近工作部分 + `idea-seed.json`（资源约束）。注意：路线文件里 Step 11 留下的**「无证据·假设」标注、「设计抉择留痕」、「这条路线的软肋」三节就是现成的靶子清单**——先过这三节，再做自己的独立检查。

**三视角各自打法**（验证完备性打法见上）：

- **检查可行性（feasibility）**：逐个核心组件问"有没有可靠实现"（官方 repo / 知名库 / 复现报告）；算力数据对照 `idea-seed.json` 的用户约束；查工程链路有没有断点（数据怎么来、预处理谁做、评测协议能不能复用）。
- **检查创新性**：拿每条路线的核心 claim 展开 2-3 个 query 变体查重；判定重合的标准沿用 Step 6——同一个问题 + 同一个核心思路才算撞；和最接近工作逐点比，差异不足以构成新贡献的指出来。
- **检查核心假设（assumption）**：逐条过「无证据·假设」标注和骨架核心假设——**优先检查决定路线能否成立的假设**；找支持证据，更找**反证**（笔记里的实测数字、表格；主动搜"X doesn't work"式负结果）。

**漏洞清单写法**（每条四件套）：漏洞描述 + **实证出处**（哪篇哪节哪表）+ **严重度**（致命 = 核心假设不成立 / 严重 = 要大改 / 一般 = 可修）+ 建议的验证/规避动作。严重度这栏是 Step 13 确定如何处理问题的直接输入，不许偷懒全标"一般"。

> **回退前更新文献记录**：独立检查查找反证时发现的新文章，**追加进 `layer1-方向/literature.json`**（对应组 + 空白矩阵改判）——一旦没有可行候选回退，重新提出候选就读全量最新的台账，不按旧信息重复提出候选。

**挑错铁律——找漏洞不产判决**：

- 正例："路线1 的核心假设 H 站不住——论文 X 表 3 实测该条件下反而下降（papers/x/x-note.md），建议先做预实验验 H"。
- 反例："路线1 得分 7、路线2 得分 9，推荐路线2"。

打分排序会让用户变成只能挑高分的验收员，就不是一起打磨了。挑错只让讨论有真凭实据；**选哪条、怎么改是主会话跟用户一起打磨的事**。

## Step 13 按检查结果修改路线（主会话亲自，必要时派补充证据的子 agent → 路线文件 v2）

问题清单回来后，**主会话先拿漏洞修一遍路线，再把修好的路线和修不了的伤交用户判**——不是把原始路线 + 漏洞清单一股脑倒给用户（那让讨论②退化成用户现场做设计）。

**每个漏洞三种处置**（按严重度分诊）：

- **能修**：改设计——路线文件更新成 v2，改动在「问题与修改记录」节留痕（哪条漏洞 → 设计改成了什么样）。
- **能绕**：设计改不动，但可以**转化成验证点**——加预实验、降级目标、加 ablation。漏洞从"设计缺陷"变成"待验证假设"，顺手记为阶段三 spec 失败解读表的素材。
- **修不了**：留作**用于判断是否继续的证据**，交讨论②用户判。

**加固的边界**：修复是补上 v1 被忽略的验证、修掉验证闭环的断点——**不是借机把方案扩充成完整方法**。修复中冒出的"如果成功了还该加 X"类想法，一律不进 v2，记进路线文件「v1 之外（留 iterate）」节当 iterate 候选。

**分工纪律**：修哪里、怎么修是判断，**主会话亲自**；修复需要新证据时（某组件有没有现成实现、某假设有没有人实测过）→ 派补充证据的子 agent（不落新文件，证据追加进对应笔记）。**决定放弃路线、合并、推翻重来 = 用户的事**，主会话不做——它只把"能修的修好，说明还有哪些问题无法解决"。

**修复以一轮为限**。如果修完仍没有可行路线，按 SKILL.md「回退条件与处理方式」返回相应步骤。

**落盘**：问题清单原文不动（保留原始依据）；每条路线 `main.md` 加「**问题与修改记录**」节（逐条漏洞 → 处置方式 → 改动内容）。讨论②用户看到的就是：v2 路线 + 修复记录 + 未修漏洞清单——一眼知道哪里还有伤、值不值得救。

## Step 14 展示 + 一起打磨（主会话，讨论②）

按检查结果修改路线后，主会话跟用户一起打磨方法。同讨论①一样**先给压缩概览、再让用户带着按需深入，不一上来灌**（拿修复记录和未修漏洞当讨论切入点），由用户的吸收速度驱动深挖。**全程遵守汇报硬格式**（一卡一件事 ≤5 行 / 新术语 ≤5 个且必跟白话 / **每次只确认一个决定**——主会话给推荐 + 理由，用户确认 / 否决 / 调整，不摆①②③开放菜单、不在一条消息里堆多个决策）。

**1. 展示各路线要点**：读路线文件（v2），转述四问（在哪动手 / 什么机制 / **预期改进及成功判据** / 凭什么信）+ 核心假设 + 首个验证实验。**提到任何论文默认用户没读过，顺带一句它做了什么**；术语紧接一句话解释。

**2. 展示修改记录和未解决的问题**。逐条说明检查发现了什么、已解决的问题怎么改、还有哪些问题待解决。讨论优先看未解决的问题。

**3. 让用户决定深入哪个（按需展开）**：给完全景后，拿未修漏洞当讨论切入点邀请用户逐个打磨，而不是继续灌。比如这样说：

> "两条路线的方法在这，挑错指出的漏洞里，这几条我已经修好了（改动在修复记录里），这几条修不了。我们逐个看——路线1 的核心假设 H 被论文 X 的实测反驳了（见 挑错/挑错-assumption.md），这篇论文我可以给你细讲它那个实验；你觉得有办法绕吗？还是把路线2 的 B 组件糅进来？想让我深挖哪条证据我从笔记里给你讲。"

- 用户说"漏洞 X 我有办法绕，因为……" → 主会话据此改路线文件、或回头让证据说话。
- 用户说"把路线1 的 A 组件换成路线2 的 B" → 一起打磨合并出新路线。
- 用户质疑某证据 / 想让某篇讲透 → 主会话回 `papers/<论文>/<论文>-note.md`（或原 PDF）核实、细讲，必要时再派深读子 agent 补证。**深挖廉价**（笔记都在盘上），且由用户节奏驱动。
- **触发回退的条件（所有路线均有无法解决的问题）**：分层回退——只有路线不可行 → 回 Step 10 重新生成路线；独立检查得到的证据表明方向本身不成立 → 回 Step 4 重新成型（方向文件和部分 PDF 都在盘上，重做很便宜；候选构想清单已空则回 Step 2）。回退前更新文献记录及连续两轮无可行候选时的处理见 SKILL.md「回退条件与处理方式」。

讨论②拍板后：主会话更新 `spec.json`（方法决策段：chosen 路线，按方向分节，记下挑错指出的关键漏洞、修复处置、用户怎么改的）。一起打磨收敛出一条（或合并出的）方法路线后，进产草稿阶段（Step 15-17）。**多方向时，讨论②收敛一个方向后，问用户是否接着挖下一个方向**（回 Step 9，papers/ 里已有的 PDF 和笔记直接复用）。

## 落盘 schema

本阶段三个落盘文件（`papers/<论文>/<论文>-note.md`、路线N-main.md、挑错-<视角>.md）的字段模板在 **`templates/`**（一产物一文件）——派子 agent 时，只把它要写的那个模板文件连同路径一起放进 prompt。
