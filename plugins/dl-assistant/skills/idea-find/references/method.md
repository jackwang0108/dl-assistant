# 下一轮取证设计

从已定义的问题、当前假设、已有数据（若有）、证据缺口和价值讨论出发，决定下一步怎样减少不确定性。它可以是定向观察、统计分析、训练/干预实验或理论检查，不默认分析先行，也不要求只有一个机制或一个组件。

## 1. 先明确本轮要学到什么

写出本轮开始前相信什么、依据是什么、最关键的未知、替代解释，以及哪种观察会改变哪个判断。首次没有本项目数据就明确未执行；已有试验数据时注明探索来源与复用限制。

探索性实验用于发现现象或估计范围，确认性实验用于区分预先提出的解释。不要在还不知道现象时写必然阳性的预测；探索后形成的假设需标为事后提出，后续独立检查不可假装已经完成。

## 2. 比较取证办法

agent 主动给出能回答该未知的方案、优缺点与推荐，候选数量随需要，不凑2–3条路线。每个方案说明：

- 操作/观测对象、变量、输入输出和必要实现；为何能区别目标解释。
- 控制条件、强简单对照、测量有效性、替代解释和不能识别的部分。
- 需要哪些读数、观察单位、划分、随机性/重复、误差或不确定性处理。
- 可能结果及其对假设的影响：支持、反对、不足、无法区分或执行不可信。
- 时间、计算、数据与学习成本，来源是实测、已有文献还是估计；缺失条件与较便宜替代办法。

实验结构要足以辨别假设，不是单纯为了尽快跑完。没有低成本办法时说明当前设计昂贵并讨论，不能把“天周级”当研究价值的普遍条件。理论问题不强迫构造GPU实验。

[取证方案模板](templates/method-route.md) 记录本轮设计及更远期设想。可说明后续条件分支帮助判断总体价值，但不把预期成功当已知，也不提前细化未批准的全部研究。

## 3. 依据与阈值

对关键设计区分同条件支持、间接支持、尚无证据、有相关反证、信息未取得。对反证说明适用条件；没有先例可以成为主方案。跨任务已有支持不证明本场景有效。

基线数字必须来自实际来源，标版本和协议，不是本项目复现值时明确说明。区分：已知数据、拟检验假设、值得投入的结果、意义有限的结果。

需要判断界限时，阈值基于任务代价、测量误差、已知变化范围或明确研究目标并说明依据。实用界限、数值容差和统计显著性不是一回事。没有依据就不填增益预测：可先估计噪声和范围，或使用有解释的定性预测。探索所得阈值后续用于检验时保留来源并避免测试集反复选择。

不能在看结果后改口径来保证成功。合理设计变更先记录原因、受影响结果及重新核查要求，再获用户批准。

## 4. 按需要独立核查

审查目的具体，不强制多轮人员与固定视角：

- 文献差异：最接近工作是否覆盖当前命题，新证据可以重新打开查新。
- 推理：关键前提和推导缺口、反证适用条件，不能凭措辞判成立。
- 实验识别：观察是否区分解释、是否遗漏关键对照/混杂、是否存在测量伪影。
- 启动条件：数据、模型、预算与代码线索是否真实，哪些仍待 baseline-survey 核查。

核查记录用 [review 模板](templates/method-faultfind.md)，指出实证问题、待验证风险和一般建议，不混为致命缺陷。agent 不需要为显得严格而制造批评，也不能用0引用、关键词缺失、方法形式不新潮推断无价值。修复关键问题后检查是否真的解决；剩余会使结果不可解释的问题不得仅改名为“待验证”后照常执行。

派前经用户确认，各 agent 写独立结果，主 agent 保留原始检查与处理理由。不得并行覆盖同一路线或文献累计文件。

## 5. 确认下一步投入

展示当前问题/假设、为何值得查、推荐实验会减少什么未知、结果影响、成本依据与剩余限制。用户不熟悉时讲清这些内容，不能只给一张表要求确认。

价值认可与资源授权分别记录；用户同意研究问题不自动批准昂贵训练，也不意味着所有细节已科学确认。关键资源未知时可以先批准小规模计时/测量，不把可申请资源当已获得。

用户确认研究说明与实验计划后才生成实验交接文件。结果可以决定继续、改问题或停止，不能以必须阳性为验收。整体价值发生变化时返回 direction.md 的价值讨论，不能只优化局部实验。
