# 主动发现问题与形成假设

本文件说明怎样从用户的研究起点和已有证据主动发现问题、提出并筛选可检验的假设，以及向用户说明当前问题是否值得继续研究。

在[运行手册](research-workflow.md)的 Step 1–3 使用本文件。主会话负责检索、推理、筛选和推荐。用户参与澄清兴趣与约束，决定是否继续研究。后续取证由 [Step 4 取证设计](evidence-design.md) 处理。

## 1. 核查起点，选出这次初查的问题

先复用已知目标、兴趣、所在项目、已有观察与资源。只补问会影响下一步的信息。目标会议、算力或数据未确认时照实记录，以后设计取证时再核实。优先查用户给出的调研路径或项目 `docs/literature-survey/`。找不到时请用户提供以前的结果路径，或建议先做 [literature-survey](../../literature-survey/SKILL.md)。已有调研较旧时，结合实际覆盖和领域发表节奏决定建议重新调研还是只补特定缺口。

| 起点 | 先做什么 | 初查要回答什么 |
| --- | --- | --- |
| 一篇论文 | 确认论文和版本，读相关论点、异常结果或局限的原文。按需沿引用找直接相关的前作及后续验证 | 论文实际观察到了什么，在什么条件下得出结论，哪条观察值得解释 |
| 用户观察或先前结果 | 写明比较对象、实际条件、测量口径及原始记录位置。区分用户报告、已核事实和主会话推断 | 目前的差异是稳定现象，还是可能来自设置、误差或测量 |
| 宽泛方向 | 利用调研的分类、代表工作和待验证问题，找有具体证据的冲突、失效条件或反常结果 | 哪个可描述的现象值得继续追，为什么它会影响解释或实际选择 |
| 已有构想或假设 | 先准确复述用户设想，再查它依赖的现象、最接近的做法及可能反驳它的结果 | 哪部分已有支持，哪部分仍是推导，是否已有工作回答同一问题 |

复用 `paper-card.json` 时，可从已读范围、论点证据、候选替换点和连接线索开始。结合 `reading_goal`、`worth_reason` 理解 `worth_reading` 对当时阅读目的的建议；上下文缺失时，回查与本次任务直接相关的证据。已有方向跟踪记录可提供持续出现的主题和反复报告的局限，按实际日期和来源核对。

用 [paper-search](../../paper-search/SKILL.md) 的 `get_capabilities` 核来源，随后用 `search_papers` 查对象、现象及最接近机制。已知稳定论文标识时用 `get_papers`，只有标题时用 `resolve_papers` 核对候选。确认身份后，视问题用 `get_paper_references`、`get_paper_citations` 或 `find_related_papers` 扩展。用户限定资料范围时按该范围查。只读摘要时，说明能核的是作者的摘要表述，决定推理的设置和结果要读原文。

初查做到能界定现象、提出可区分的解释，或指出原构想的关键问题即可。用[研究起点模板](templates/research-seed.md)保存 `idea-seed.json`，记录这一轮查到了什么、为何可以继续、下一条最值得核的证据是什么。

## 2. 主动提出、比较并筛选候选

从证据中找有解释价值的差异。候选可以来自不同结果之间的冲突、稳定失效条件、未经核查的理论前提、指标与实际目标的错配，或用户经验和跨领域机制。引用用户直觉时保留原来的意思，主会话接着推理并给出可检验的候选。比较时使用同一证据标准。两个组件可以组合、论文把某项工作列为未来方向，或相关术语用得相似，都只是线索。要进一步说明什么机制可能发生在什么条件下，以及验证后会改变什么认识。

对重点候选，写出以下因果或推理链。

> 观察及出处 → 可能机制 → 最强替代解释 → 各自的预测 → 下一条需要的证据

1. **观察。** 说清哪个对象、什么条件、观察到什么，给出处。比如同为「加速」，先分清是在比较单张请求延迟、批量吞吐，还是计算量。
2. **机制。** 说明现有前提如何推到候选解释。指出最弱的一步需要靠哪项证据检查。涉及方法迁移时，核原场景依赖的条件在当前场景是否具备。
3. **替代解释与预测。** 选目前最有说服力的替代解释，写双方分别预计什么现象。预测相同时，寻找可以改变或固定某一变量的条件，或补读能区分解释的原文。
4. **科学问题与意义。** 明确回答「即使做成功，结果会回答什么科学问题，论文能据此提出什么新结论？」同时写什么结果虽可靠但意义有限，以及哪项观察会让原问题或假设需要修改。

主会话比较候选，写明推荐、待补证或放弃的理由。推荐项给最关键的依据、替代解释及可能新增。待补证项写明缺哪条证据和不同结果会怎样改变推荐。放弃项引用反证，或说明最接近工作在什么条件下已回答同一问题。查无先例时，按具体推理、预测及取证途径判断，并记明查过的范围。一个问题若因新增证据变得更有意义，可以调整推荐。按[候选记录模板](templates/research-candidate.md)写入 `candidates/candidate-<编号>-<slug>.md`，筛选的关键依据和下一步写入 `spec.json`。

## 3. 用定向补查反复检验推理

先从已做调研的 `survey.json` 选取与当前问题有关的论文、比较和待验证问题，再用 `coverage-review.md` 检查实际查询截至日期、来源和待补范围。可回查同版本原文的证据直接引用。根据当前候选和已有覆盖，决定还需要执行哪些查询。

| 核查任务 | 具体怎么查 | 如何判读 |
| --- | --- | --- |
| 近期工作 | 围绕问题、任务和机制的不同叫法，从已有覆盖的截至日期判断需补的时段。根据领域选择可用来源和日期口径。按需使用 [HF 补查](../../literature-survey/references/hf-papers.md) | 说明实际查到哪一天、哪些来源或时段有缺口。近期论文改变假设时，将其加入证据记录并重评 |
| 最接近的工作 | 分别用问题表述、机制同义词、关键条件和对照查。同一命题可能藏在不同任务术语下，沿确认过的论文查前序和后续工作 | 核论文的实际贡献、任务、条件、设置和对照。逐项写已回答什么、哪部分仍未回答，避免用期刊档次、热度或引用数替代内容比较 |
| 反面证据与跨场景线索 | 按失败条件、消融、敏感性、相反结果及其他领域的等价机制搜。定位原文表格、假设或边界 | 比较反例与候选所依赖的条件。区分适用的反证、条件不同的观察及尚未核到证据。机制迁移时明确要保留的前提 |

本轮查询保存在 `literature/search/`，按实际参数、日期口径、截至时间、来源状态和覆盖记录区别成功无命中、部分结果、失败和未执行。使用固定版本的原文核对会影响结论的对照和读数。需要单独记录本轮补读时，按[论文证据笔记模板](templates/paper-evidence-note.md)保存到 `literature/papers/`。论文身份用稳定标识或已核实的互链合并，标题相似只作为待核提示。版本或来源冲突保留各自出处。

用[研究问题证据模板](templates/question-evidence.md)更新 `literature/literature.json`。把每条关键证据关联到问题、假设或候选解释，明确支持、削弱或仍无法区分哪一步，并写下证据条件。与当前问题无关的上游分类和整批论文可按原路径回查。

需要委派时，先说明数量、任务、输入、独立输出路径和分工理由，等用户确认。任务可按最接近工作、竞争解释、反面证据或技术条件分配。给不同核查者相同的已核事实和问题，各自保存原始结果。主会话综合并核查冲突。

## 4. 给出研究价值判断，与用户讨论

对推荐项先讲清问题和必要背景。介绍相关论文时，用一句话说明它做了什么、为什么相关，再指向版本及原文位置供复查。向用户说明以下内容。

- **当前问题和可能的回答。** 前人已回答到哪里，这次多问了哪一部分。即使假设成立，论文可以新增哪项科学结论、适用于哪些条件。出现可信反例时，可能据此界定什么范围。
- **推荐理由和最强反对理由。** 说清现有证据最有力的一点、最弱的推理环节、仍未排除的解释。若新证据会改变建议，指出具体该查哪项材料。
- **剩余价值和投入上的判断。** 改变问题或范围后，重新比较能留下什么认识或实践意义。只剩不同设备、数据或略改设定时，说明这些变化是否能回答新的问题。此处可指出资源未知如何影响下一步，具体投入留到取证设计后确认。

主会话先给理由和推荐。用户可以挑战相关证据、要求补背景、调整关注点或决定是否继续。按实际答复写决策日志。用户认可一个研究问题时，记录认可的范围；假设结论和正式取证投入分别在后续处理。

## 5. 根据证据决定下一步

有合理依据和可继续核查的问题，且用户认可研究取向时，保存问题、假设、关键证据及剩余未知，进入 [Step 4](research-workflow.md#step-4-选择证据写出对照并检查设计)。已有工作覆盖原问题、出现可比反证，或问题缩小后研究增量消失时，更新候选和 `spec.json`，回 Step 2 重新筛选。仍缺决定性材料时写具体补查或取观察任务。预算已到或继续检索难以改变推荐时，给出暂停或换问题的理由及续做条件。详细路径见[产出约定](research-records.md)。

## 贯穿示例 · 裁剪后 FLOPs 下降，端到端延迟未降

以下沿用[运行手册案例](research-workflow.md#完整示例--边缘设备上的视觉模型加速)，研究起点、论文和结论均为虚构。

1. **初查。** 用户报告批大小为 1 的端到端延迟没有随裁剪下降，还未提供原始日志。复用调研中 A v2 §4.1、§4.2 表 2 和 B v1 §4.2 表 1。A 是同一设备上的单张端到端对照，B 是另一设备的批量子图吞吐。两篇结果各自说明不同问题。先核用户的运行时和计时边界，再分析裁剪为什么没有带来预期收益。
2. **候选推理。** 访存解释认为中间张量写回可能仍是瓶颈，预测算子实现固定时，延迟随写回量下降而变化（H2）。替代解释是裁剪改变形状后，运行时选了不同实现，预测在写回量相近时，延迟差异跟随实现切换（H3）。两篇论文都只提供线索。先查有没有同条件的分项对照或轨迹。
3. **筛选和补查。** 查到上游已核的 C v1 §4.3 表 3，在设备 C 上验证了压缩加融合的组合。撤回原先关于「首次组合」的预期主张。表 3 的基线同时关闭压缩和融合，无法说明写回量或实现切换的单独作用。建议继续核 Q2「什么条件能解释并预测单张场景的组合收益」。依据是该问题会改变用户该不该同时使用两项改动。主要限制是分项材料未取得且本项目的测量条件尚待核。补查聚焦分项消融及运行时实现，仍缺可比对照时据实保留未知。
4. **和用户讨论价值。** 「已有工作说明组合在一台设备上可以更快。我们现在要回答的问题是，什么条件决定它能不能带来收益，以及能不能预测收益何时消失。如果看到的仍只是某台机器上的配置差异，科学结论就只到这个设置。若能区分少写回和算子实现切换，就可能说明哪种条件下该启用哪个改动。最大的反对理由是 C 的补充材料可能已经回答这个问题，所以我建议先核该材料，保留在当前设备上检验机制的准备。你认可这个问题后，我们再一起看取证方式。」
5. **保存下一步。** `idea-seed.json` 记原始观察及设置未知，候选文件记 H2、H3 和筛选理由，`literature/literature.json` 引用 C 表 3 的证据和补查范围。`spec.json` 记录问题由 Q1 到 Q2 的修订、用户答复和下一步。认可继续研究 Q2 时可进入取证设计，具体实验和投入待后续确认。
