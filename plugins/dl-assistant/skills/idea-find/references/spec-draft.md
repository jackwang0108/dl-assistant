# 下一轮实验交接草案

当用户认可当前问题的研究意义且下一步需要实验时，先写好交接草案，再把 spec 和 plan 的文件路径一起给用户审阅。两份当前版本均获明确批准后才交接执行，记录批准对应的文件版本与范围。若仍需阅读、推理或决定暂停，保存当前认识即可。

文件名保持：`specs/<slug>-idea-spec-draft.md`、`<slug>-idea-plan-draft.md`、`<slug>-claim-tree-draft.json`。三份文件自足且相互引用，包含执行所必需的证据位置，不能依赖交接后不存在的会话内容。

## 研究说明：当前问题与假设

保留共享 spec 的 §0–§4 及附录位置以便中期发现内容，但采用下列含义，不照搬预设最终论文结论的措辞：

- **§0 研究问题与当前假设**：明确问题定义、范围、局部Q/H编号及稳定命题。P1对应当前候选总假设，不写成已经发现的论文结论；列替代解释、条件与已有证据，映射本轮要检验的claims。
- **§1 问题为什么值得回答**：目标用户/研究者的实际问题或科学认识缺口、回答后新增什么、哪些结果意义有限、问题收窄后的价值变化、已讨论的投入理由。
- **§2 已有认识与出处**：最接近工作、支持/反对证据及适用条件、尚未取得的信息、版本与原文位置、检索范围和限制。文献不算本项目证据。
- **§3 与已有工作差异和价值边界**：作者已做什么、本轮研究多问什么、差异为何可能重要，创新性待核查部分。不把supported当创新点。
- **§4 可能结果与下一步解释**：支持、反证、不足、无法区分、执行或测量不可信分别怎样解释；注明依据与外推限制，哪些变化需要重新讨论研究价值。不以任意阈值或必须阳性验收。
- **附录：实验载体需求**：模型/任务/数据/测量接口、强对照需求、资源约束与未知、候选仓库真实URL及未核查项。前驱改进型或基础代码需求按真实研究形态说明，不限定只能有这两种研究类型。

目标会议可未知，只记录用户已确定的目标，不编造会议档次、日期、GPU规格。模块级实现需求写清，精确file:line等读真实代码后补，不伪造运行入口。

## 本轮计划：为哪种判断取得什么证据

沿共享 plan 的实验总览、方案设计、每实验原理、阶段安排、资源和完成定义组织，但未适用部分明确省略：

1. 本轮开始前的认识、已有数据（若有）、关键未知、问题/假设映射和期望减少的不确定性。
2. 探索或确认的类型；若探索后形成新假设，后续独立检验与测试复用限制。
3. 输入输出、实现、关键公式/步骤和必要对照，条件是否可比，不能区分的解释。
4. 观测单位、数据来源/划分、指标与读数、统计/误差处理、资料和测量有效性。
5. 不同结果对假设的影响，判断界限的具体依据。没有先验数值时标未知，安排探索性估计或有理由的定性预测，不制造预期提升。
6. 执行顺序与依赖、预算依据、便宜替代、已批准投入、缺失资源及停止/返回条件。
7. 可执行性边界、真实入口和待绑定工程项；核心科学设计未知则返回研究讨论，不交给 execution 临时发明。
8. 完成定义为真实数据、对照检查、偏差和可解释范围齐全，不要求任何假设成立。结果须回答“观察到什么、原判断应如何更新”，未决同样允许。

能预测后续研究分支有助于判断意义，但不要求完整最终方法或论文实验矩阵。工程入口待 setup 绑定不代表科学设计也可以空缺；关键比较无法定义时只交付准备任务或暂停，不标科学实验已可启动。

## 假设记录：兼容两层 claims 结构

字段结构参考 [claims-template.json](../../dl-assistant/references/claims-template.json)，遵守其支持与创新性分开记录的定义。沿用 version、snapshot_date、parent_version、paper_claim、claims 字段便于交接：

- P1 是候选总假设，status=active、verdict=pending、supported_by=[]。明确探索问题尚无方向性总假设时，paper_claim可为null、claims可为空；不为凑两层结构编造命题。问题本身仍未定义清楚则先返回问题形成。
- 子论点只记录本轮确实要检查的命题，type 按 hypothesis/mechanism/performance 选；实验完成条件等工程任务不伪装成研究假设。探索性取证尚无方向预测时，可陈述明确的待检验关系或边界并标探索，不预设阳性。
- 所有 verdict=pending、evidence=[]、is_innovation=false、evidence_strength=none，method_tag空；version/snapshot_date在正式进入版本记录时由下游填写。evidence_quality.comparable 在实验前未知，可为 null，notes说明不可提前声称通过。
- H编号到C编号的映射及候选P1范围写进notes；命题变化分配新ID，原ID不改义。问题和探索性目标可保留在研究说明，不硬转换成命题。
- 先验文献证据留研究说明，不能填入验收 evidence 冒充新实验结果；创新性与价值判断独立描述，不由 supported 自动升级。

## 接收与执行顺序

先由 baseline-survey 核对候选仓库与实验载体；选定后 code-project-setup → code-paper-reproduction → 按需 code-idea-prepare → **code-reading（必经，用户读懂代码）** → code-idea-execution。

交接必须带三份草案、批准计划、相关candidate/handoff自查路径、必要原文证据和后续选型/准备报告；文件不在时说明具体缺失，不自动扩大传输授权。execution起手结合真实代码绑定工程细节，研究设计发生变化时回到用户与研究判断，不能默改问题或测试口径。

给中期的明确要求：按本轮问题/假设取得可信数据，分别报告实现失败、测量问题和科学观察；下一轮 iterate 再从已有问题、假设与数据出发更新认识、价值和取证计划。execution与iterate已按本意图更新；后期skills已配套共享研究判断；接收历史项目记录时核对缺失与语义冲突，不将旧字段当新版验证。
