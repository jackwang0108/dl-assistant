# 研究说明、取证方案与 claim 草案

本文件说明怎样把已认可的研究问题和首轮取证设计写成三份可审阅、可交接的草案，并记录用户确认的版本、投入范围和仍待核实的条件。

**研究说明（spec）** 回答「研究什么、为什么值得、成功后能主张什么」。

**本轮取证方案（plan）** 回答「这轮要弄清什么、怎样取得证据、不同结果怎么解释」。

在 [工作流 Step 5](research-workflow.md#step-5-提交草案确认投入和交接版本) 写草案。主会话将科学问题、实验动作和待检验的命题对齐，再把当前的两份 Markdown 草案一起给用户审阅。各份文件应能通过所列路径和编号回查证据及解释依据。继续读文献、补观察或暂停时，按 [决策日志约定](research-records.md#决策日志与续做) 保存当前判断和下一步。

| 文件 | 从哪里取材料 | 写到什么程度 |
| --- | --- | --- |
| `specs/<方向slug>-idea-spec-draft.md` | `spec.json` 中已讨论的问题与假设、`candidates/` 中的价值判断、`literature/literature.json` 及关键原文 | 写明当前问题、假设、最接近工作的证据与边界、成功后可能提出的结论，以及实验载体需求。注明关键证据版本和原文位置 |
| `specs/<方向slug>-idea-plan-draft.md` | [取证设计记录](templates/design-record.md)产出的 `evidence-design/design.md` 当前修订版，以及影响设计的核查记录 | 提取推荐设计、关键对照、测量、结果解释、成本和准备条件。引用设计路径和修订标识，区分本轮待确认的执行范围和后续备选 |
| `specs/<方向slug>-claim-tree-draft.json` | 研究说明中的 Q/H 与取证方案中能检验预测的取证项 | 按当前两层格式记录可由本项目证据检验的命题。用编号关联问题、假设、取证项及所对应的草案版本 |

## 一、研究说明草案

沿用[共享 spec 模板](../../dl-assistant/references/spec-template.md)的 §0–§4 和附录位置，便于下游定位。初稿用已有证据说明为什么值得做，用研究假设描述预期主张。

写完后检查，即使首轮取证得到预期读数，哪些结果只说明实施或测量可行，哪些结果能回答科学问题，以及哪些结果还需要补对照才支持预期主张。写清相对最接近工作的新增、适用条件和最强替代解释。后续由 `code-idea-iterate` 用实际观察复核这些判断，并评估最后有哪些发现可用于论文论证。

| 章节 | 写什么 | 从哪里取材料 |
| --- | --- | --- |
| §0 总论点与本轮范围 | 写科学问题 Q、候选总假设 P1、竞争解释 H 和本轮对应的子论点。给出条件和可区分的预测。Roadmap 记录各命题当前状态，后续分支按可能的取证结果说明 | 候选记录、`spec.json` 的当前问题和假设、取证设计 |
| §1 问题定义与意义 | 写研究对象、范围、现象、已有解释的不足，以及谁会因回答这个问题而改变判断或做法。交代问题收窄后剩下多少意义 | 起点记录、候选筛选和研究取向决定 |
| §2 文献基础 | 写最接近工作做了什么、实际设置、支持和反对证据、固定版本、原文位置及覆盖限制。标明哪些信息来自摘要，哪些已核正文 | `literature/literature.json`、引用的上游记录和论文笔记 |
| §3 预期新增与边界 | 明确回答「即使做成功，结果会回答什么科学问题，论文能据此提出什么新结论？」写清与最接近工作相比多回答了哪个问题、依赖什么条件、哪些结果的意义有限 | 研究价值判断、最接近工作对照和仍待核的差异 |
| §4 结果解释与下一步 | 用表格说明什么观测支持或削弱假设、什么结果无法区分解释、测量或执行偏差会怎样影响判断。为每条注明所检验的假设、判据依据与后续行动 | 本轮取证方案的对照和判据、独立核查中的关键风险 |
| 附录 代码接入点与待补齐 | 写模块级需求和接入目标、任务、模型、数据、测量接口、资源与候选仓库线索。需要选型时在「待补齐」写研究构想类型、仓库用于比较基线还是开展分析取证，以及已知 URL 和未查项 | 方案条件、项目信息及仓库线索 |

目标会议按用户已确认的信息填写，可以未知。代码接入点写到模块及输入输出层面。精确文件行号、实际运行入口和正式版本号在拿到真实代码后补。可以先写清判据怎样取得，具体阈值等噪声基准、已知对照或用户验收要求到位后再确认。

## 二、首轮取证方案草案

按[共享 plan 模板](../../dl-assistant/references/plan-template.md)及[编写原则](../../dl-assistant/references/plan-writing-principles.md)组织。先写总览和对照，再把实际需要执行的取证项逐项写清。方案数量由要区分的解释和可用资源决定。

1. **本轮关键未知。** 写入 Q/H 和 claim 编号，交代原先相信什么、已有证据的边界、这轮能减少哪个未知。注明该项用于探索、确认，还是准备与测量检查。用探索数据提出的新假设，记录后续怎样用独立材料检验。
2. **方案设计与共享条件。** 写最小必要的实现、原理、输入输出、代码模块及对照。列明哪些任务、模型、数据、硬件或运行时条件必须保留。缩减规模时说明依据、保留项和结果可以解释的范围。
3. **每项取证的原理。** 说明对应预测、各对照改了什么、排除哪项替代解释、观测单位及指标、数据划分、重复和误差处理。把可能结果对应到支持、削弱、无法区分或测量不可信，注明何时需要补对照或重做。判据写出依据，未知时先写怎样取得可用基准。
4. **执行顺序、资源和停止条件。** 标明依赖、优先项和可选分支，给出成本依据及待核条件。用户只批准准备工作时，明确这轮可做的检查和停止位置。超过获准范围的部分保留为待确认。
5. **工程接入和完成定义。** 有真实代码时写可核的入口，仓库待选时写执行方要核实的接口、配置和运行步骤。完成定义检查记录、实际条件、对照、结果及偏差是否齐备，确保下游看得出这轮回答了什么、还回答不了什么。核心科学对照尚未定义时，先回到取证设计，或只交接已明确的准备任务。

给用户讲解时按「要分清什么 → 为什么这个设计能分清 → 每个对照有什么作用 → 看见不同结果会怎样判断」展开。说明实际结果需要保存哪些证据，以便执行后用它们分析和修订假设。

## 三、初始两层 claim 树

使用当前本地 [claims-template.json](../../dl-assistant/references/claims-template.json)。P1 写待检验的候选总假设。子论点写本轮可检验的研究命题，在 `notes` 记录 Q/H 与取证项编号的关系。准备代码、跑通评测和能否采到稳定轨迹写在 plan 的准备任务里。问题或可检验命题还没形成时，回到定义问题或设计取证，可先保存已明确的准备任务。

- 初始 `evidence_assessment` 为 `pending`，子论点的 `evidence` 为空，P1 的 `supported_by` 为空。`evidence_strength` 为 `none`，`is_innovation` 为 `false`，`method_tag` 和 `evidence_assessment_source` 留空。文献证据在研究说明引用，运行证据实际取得后再填入 claim 树。
- `evidence_assessment` 记录本轮证据在实际条件下对具体命题的支持程度。实验跑通、读数有效、证据支持命题、结果形成科学贡献分别判断。`is_innovation: false` 表示草案阶段尚未确认贡献。后续即使证据判断更新为 `supported`，也要另行核查回答了什么科学问题以及相对已有工作的新增。
- 子论点类型随命题选 `hypothesis`、`mechanism` 或 `performance`。草案的 `evidence_quality.data_validity` 为 `unassessed`，`issues` 和 `inference_limits` 初始留空。正式取证后，在对应证据里写实际对照、条件和限制。
- 研究命题改变时分配新的 ID，记录与原命题的关系。正式 `version`、`parent_version` 和 `snapshot_date` 由下游建版本时确认。

## 四、确认与交接

交接时，接收方应能从材料和批准记录确认：现在可以做什么、做到哪里应停、需要带回哪些证据，以及下一次确认哪项决定。

### 交出材料前，核对每项任务的批准

1. **对照检查三份草案。** 确认 Q/H、待检验子论点、取证项及解释规则逐项对应。检查问题或假设改动后，预期新增是否仍有依据，以及当前哪些科学条件已定义、哪些工程条件仍待绑定。
2. **把当前版本一起给用户审阅。** 说明研究问题与预期新增、本轮关键对照、不同结果的解释、预计预算和未决条件，再附两份 Markdown 草案。用户可一次确认两份文件，并明确批准准备任务或正式实验的具体范围。
3. **把决定与任务写进现有记录。** 按 [产出约定](research-records.md#决策日志与续做)，在 `spec.json` 的 `decisions` 记录决定 ID、用户实际答复、`draft_versions`、`approved_scope` 和 `pending`。交接摘要引用决定 ID，并把批准文字对应到 plan 中的取证项、资源和停止点。

| 用户确认了什么 | 怎样记录，执行方能做到哪里 |
| --- | --- |
| 认可研究方向或同意准备方案 | 记录研究取向的决定及仍待确认的投入。按实际答复继续设计或核对材料 |
| 只批准准备任务，例如在一台目标设备上做 T0 | 记录两份草案的版本、获准任务、资源、完成条件及须带回的证据。做到 T0 的停止点交回。写入同一份 plan 的 T1 保持待决，相关子论点的证据判断保持 `pending` |
| 批准正式取证 | 记录实际获批的取证项、关键对照、测量与解释规则、投入和停止条件。接收方沿用仍覆盖当前版本的批准，并按 execution 工作流核对实现和开跑范围 |

### 给执行方的接收核对表

需要仓库选型时，向 `baseline-survey` 提供研究说明中明确的任务、模型、数据、测量接口、候选仓库线索和载体用途。选定后经 `code-project-setup`、`code-paper-reproduction`、按需 `code-idea-prepare` 和 `code-reading`，再交 `code-idea-execution`。将实际接收方、版本和范围记入 `spec.json`。

| 接收时核什么 | 到哪里查，核完怎样记录 |
| --- | --- |
| 三份草案和批准记录 | 确认文件能打开，研究说明与取证方案的路径和修订对应 `decisions` 中的批准项。核初始论点与这两份草案的 Q/H 和取证项对应。注明路径相对项目根、调研目录还是实际存储位置 |
| 当前能做的任务及边界 | 对照决定 ID、用户答复和 plan 的实际取证编号。从中取出获准任务、可用资源、停止点、须带回的证据及 `pending`。续做时复用覆盖当前任务的明确授权 |
| 必须保留的科学条件和证据位置 | 查取证设计、最接近工作的原文与已有核查结果。列清要保留的研究对象、比较组、测量口径和解释条件，并指向记录里的具体位置 |
| 实际环境、基准和工程待补项 | 读取实际的选型、setup、reproduction、cleanup 记录及验证范围。照 plan 核仓库、入口、设备、运行时、资产和测量能力。交接时区分已实测、已静态确认及尚待核实 |
| 版本快照与下一步 | 建立正式版本时，把三份草案对应到 `01-idea-spec.md`、`02-research-plan.md` 和 `claims.json`，保留来源及批准记录。按[执行手册 Step 1](../../code-idea-execution/references/workflow.md#step-1-恢复现场核对输入与批准范围)汇报接收结论 |

当前仓库提供的一条实际命令、某个配置值或源码位置，只要符合已批准的科学条件，可以补进 `03-claim-code-map.md` 和对应运行记录。若换设备、调整计时口径或缺少隔离对照会改变可比性或解释范围，记录原计划、实际发现、可行建议和影响，再确认受影响的任务。已获准、且可独立完成的准备工作按原范围推进。

完成已移交的准备任务后，带回实际输出、成本、条件和偏差。将已经回答的问题与正式实验待决项分别写清，并在原决定及版本的基础上记录下一次确认。

## 填写示例 · 边缘设备上的视觉模型加速

以下为虚构示例，沿用[运行手册案例](research-workflow.md#完整示例--边缘设备上的视觉模型加速)的 Q2、H2、H3 和基准核查批准范围。

**研究说明。** C v1 §4.3 表 3 已验证组合部署。Q2 追问同一设备和运行时中的单张请求下，哪些条件能够解释并预测组合收益。P1 暂把中间张量写回量和运行时实现选择作为候选解释。若能分别操纵、复查这两项，就可以讨论各机制在所测条件下何时改变收益。若只能观察到组合比原版快，只能记录所测设置的收益，机制贡献仍待取证。若能确认某个条件下组合收益稳定消失，也可能形成有价值的边界结论，其新增仍需与最接近工作对照。依据指向 `literature/literature.json` 的 E1，分项消融未取得。实验载体需支持同模型的部署比较及轨迹采集。

**本轮取证方案。** T0 先确认目标硬件、运行时、计时边界、重复波动和轨迹能否取得。它是准备任务。T1 记录原版、仅裁剪、仅融合和组合的延迟、精度和执行轨迹，再检查是否能够隔离其中的变量。如能保持实现固定且建立不同写回量的可比对照，就用它检验 C1。如能获得写回量相近、运行时实现不同的可比对照，就用它检验 C2。若两项一起变化，四组结果仅用于确认配置收益，机制判断待增加隔离对照。正式对照的预算等 T0 提供耗时和波动依据后确认。

| 科学问题 | 假设 | 待检验子论点 | 取证项 |
| --- | --- | --- | --- |
| Q2 组合收益在什么条件下出现 | H2 访存解释 | C1 实现固定时，组合收益随中间张量写回量下降而变化 | T1 中实现固定的可比对照 |
| Q2 组合收益在什么条件下出现 | H3 运行时实现解释 | C2 写回量相近时，延迟差异主要随算子实现选择变化 | T1 中写回量相近、实现选择不同的可比对照 |

### 可直接发送的交接摘要

以下假定用户已批准 T0，所列路径相对于调研目录。

> **交接任务**
>
> 先确认在一台目标设备上能否稳定取得单张端到端延迟、写回量和实际算子实现。需要选型时，仓库须支持同一模型的部署比较及运行时轨迹采集。选型和准备报告随草案交执行方。
>
