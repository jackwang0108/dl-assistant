# 找方向阶段（Step 1-8）打法

找方向阶段的产物是 **1-2 个"方向"**——每个讲清"哪类研究者遇到什么困难、我们能利用什么已有资源或专长、做出来的论文长什么样（WHAT）"，不设计方法（HOW，那是挖方法阶段）。本份只讲**怎么干活（流程）**；七个落盘文件（idea-seed.json、pitches/*.md、survey-channels/*.json、literature.json、方向N-main.md、方向N-importance.json、方向N-verify.json）的 schema 在 `templates/`（一产物一文件）。目录树 / 落盘次序见 `output-contract.md`。

**分工原则（贯穿本阶段）**：**通过对话明确问题、写初步构想、方向成型是创造性判断 → 留主会话且全局**（避免候选与已有工作重合）；**定向调研、方向充实是体力活 → 派发给子 agent 且落盘**。

> **本阶段的因果链：清晰锚点 + 资源与专长（Step 1）→ 初步构想清单 + 由用户筛选构想（Step 2）→ 定向调研验证（Step 3）→ 方向成型（Step 4）**。
>
> - **方向从"痛点 × 资源与专长"里长，不从文献空白里长**——"没人解释 X"是空白，但未必是你的 paper。痛点（哪类研究者遇到什么困难）和资源与专长（我们能利用什么已有资源或专长）缺一个，方向就是替别人找的。
> - **用户的品味是第一过滤器，必须前置**——先产便宜的初步构想 让用户杀，保留的候选才配进贵的调研和验证。反过来的顺序（走完调研才让用户看成品）必出垃圾。
> - **调研的角色是验证器，不是生成器**——"gap 真实存在吗"的答案从调研产出里读出来；但调研不负责生方向，方向在 候选构想清单里已经有了。
> - 调研验的是 **gap**（空白真不真、做得好不好）；Step 6 充实验的是**方向**（我们想的具体思路是否与已有工作重合、能不能启动）。**gap 真 ≠ 方向可行**，两层别混。

> **一起打磨前提**：方向不是给用户做选择题的成品。Step 7 主会话拿方向 + 证据跟用户逐轮打磨，用户质疑一点、主会话回头补一份证据再改。
>
> **派子 agent 的类型**：调研 / 充实这些要落盘的活，派**有写权限的 agent**（`general-purpose`）——不要派 `Explore`（只读，写不了文件）。
>
> **发起前先请用户确认**：每次派发（Step 3 通道调研、Step 6 每方向的充实）之前先请用户确认——纪律见 SKILL.md「派子 agent 两条规矩」。
>
> **已有线索都要验证**：paper-card / connections.md / LS / DT 给的种子，角色是**对话素材 + 查询锚点**，不是候选结论——哪怕来自刚读的新文章，里面某些想法也可能已被做掉。种子的价值是给出具体可检验的切入角度；"现在还能不能做"由 Step 3 对近 12 个月文献的检索回答。

> **让用户跟得上（贯穿本阶段）**：子 agent 会检索大量用户没读过的论文——对用户这些全是新信息。若把这些发现攒到讨论环节一次性倾倒，用户来不及消化，一起打磨就退化成点头。所以主会话在**每次派发前后的停顿**上，顺手用白话把刚拿到的东西讲给用户听，让用户的上下文跟着调研一起长；到讨论时用户已经有背景，已经了解相关背景。**一切摆给用户看的汇报遵守 SKILL.md「讨论汇报硬格式」**：一卡一件事（≤5 行）、新术语 ≤5 个且首次出现必跟白话、每次只确认一个决定。具体见下面各步的「边查边讲」提示和 Step 7 的按需展开式讨论。

## Step 1 起点对齐 + 确认可用资源与专长 + 通过对话明确问题（主会话 → idea-seed.json + spec.json 起点段）

主会话亲自做，不派子 agent。三件事：对齐起点（硬门槛）、确认资源与专长、扫种子做通过对话明确问题。

**① 起点对齐（问用户，拿不到具体值不许往下走）**：

- 起点是啥（论文 / 方法 / 领域 / 现象）？
- **目标会议档次**（定 novelty 严格度）？
- **资源约束**（算力 / 数据）？

**venue 和资源必须拿到具体值才许建文件夹进 Step 2**。用户说"未定 / 不知道" → 当场聊定一个工作假设（如"先按 CVPR 级 + 8 卡 A100 设计"），不许写"未知"放行——没有约束的方向和路线会被设计成空中楼阁：体量奔着 10³–10⁴ GPU-hour 去，到讨论②才发现算力对不上（真实踩过的坑）。

**② 确认可用资源与专长（本步核心之一）**：问用户"你有哪些可用的资源或擅长的方法"——

- **算力**：什么量级、能训多大的东西（别人要做同样的实验得多少成本）；
- **熟练掌握的工具**：你深度掌握、别人要用得现学的方法 / 框架 / 理论机器（如"SIGReg 原理化反塌缩"这种独家工具）；
- **独特见解**：你刚读的论文里别人没注意的观察、你亲身经历过的失败；
- **独家数据 / 资源**：别人拿不到的。

资源与专长落进 `idea-seed.json` 的 `wedge` 字段——它是 Step 2 每个 pitch 的"可利用的资源与专长"字段的**唯一来源**。聊不出资源与专长不代表没有，主会话要拿种子源提示（"你刚精读过 X，里面的 Y 你比大多数人熟，这是可以利用的专长"）。

**③ 检查已有的研究线索**（先扫再问，三个源都只是素材）：

- **paper-card**（仅起点是某篇论文时）：先扫 `docs/paper-reading/`（写死的产出目录）下有没有这篇的 `paper-card.json`——扫到就读 `swappable_components`（替换点）+ `connections`（连接点，带 `direction` 内向/外向 + `kind`；可按 kind 挑：内向「方法上」= 直接改进点候选，外向「搬思想」= 迁移类候选）；**同目录有 `connections.md` 一起读**（人读的五件套迷你 pitch，比 card 字段信息全）；`worth_reading:false` 的卡是避坑信号。扫不到再问用户「这篇你之前用 paper-reading 深度阅读过吗？存在别的目录吗？」
- **LS 报告**：先扫 `docs/literature-survey/`（写死的产出目录）有没有相关领域的报告——扫到 → 拿给用户确认（"找到了 X 的调研报告，用它做背景？"）→ 读 `survey.json` 的 `taxonomy`（领域地图）+ `papers`（论文池）+ `gaps`（gap 线索）。注意：**LS 是入门向的全景调研，只当背景地图**（词汇 / 分组 / 经典文献），**不当新鲜度来源**；它的 gaps 只是对话素材和查询锚点。
- **DT 累积库**：先扫 `docs/direction-tracking/track-*/library.md` 有没有相关方向的累积库——扫到 → 消费**持续出现的主题**（哪些子问题反复冒头）和**反复出现的 limitation** 当素材；扫不到跳过。

**④ 通过对话明确问题**（本步核心，几轮）：用户的 idea 常是模糊的——"我觉得 XX 可能能做点东西"。主会话拿扫到的种子当素材，跟用户聊几轮把它磨清晰：

- 你想解决的**问题**是什么（一句话）？
- 你觉得现有方法**哪里不够**（直觉就行，不用引证）？
- 脑子里的**雏形**是什么（哪怕很糙——换个组件？搬到别的任务？解释某个现象）？
- 种子清单里哪几条你**有感觉**、哪几条没感觉？

用户完全没有具体 idea、纯找 gap 时，对话目标降为**锚定一个子问题域**（"这几条线里你对哪条有感觉、想往哪挖"）——总之 Step 2 产 pitch 之前必须有一个清晰锚点，不对整个领域撒网。

对话收敛后落 `idea-seed.json` 雏形卡（schema 见 `templates/direction-seed-card.md`）：问题一句话 / 用户的直觉动机 / **资源与专长 wedge** / 雏形（糙也行）/ 种子清单（带来源和 kind）/ 还模糊的点 / 会议 / 资源。

**⑤ 根据对话判断从哪一步开始（三种情况）**——通过对话明确问题收敛后，先判断是否需要 Step 2：

- **已有成型构想（fast）**：用户的 idea 已成型——能说出"用什么机制、解决什么、与哪个 baseline 比较"这个完整度（哪怕糙）→ **跳过 Step 2 候选构想清单**，idea 直接落 `pitches/pitch-1-<slug>.md`（来源: 用户），进 Step 3 调研。注意 Step 3 在处理成型构想时的作用是**查找能否定构想的证据**（与已有工作重合 / 方法可能行不通 / 已有工作充分解决才放弃该构想），不是重新发散——**禁句："把你的 idea 拆成几个方向"**。边界情况（有 idea 但很糙）默认已有成型构想：细节留到后面细化并独立检查。
- **仅有大致方向（divergent）**：只有模糊方向 / 锚定的子问题域 → 走 Step 2（先征集用户的想法 + 主会话补充的构想，见下）。
- **建议先明确问题或准备资源**：没锚点又没资源与专长，照旧（见下）。

将入口类型记入 `idea-seed.json` 的 `entry_track` 字段 + `spec.json` 起点段。已有成型构想被 Step 3 的证据否定（与已有工作重合 / 充分解决）→ 回 Step 2 征集并筛选候选——用户服气，因为是有证据支持放弃，不是流程稀释的。

> **建议先明确问题或准备资源（没锚点又没资源与专长）**：用户既说不清想做什么（纯找 gap），又聊不出任何资源与专长 → **不硬产方向**。直说："现在硬找就是替文献找空白，产不出你的 paper。建议先做 X（paper-reading 精读攒 connections / literature-survey 画地图养感觉），积累相关知识和资源后再继续。"用户坚持继续 → 可以走，但必须明示质量风险、记进 spec.json。**宁可建议先做准备，也不产垃圾方向**——硬产的方向走完全流程也是垃圾，还烧掉调研和讨论的成本（真实踩过的坑）。

> **边查边讲**：扫种子时顺手白话讲"你之前读的那篇留了这几个替换点和连接点""LS 报告里这个领域长这样"，让对话有共同素材。

## Step 2 先征集用户的想法 + 候选构想清单 + 由用户筛选构想（主会话 → pitches/pitch-N-<slug>.md → spec.json pitch 决策段）

> **用户已有成型构想时跳过本步**：判断从哪一步开始为 fast 时，用户的成型 idea 直接落 `pitches/pitch-1-<slug>.md`（来源: 用户；五行照样写全——写不全的字段当场跟用户聊清），直接进 Step 3 查找能否定构想的证据。

**先收集用户提出的构想，再由主会话补充候选，由用户筛选。** 只对用户保留的候选开展 Step 3 的详细调研。

**① 先征集用户的想法（先收用户的跳跃，不调研）**：主会话摆**具体要讨论的问题**——锚点一句话（哪类研究者遇到什么困难）+ 资源与专长一句话（有哪些可用的资源或专长）+ 比较对象与评测任务一句话（现有方法在哪个场景有缺陷）——然后停下来等用户先说："你自己先说说，半句话、一个画面、一个类比都行。"**不要先给备选方案再问用户**："我在想是不是可以 X 或 Y——你觉得呢" = 先用备选方案影响了用户的回答，征集作废（手法细节见 `code-idea-iterate/references/research-dialogue.md` 手法五）。尽量按用户的原话记下、落盘（来源: 用户，**直接列入待调研候选**——用户来源的 pitch 只能由用户本人放弃，agent 否证它们靠 Step 3 调研证据，不靠品味）。用户说"没有，你来"→ 不阻塞，直接进②。

**② 主会话补充候选**（读 `idea-seed.json` 的种子 + 资源与专长 + 清晰锚点，不派子 agent、不调研——是否与已有工作重合是 Step 3 的事）：来源一律标「补丁候选」，角色是**对照材料 + 兜底**（帮用户确认"这些都不是我要的"，或用户没想法时接住），数量补位到池子总量 5-8 个即可。每个 pitch 一页以内、**五行**：

- **痛点**：哪类研究者遇到什么困难（具体到哪类研究者 / 哪个方法的哪个缺陷），一句话。
- **可利用的资源与专长**：我们能利用什么已有资源或专长——必须指出能利用 `idea-seed.json` 里的具体资源与专长（算力 / 熟练掌握的工具 / 独特见解 / 独家数据）。**无法说明所用资源或专长时不提出该构想**——没有可利用的资源与专长的方向是替别人找的方向。
- **比较对象与评测任务**：和哪个 baseline 比较、在哪个 benchmark 上比较——有名字的 baseline + 有名字的 benchmark / 指标，一句话。
- **主表预览**：这篇论文的 Table 1 长什么样——哪几行哪几列、达到什么数值算成功，一句话。
- **组合新增了什么能力**：组合能做到什么单一方法做不到的事——答不出 = 单纯拼接，不许产。

**形态偏置（硬纪律）**：默认只产"现有方法有明确缺陷，且有适合比较的 baseline"的形态（技术改进型 / 迁移型 / 组合型 / 新任务红利型——见附录形态清单）。**机理化 / 现象驱动型**（解释为什么、刻画边界、证明最优性）**只在用户 Step 1 明确说"这次就想做理解型工作"时才产**——这类形态是 LLM 的天然引力方向（听起来 profound），但最难转成能发的 paper；即使用户点名要，也照样要写出主表预览（它的"主表"可以是理论预测 vs 实测的吻合图，但必须具体到坐标轴和成功判据）。

**③ 由用户筛选构想**（pitch 评审）：把池子摆给用户——**遵守汇报硬格式**：一个 pitch 一张卡（≤5 行），新术语必跟白话，先给压缩全景再让用户逐个过。用户可以：

- **放弃**：这条没感觉 / 不像能发的 / 不是我想做的——放弃并记录理由（用户提出的 pitch 只能由用户本人放弃）；
- **修改**："痛点对了但比较对象与评测任务不对"式调整——主会话当场改；
- **合并**："A 的可利用的资源与专长 + B 的痛点"——合并出新 pitch；
- **补充**：用户临时又想到的 pitch——直接列入待调研候选，编号接着排。

筛选至剩下 **1-2 个保留的候选**。**连续两轮没有保留候选 → 请用户决定下一步**：这起点 / 这领域可能真没戏，讨论换起点还是先积累研究所需的知识和资源，不要勉强继续。

**④ 落盘**：每个 pitch 一份 `layer1-方向/pitches/pitch-N-<slug>.md`（schema 见 `templates/direction-pitch.md`，**来源字段必填**）——**未保留的构想也留着**，在文件末尾记录未保留的原因（复盘和重新提出候选的素材）；`spec.json` 记 pitch 决策段（含用户提出构想的记录：用户抛了几个 / 说没有 / 原话摘要）。

> pitch 是**待验证假设**——"还能不能做"不由主会话拍脑袋，由 Step 3 调研回答。pitch 阶段主会话凭的是种子 + 资源与专长 + 判断力，不是文献覆盖。这也意味着 pitch 里可能有与已有工作重合的——正常，Step 3 会查；也可能有"其实能做但主会话没想到"的漏——可接受，用户补 pitch 的通道一直开着。

## Step 3 围绕候选构想查阅最新文献（2-3 个通道子 agent → survey-channels/*.json → 主会话合并 literature.json）

**只调研保留的 pitch**（1-2 个；用户已有成型构想时， 只调研用户的 pitch-1）。任务书从 pitch 推导：核心机制关键词 + 同义变体 + 痛点涉及的 baseline + pitch 里点名的论文。**空白矩阵记录每个候选问题已有的研究及其完成程度**——方向已经在 候选构想清单里，调研只回答"这个 pitch 是不是已经被做了、做到什么程度"，不再负责生方向。**针对成型构想：调研的角色是查找能否定构想的证据**——目标是找"这个 idea 不成立 / 已被做好"的证据，不是找"可以拆成什么别的方向"。

**调研即验证**——不再单设 gap 核验环节，四条铁规直接写进每个通道子 agent 的任务书：

1. **必须检索近 12 个月的工作**：近 12 个月必查——arXiv（带日期范围，`submittedDate` 降序；经 paper-search MCP 时自由文本会被自动转写成 `all:"词" AND ...` 字段式查询，宽词可直接写，但"learning"这类常见词区分度低、特化词越多越精确）+ scholar 按年过滤 + **`hf papers` 日报 / trending**（前瞻性 idea 一旦被人做过，HF 上通常讨论热度很高；命中即优先核与已有工作重合）。**主题定向查新用 `hf papers search` + `published_at` 后筛**——`ls --month` 硬上限 100 篇、无分页，不能回填。**无论有没有 LS 报告都扫**——LS 管入门全景，不管新鲜度。
2. **围着锚点查**：每个用户保留的 pitch 都要给出"现在还能不能做"的结论：没人碰 / 被触及但粗糙 / 被 follow 但做得差 / 已有工作充分解决。
3. **最接近的 3-5 篇读深浅**：不只登记存在——评估**做得好不好**：方法成不成熟、效果强不强、作者自己承认的 limitation 是什么。"没人做"和"没人做好"都是机会，只有 充分解决才据此放弃。
4. **方法可能行不通的证据是独立查询通道**：主动搜负结果、"we tried X but it doesn't work" 式失败自述、被审稿批评的方向——调研查的是"存在什么"，**失败和绕开是另一种检索**，不主动搜看不到（这是最容易翻车的地方，别把方法可能行不通当蓝海）。跨域有无现成解法也在这一通道查（有 = 借鉴机会，强化挖方法阶段，不是砍）。

**通道切分**（派发前请用户确认，说清派几个、各查什么）：

| 通道 | 查什么 | 落盘 |
| --- | --- | --- |
| **fresh** | 查阅近 12 个月的工作 + 记录已发表的相关工作：近 12 个月 arXiv / scholar / HF，每个 pitch 的现状结论 | `survey-channels/fresh.json` |
| **closest** | 最接近的 3-5 篇读深浅（做得好不好）+ 正向引用追踪（谁引用了起点论文/最接近工作，近 1-2 年跟进归类竞争态势） | `survey-channels/closest.json` |
| **negative** | 方法可能行不通的证据（负结果 / 失败自述 / 被批方向）+ 跨域现成解法 / 迁移机会 | `survey-channels/negative.json` |

锚点窄、文献量小时可并为 1-2 个 agent（通道合并，铁规不省）。

**主会话合并**：通道结果回来后，主会话按 arXiv ID 归一化去重，合并成 `literature.json`（schema 见 `templates/direction-literature.md`）——分组 + **空白矩阵**（每格标「做到什么程度」：没人碰 / 粗糙 / 做得差 / solid，每条必须带 arXiv 依据）+ 最接近评估 + 方法可能行不通的证据 + 跨域线索。合并是判断活（去重、分组、定空白格判词），不外包。

> **防偷懒铁律**：通道子 agent 只登记和评估**检索到的真实文献**，不许生成"建议方向"；文献台账里不许出现没有 arXiv 依据的格子。

> **边查边讲（调研回来后，方向成型前）**：主会话先用**白话给用户讲一段"这几个 pitch 现状长啥样"**——哪条还开着、哪些问题已被充分解决、最接近的几篇做到什么程度、有没有方法可能行不通的证据。提到任何论文默认用户没读过，顺带一句它干了啥。这段不落盘、不是讨论环节、不用用户拍板，纯粹是把用户带上车。

> **触发回退的条件（用户保留的 pitch 已被前人充分解决）**：调研发现用户保留的 pitch 已有工作充分解决（不是做得差，是真的做好了）→ 回 Step 2：候选构想清单里重新考虑未选的候选（限因用户缺乏兴趣以外的理由未被选中的构想）/ 补充候选 / 换研究方向——用户拍板。回退前更新文献记录及请用户决定的条件见 SKILL.md「回退条件与处理方式」。

## Step 4 方向成型（主会话，不派子 agent → 写 方向N-<slug>-main.md 骨架）

**这一步是判断，留主会话。** 主会话读 `literature.json`（全局视角：分组 + 空白矩阵 + 最接近评估 + 方法可能行不通的证据）+ 用户保留的 pitch，把保留的候选升级成 **1-2 个方向骨架**。

**方向不是从空白格里重新生成的，是从用户保留的 pitch 升级来的**——调研证据给 pitch 补上"为什么这空白真、为什么现在能做"的论证，但方向的灵魂（痛点 / 可利用的资源与专长 / 比较对象与评测任务）在 pitch 阶段就定了。若调研回来发现需要调整 pitch 的核心设定（比较对象与评测任务换 benchmark、痛点收窄），主会话改并留痕。

每个方向骨架必填（schema 见 `templates/direction-main.md`）：

- **来源逻辑**：从哪个 pitch 来（指回 `pitches/pitch-N-<slug>.md`）+ 调研怎么验证的（空白矩阵哪格、做到什么程度、arXiv 依据）——审计链：**方向 ← pitch ← 痛点 × 资源与专长**，调研只证伪和摸底，不生成。
- **三项必填内容**：
  - **痛点**（哪类研究者遇到什么困难，一句话——正例："X 在 Y 条件下必须重跑全量 Z，代价随 N 线性涨"；反例（不许这么写）："XX 效果不够好"——这种写法无法通过 Step 5 预审）；
  - **可利用的资源与专长**（我们能利用什么已有资源或专长——说明利用 `idea-seed.json` 中哪项资源或专长，一句话）；
  - **主表预览**（这篇论文的 Table 1：什么 benchmark、与哪个具体 baseline 比较、达到什么数值算成功，一句话——**写不出具体主表的方向不许进 Step 5**。这条逼"这方向做出来的论文长什么样"在调研验证后就具体化，而不是等挖方法才发现没有 payoff）。
- **核心问题**（一句话）、**初步直觉**（仅一句，不展开方法）。
- **强依赖论文清单（3-5 篇）**——主会话最懂哪几篇是这个方向的命脉，列进去。Step 8 据此下载 PDF。

> **边界纪律**：方向骨架**只讲问题、不设计方法**。"初步直觉"点到一句即可——一旦展开"用什么模型/怎么搭"就踩进挖方法阶段了。

## Step 5 重要性独立预审（1 个子 agent → 方向N-<slug>-importance.json）

方向骨架有了形态、充实验证之前，先过**重要性预审**——pitch 用户筛选验的是"用户想不想做"，这里验的是"**这空白值不值得填**"。派 1 个子 agent，人设 = **严苛顶会审稿人 / AC**（不是帮腔的同行），对每个方向骨架过 Hamming 五问：

1. **谁会在意这个结果？** 具体到哪类研究者 / 哪个子社区。答不出具体人群 = 没人 care 的边角。
2. **审稿人凭什么 care？** significance 一句话站不站得住（"X 变好了"不够，要说清"为什么 X 重要"）。
3. **三年后还有人做这个问题吗？** 浪潮头还是退潮尾——拿近 1-2 年该问题的论文数趋势作证（paper-search 可查）。
4. **做出来了谁接着做？** 能开一条线（后续自然长出一串问题）还是一次性工作。
5. **是不是太小或太老？** 太小 = 一个 trick 撑不起一篇；太老 = 十年前被反复做过的问题换个壳。

用真实文献的证据指出影响研究重要性的问题，列出问题清单，不打分、不排序。讨论①由用户决定是否继续。即使已有研究很少，用户也可以据预审证据及早放弃需求不明确的方向，节省后续方法设计的时间。

> **派发前请用户确认**：说清"对 N 个方向骨架做重要性预审，视角是严苛审稿人"，点头再发。
>
> **边查边讲（预审回来后）**：白话讲"这几个方向里，审稿人视角看哪些是真重要、哪些缺少明确需求"，再进 Step 6 充实。
>
> **触发回退的条件（所有方向均未通过）**：所有方向都没过预审 → 回 Step 4 重新成型（候选构想清单里还有保留的候选或未选的候选）；候选构想清单已空 → 回 Step 2。回退前更新文献记录及连续两轮无可行候选时的处理见 SKILL.md「回退条件与处理方式」。

## Step 6 充实方向（每方向 1 个充实子 agent 并行 → 更新方向文件 + 写 -verify.json）

主会话把方向骨架写好后，**对每个方向各派 1 个充实子 agent**（并行、各管一个方向、不冲突）。

> **注意：这一步验的是「方向」可行性，不是 gap（gap 已在 Step 3 调研里验过）**：Step 3 确认了空白真实存在、没人做好、不是方法可能行不通；Step 6 这里验的是**从 pitch 升级的具体方向**——是否与已有工作重合、能不能启动、算力够不够。**gap 真 ≠ 方向可行**：空白没被填，但我们想的具体方向可能别人已经做过（与已有工作重合）。

充实子 agent 做两件事，**都严格停在"问题这一侧"，不设计方法**：

**① 方向可行性验证**——过下面这张过滤器，逐项落进 `方向N-<slug>-verify.json`：

| 检查项 | 要回答什么 | 不通过 = 丢弃 |
| --- | --- | --- |
| **是否与已有工作重合** | 这个**具体方向思路**有没有人已经做了？（gap 可能还在，但我们的解法思路可能与已有工作重合） | 已有工作做了 essentially the same，差异不足以构成新方向 |
| **有效吗** | 这方向的具体思路**真的能解决痛点** 吗（逻辑成立）？ | 逻辑不成立 / 解决不了痛点 |
| **能启动吗** | 有没有任何 baseline / 数据集 / 开源代码可以起步？ | 找不到任何可基于此起步的资源 |
| **资源匹配吗** | 所需算力/数据在用户约束内吗？ | 需远超用户约束的算力/数据 |

每一项**怎么查、查到什么程度**（任务书里写给子 agent 的操作指导）：

- **任务书输入**：子 agent 开工先读四份——本方向 `方向N-<slug>-main.md`、来源 pitch `pitches/pitch-N-<slug>.md`、`layer1-方向/literature.json`、`idea-seed.json`（拿用户资源约束和资源与专长）。工具：paper-search MCP 查文献、GitHub / HuggingFace MCP 找代码。
- **是否与已有工作重合**：两个动作。① 先把 `closest_assessment` 里那 3-5 篇逐条跟本方向思路比对——它们是最可能与本方向重合的工作，Step 3 已摸过底，这步最便宜；② 再把方向的「初步直觉」展开成 2-3 个 query 变体（核心机制 + 任务名的不同组合）补查一轮。**判据**：与已有工作重合 = 同一个问题 + 同一个核心思路；只是问题相同、思路不同不算撞——那种记进「差异化」，不是丢弃理由。
- **有效吗**：写推理链，不写结论——"痛点是 X → 思路是 Y → 因为 Z（机制 / 证据，指回 literature.json 或具体论文）所以 Y 能解 X"。Z 缺证据不许空喊"逻辑成立"——把缺证据的 Z 标出来，直接进「风险信号」。
- **能启动吗**：去 GitHub / HuggingFace 找官方 repo、论文代码、可用数据集。"可起步"的标准放宽：有可改的 repo 或有可训的数据就算，不要求权重齐全。**边界**：只列线索 URL，不核查质量——权重下不下得到、代码接不接得进是 `baseline-survey` 的尽调，这里不越界。
- **资源匹配吗**：对照写死——`closest_assessment` 里论文自报的算力 / 数据规模（几卡几天、多大数据）vs `idea-seed.json` 里的用户约束。论文没报就按同量级工作估，并注明是估的。

> **为什么不查"创新点够不够/能不能发表"**：method 的核心创新点是随 `code-idea-iterate` 用实验证据迭代、写论文时从中期代码库提炼出来的——第一阶段还没实验、没迭代，判"创新点薄不薄"是**过早**的，且和产草稿阶段"实验设计留中期"的定位冲突。但注意：**payoff 的具体性已经在 pitch（主表预览）和方向成型（三项必填内容）阶段保证过了**——这里只回答**"这个方向立不立得住、能不能上手"**。

**② 充实问题侧**——把方向文件的"为什么值得做"做扎实，四个字段各写到这个颗粒度：

- **竞争态势**：几篇跟进、最近一篇什么时候发的、有没有强组在跟——据此给红海 / 蓝海的判断和依据。
- **差异化角度**：和最接近工作的差异是什么 + **差异为什么重要**（解决了什么它们解决不了的事）——不是罗列不同点。
- **可行性信号**：①④查到的代码 / 数据 / 开源线索汇总（URL 清单）。
- **风险信号**：最可能让方向失效的 1-2 个因素——「有效吗」里缺证据的 Z 自动进这里；另外主动想一个：这个方向最可能因什么原因失败。

更新回 `方向N-<slug>-main.md`。

**充实子 agent 不做什么**：不设计方法、不选模型、不搭结构——那是挖方法阶段。它只把"这个方向立得住、能上手"论证扎实。

**返回主会话**：立得住/丢弃 + 一句话依据 + verify 路径。若某方向因与已有工作重合判丢弃，在 verify 里留「已覆盖·可深挖」（原方向核心 / 被哪篇覆盖 URL / 是否适合作新起点）。

## Step 7 展示 + 一起打磨（主会话，讨论①）

充实子 agent 全部返回后，主会话跟用户一起打磨方向。这次讨论的目标是让用户**参与到打磨里**，而不是做选择题——所以**先给压缩概览、再让用户带着按需深入，不一上来灌**，由用户的吸收速度驱动深度。**全程遵守汇报硬格式**（一卡一件事 ≤5 行 / 新术语 ≤5 个且必跟白话 / 每次只确认一个决定）。

**1. 先给调研摘要**：调研范围 / 各 pitch 现状 / 关键发现 / 空白在哪。让用户知道主会话做了什么、发现了什么（若已在 Step 3 末垫过地基，这里做承接，不重复倾倒）。

**2. 再展示立得住的方向**：读方向文件转述要点——**痛点 / 可利用的资源与专长 / 主表预览三件套打头**，附论文 URL。**每提一篇论文默认用户没读过，顺带一句它干了啥、为什么跟这方向有关**；提到专业术语，紧接一句话解释（例："cyclic fixed points"——指模型反复循环后隐藏状态进入固定模式、无法再提炼新信息）。

**3. 让用户决定深入哪个**：给完压缩全景后，明确邀请用户指定深挖点，而不是继续灌。比如这样说：

> "以上是几个通过文献验证的方向。这些方向、调研、查重全都落盘了。想让我深挖哪块，我从盘上的文件给你讲——哪个方向的痛点你觉得最真实？哪篇论文你想让我讲讲它到底做了什么？哪条查重结论你想让我再追证据？还是有别的角度想加进来？我们改哪个我就更新哪份文件。"

- 用户指定要深挖某篇 / 某判断 → 主会话回 `literature.json` 或对应 verify 文件把细节讲清楚。**深挖是廉价的**（数据都在盘上），且是用户按自己节奏在驱动深度，不是 agent 一次灌完。
- 充实子 agent 是自己验证自己的方向，会偏乐观。主会话转述时**带着怀疑逐条追问依据**，别照单全收——尤其"竞争较少是否因为已有工作发现这条路行不通"。
- 用户可以多选方向（"这几个都想做"），记进 `spec.json`——但**挖方法串行**（一次只挖一个，见 method.md 的负载纪律），讨论①同时定下先挖哪个。
- 用户也可以说"把 A 的这块和 B 的那块糅一起"，主会话就据此造一个新的。
- **触发回退的条件（所有方向均未通过）**：所有方向都没通过验证 → 回 Step 4 重新成型（或 Step 2 补 pitch）；请用户决定下一步时建议换更近的、或引用少但方法有趣的论文当起点，别编造凑数。回退前更新文献记录及请用户决定的条件见 SKILL.md「回退条件与处理方式」。
- 若充实时触发「已覆盖·可深挖」，主会话汇总后可建议用户以覆盖论文为新起点重跑找方向阶段。

讨论①拍板后：主会话更新 `spec.json`（方向决策段：chosen 方向 + 用户质疑了哪条、主会话补了什么证据、结论怎么变 + **选题理由快照** + 先挖哪个方向）。

---

## Step 8：下载强依赖 PDF（主会话）

讨论①用户选定方向后（可多选），主会话按**各选定方向 `方向N-<slug>-main.md` 的强依赖论文清单**下载 PDF：

- `download_paper_asset` 指定 `paper_ref`、`asset_type="pdf"` 和已核版本，取返回的 `path` → 存进 `papers/<论文-slug>/<论文-slug>.pdf`（一论文一子目录，文件名用可读 slug）。
- 每篇下载落盘 `papers/<论文>/` 并在方向文件的强依赖清单上标记——这是挖方法阶段只深读本方向论文、不碰别方向的依据。
- **下载求全**：选定的方向，强依赖全下（哪怕十几篇）——下载是廉价 I/O，落盘可审计、换方向不重下。深读的 token 成本留到挖方法阶段只对焦选定方向。

> 未选定的方向**不下载**（省 I/O）；方向文件留着，将来换方向做挖方法时主会话补下那个方向的 PDF 即可。

## 附录：常见方向形态参考（命名校准用，不是菜单）

Step 2 产 pitch 时对照这份清单校准形态。**默认只产前四类**（现有方法有明确缺陷，且有适合比较的 baseline）；后两类只在用户明确说"这次就想做理解型工作"时才产，且照样要过主表预览。**不许拿着清单往文献上套**（菜单硬套是 LS organizing-axis 定过案的反模式）；形态是从痛点 × 资源与专长里长出来的，不是从清单里挑的。

- **技术改进型**（默认）：现有方法有明确缺陷（效果 / 代价 / 假设 / 适用范围），针对该缺陷做改进。
- **新任务红利型**（默认）：近 1-2 年新任务 / 新场景，显而易见的子问题还没人做。
- **迁移型**（默认）：别处验证有效的核心思想 / 现成解法，搬到本任务。
- **组合型**（默认）：两个各自验证过的思想 / 模块融合，解决单独任一个都解决不了的问题。**注意**：组合型的核心假设通常是未验证的假设（"A 的洞察在 B 的场景成立吗"），且往往**不存在直接前驱 repo**——其 v1 天然分析先行（首个验证实验 = 检验假设的分析实验，见 `method.md`），载体选型走 baseline-survey 的选择用于分析实验的代码仓库的流程。这不违反形态偏置（它仍能提出具体的论文主表），只是验证顺序是先验假设再与 baseline 比较。
- **现象驱动型**（仅用户点名）：多篇论文反复出现但没人系统解释的反直觉现象。
- **机理化型**（仅用户点名）：方法确实 work 但没人说清为什么，从"知其然"推进到"知其所以然"。

## 落盘 schema

本阶段七个落盘文件（idea-seed.json、pitches/*.md、survey-channels/*.json、literature.json、方向N-main.md、方向N-importance.json、方向N-verify.json）的字段模板在 **`templates/`**（一产物一文件）——派子 agent 时，只把它要写的那个模板文件连同路径一起放进 prompt。
