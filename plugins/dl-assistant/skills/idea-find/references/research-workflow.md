# Idea Find 运行手册

本文件说明怎样从研究起点取得证据，由主会话提出并筛选假设，与用户判断研究价值，再把下一轮取证设计到可执行。阶段和确认点对应 [SKILL 运行流程图](../SKILL.md#运行流程图)。现有方向、方法和草案参考提供操作细节及文件格式，推进顺序和确认点按本手册执行。

## 开始或续做

先使用已知的任务、现象、用户兴趣、资源和研究目标。有论文、观察或方向就先核查能影响判断的资料。目标会议和资源未知时可继续提出问题，设计实验时再核实影响方案的约束。范围太宽时，从相互冲突的结果、反复出现的局限或一项具体任务开始，向用户解释为什么选它。

**先检查已有文献调研。** 优先使用用户给出的结果路径，也可查看项目的 `docs/literature-survey/`。从相关调研的 `survey.json`、`report.md` 和 `coverage-review.md` 核对主题、实际覆盖截至日期、来源和未完成范围。

- **有相关且适用的结果。** 直接使用其中与问题相关的论文、比较和待验证问题。
- **找不到相关结果。** 请用户告知以前的结果路径，或建议先做一轮 [literature-survey](../../literature-survey/SKILL.md)，尤其是起点只有一个宽泛方向时。
- **结果较旧或主题变化较大。** 按领域发表节奏和本次问题判断旧覆盖是否可能改变结论。说明漏了哪个时段或哪些重要路线。缺口较大时建议新做一轮调研；只是当前问题的一小段缺口时，在 Step 3 定向补查。

用户选择直接开始，或已有足够具体的问题时，可先做定向检索，说明能判断到哪里。由用户决定是否先做正式调研。

| 已有材料 | 从哪里继续 |
| --- | --- |
| 论文、调研、跟踪记录或观察 | 从 Step 1 核查可用证据和研究起点 |
| 已有候选，尚无可靠筛选依据 | 从 Step 2 补缺的推理或文献，重新给推荐 |
| 已有问题和假设，尚未决定是否继续 | 从 Step 3 核对最接近工作、近期证据和研究价值 |
| 用户认可研究问题，已有或缺取证方案 | 从 Step 4 检查关键条件、对照和成本 |
| 草案待确认，或确认后改过文件 | 从 Step 5 对照 [`spec.json` 决策日志](research-records.md#决策日志与续做)的决定和草案版本。变更影响问题或取证设计时回对应步骤 |

续做时打开已有的调研目录，先读 `spec.json` 和最新证据，确认已做的决定、未决问题和续做位置。需要查找文件时参照 [产出约定](research-records.md)。新证据改变判断时记录变化原因。已有本项目实验结果、需要决定下一轮研究时，交给 `code-idea-iterate`。

## 阶段一 · 发现并界定问题

### Step 1 核查起点，实际检索

1. **写下这次初查要解决的问题。** 从任务、对象、观察到的差异及测量条件出发，找出哪项信息最影响下一步。已有构想时，优先查支撑它的现象是否成立、最接近的工作是否已回答同一个问题。只有宽泛方向时，从代表方法、相互冲突的结果或反复出现的失效场景切入。例如，裁剪后 FLOPs 下降但延迟未降，先核论文测的是整次推理还是单个算子，以及设备、批大小和运行时是否一致。
2. **对照已有资料。** `paper-card.json` 可提供已读来源、论点证据、组件和连接线索。结合 `reading_goal`、`worth_reason` 理解 `worth_reading`。阅读建议缺少上下文时，以任务相关的证据为依据。`survey.json` 中的 `taxonomy`、`papers`、`gaps` 可提供词汇、代表工作和待验证问题。核对覆盖截至日期和证据层次后，按缺口补查。
3. **调用检索工具。** 按 [paper-search](../../paper-search/SKILL.md) 调用 `get_capabilities`，随后用 `search_papers` 查现象及最接近机制。已知稳定标识时用 `get_papers`，只有标题时用 `resolve_papers` 核候选。确认种子身份后按需用 `get_paper_citations`、`get_paper_references` 或 `find_related_papers` 扩展。可复用覆盖本次问题的检索记录。用户限定资料范围时按约定执行，并说明范围对结论的影响。
4. **定位会改变判断的原文。** arXiv 优先用 [tex-mcp](../../tex-mcp/SKILL.md) 打开固定版本后读相关章节及引用的公式、表格。只有 PDF 或需要核对原页时，用 [pdf-mcp](../../pdf-mcp/SKILL.md) 读取对应位置。记录论文标识、版本、位置、核查深度和实际条件。只读摘要时，相关机制或实验判断保持待核。

主会话可直接执行常规检索。需要委派时，说明数量、任务、输入、输出路径、分工理由，等用户确认。派出的任务可以检索、独立推理或核查解释，接回后由主会话核证据、去重并给推荐。

**何时结束初查。** 当已有材料足以界定一个值得解释的现象、提出可以区分的解释，或指出已有构想的关键前提为什么站不住时，进入 Step 2。向用户交代初查发现及其依据。若最关键的前提仍无法核实，给出最有价值的下一条查询、要读的原文位置或待取得的观察，说明它将改变哪项判断。初查只做到足以确定下一步，系统查新和深入对照留到 Step 3。

**保存。** 按[研究起点模板](templates/research-seed.md)写 `idea-seed.json`，记录初查问题、现象、约束、来源、初步结论及未决项。实际查询按[文献检索记录模板](templates/literature-search-record.md)写入 `literature/search/`，需补核原文时，按[论文证据笔记模板](templates/paper-evidence-note.md)将位置和条件记在 `literature/papers/` 对应的笔记里。来源失败时按需换可用来源，仍缺证据时注明现有结论的限度。

### Step 2 主会话提出假设并筛选

按[问题发现指引](question-discovery.md#2-主动提出比较并筛选候选)为值得讨论的想法写下**候选研究问题与假设**。早期有缺项时，记录缺什么和怎样补，先查最可能改变推荐的那一项。

| 要检查什么 | 具体做法 |
| --- | --- |
| 问题 | 一句话写对象、适用条件、具体未知及回答它的用途 |
| 假设和预测 | 写可能的机制或解法，并推导若成立会观察到什么 |
| 推理 | 分开记录已读证据、关键前提和由此作出的推断。补查最弱的一段推理 |
| 研究价值 | **即使做成功，结果会回答什么科学问题，论文能据此提出什么新结论？** 说明谁会因此改变判断或下一步行动 |
| 替代解释与反证 | 写最强的替代解释、它的预测及可能推翻当前解释的证据 |

用户构想与 agent 构想用同一尺度。只凭词语或方法联想得到的候选，先补机制和差异预测。查无先例时，检查推理与取证途径，并保留实际检索边界。主会话完成筛选后，给出状态和一段能追问、能复查的理由。

| 判断 | 理由要写到什么程度 |
| --- | --- |
| 推荐 | 写出决定性观察及出处、由观察到假设的推理、最强的替代解释，以及即使成功也仍需验证的边界。明确回答哪个科学问题，能为论文增加哪项结论 |
| 待补证 | 指明卡住判断的未知、下一篇要读的具体位置或待取得的观测。说明证据支持、反驳或仍无法区分时，推荐将怎样变化 |
| 放弃 | 给出推翻假设的证据和适用条件，或最接近工作在哪些条件下已经回答了同一问题。如果还有残余问题，交代它是否值得追及理由 |

主推候选要把证据、推理和研究新增讲完整。结论应具体到解释哪种现象、验证什么机制或界定哪项适用条件。若实验成功只会得到一个更好的数值，进一步说明这项差异回答了什么有意义的问题，再决定是否推进。明显重复或已有直接反证的候选可简写，同时保留对应证据。

**首次向用户讲解候选。** 从一个具体的观察或对照入手，用下面的顺序讲主推项。仅在备选会改变研究问题、可得证据或重要约束时，解释两者的实际差别。主会话完成比较，给出暂时的推荐和下一项核查。

> 实际观察到了什么 → 为什么这个结果值得解释 → 现有工作已经回答到哪里 → 我们还想弄清什么 → 如果做成，会新增什么认识 → 主会话推荐什么、为什么

按用户已经展示的熟悉程度调整讲解。程度未知或不熟悉时，先用具体设置、读数或对照说明问题，再解释会影响判断的术语。讲完给用户一轮追问或选择用自己的话复述的机会，可以邀请他指出哪一步需要展开。熟悉时可简述关键对照、可能新增和主要未知，并接着说明建议的补查。首次展示可澄清会改变查证的兴趣和约束。研究取向在 Step 3 讨论，实验规模和投入在 Step 5 确认。见[两种讲解示例](question-discovery.md#首次讲解候选的两种示例)。

**保存。** 按[候选研究问题与假设模板](templates/research-candidate.md)写入 `candidates/candidate-<编号>-<slug>.md`，在 `spec.json` 写当前推荐与下一次要核的证据。没有合理推进项时，保存原因并和用户讨论暂停或换问题。

## 阶段二 · 判断研究价值

### Step 3 深入查新、对照最接近的工作并讨论是否继续

先从已有调研选取与当前问题相关的 `papers`、`comparisons` 和 `gaps`，按稳定论文标识及上游文件中的条目编号引用。核对 `coverage-review.md` 的实际覆盖，必要时打开对应笔记或原文。本轮只补会影响判断的缺口，例如候选收窄后需要专门的对照、未覆盖的时间段、最接近工作或反面证据。暂无调研时，从当前问题直接定向检索。查询可以合并，重点是留下每种判断的依据和覆盖限制。

| 核查方向 | 执行方法 | 要回答的问题 |
| --- | --- | --- |
| 近期工作 | 从已有结果的实际覆盖截至日期判断需补的时间段。没有可复用的近期记录时，可从近 12 个月起步，按领域选择窗口及支持相应日期口径的来源。需要 HF 补充时按 [HF 查新说明](../../literature-survey/references/hf-papers.md) 执行 | 截至哪天查了哪些来源，近期工作是否改变原判断 |
| 最接近工作 | 查相关论文的正反向引用与同义方法。回查最接近论文的机制、数据、对照、任务、设置与局限 | 对方回答了什么、验证到哪些条件、剩余差异能否改变结论 |
| 反面证据与替代解释 | 用失败条件、敏感性、边界、冲突结果或跨领域等价机制补查 | 哪些证据削弱当前假设，是否有更简单的解释或已知解法 |

本轮追加查询保存实际参数、来源、日期口径、截至日期及查询快照或结果引用。检查 `source_reports`、`coverage` 和预算。需要读完本地快照时用 `get_query_results`，需要上游补查时按 MCP 当前接口用 `extend_query` 或新请求。区分成功无命中、失败、部分结果和未执行。合并文献时优先核对稳定 arXiv ID、DOI 或论文页面，保留观察来源和版本冲突。详细结果按[文献检索记录模板](templates/literature-search-record.md)写入 `literature/search/`。

**按需独立核查。** 当已有工作是否覆盖当前命题、反证是否适用或关键证据能否取得会改变推荐时，可用[候选问题独立核查模板](templates/candidate-verification.md)，将原件保存到 `candidates/reviews/`。主会话在候选记录引用发现编号，并说明处理方式。

**保存。** 按[研究问题证据模板](templates/question-evidence.md)更新 `literature/literature.json`。保留上游引用、与当前命题有关的原文证据、需要定向补查的问题和它们对判断的影响。研究问题的调整、候选推荐与用户决定分别记入相应候选记录和 `spec.json`。

**分别判断证据、创新性和价值。** 对最接近的工作逐项写「已做什么、证据到哪里、当前命题仍会新增什么」。只改变设备、数据或设定时，说清新条件为什么重要，能否产生可区分的解释或决策。如果现有工作已经回答了问题，或收窄后只剩意义有限的差异，回 Step 2 重新评价。覆盖不足又可能改变创新性判断时，先补查或明确保留未知。

**讲清查新怎样改变判断，再请用户确认。** 接着第一次讲过的现象和问题，说明哪条新证据影响判断、原推荐是否调整。如果问题变了，先用一句话重述修订后的问题。以查新后保留的问题为准，重新回答。**即使做成功，结果会回答什么科学问题，论文能据此提出什么新结论？** 讲清最接近工作的条件、最强的反对理由，以及什么新证据会改变推荐。指出哪些判断已核正文、哪些还待补证。用户仍在追问或表示没跟上时，先解释卡住的地方。用户已有足够上下文时，给出建议，并明确询问是否继续研究这个具体问题，也可讨论改题、补证或暂停。

按上一轮提出的行动解释「好」或「继续」。如果当时在讲解或商定补查，按该范围推进，研究取向仍待确认。如果当时已明确询问是否继续研究这个问题，可按上下文记为对该问题的认可。认可后进入取证设计，并将决定、依据及剩余未知写入 `spec.json`。实验投入在 Step 5 确认。

## 阶段三 · 设计下一轮取证并交接

### Step 4 选择证据、写出对照并检查设计

按以下顺序向用户讲解本轮设计，再展示实验表。

> 要分清什么 → 为什么这个设计能分清 → 每个对照有什么作用 → 看见不同结果会怎样判断

先用具体例子讲清本轮要减少的未知，以及它和当前科学问题的关系。解释如果只跑最直观的一组实验，哪些解释会混在一起。讲到对照时，说清每组改哪项、保持哪些条件、排除什么解释。若设计只能回答更窄的问题，把能回答和仍待回答的部分讲明白。对会影响解释的条件和投入，说明保留条件的依据与代价。

1. **先写本轮要减少的未知。** 明确要区分的解释或要验证的预测。按问题选择原始观测、分析、理论检查、小规模干预或完整训练，并说明理由。将能在同一条件下区分解释的方案放在优先位置。
2. **写目标条件和缩减依据。** 列出目标任务、数据、模型、硬件、预算和评测协议，标明假设依赖哪几项。缩减前解释哪些条件保持、哪些改变、依据是什么，以及结果能否迁移到目标条件。低成本方案若会移除关键机制，调整条件、评估资源或回到问题判断。
3. **写下对照和结果解释。** 明确基线、各组只切换或共同改变什么，如何控制替代解释、收集哪些测量。写出支持、削弱、结果不确定时各采取什么行动。定量阈值来自已有基线、测量误差或用户验收约束；尚无这些依据时，先定义如何取得基线或噪声观测。
4. **查运行与归因风险。** 用 [方法与取证设计](evidence-design.md) 的核查材料检查对照、代码载体、数据和评测。需要独立检查时，按风险分配检查视角。主会话逐条处理会改变解释的缺陷，必要时缩小结论或修改设计。问题发生变化时回 Step 3 重新判断价值。
5. **保存交接前自查。** 在取证设计记录中复核 Step 2 的五项，再写设计能否回答问题、各结果的解释边界、成本依据及待批准投入。每项有实际依据、未知及对下一步的影响。不能区分解释时先修设计，资料或资源有待确认时写清具体事项。

**把结果的解释讲给用户。** 实验前说明哪些可能结果会支持或削弱各解释、哪些结果只足以说明总体效果、什么情况需要重做或补对照。把这一对应关系写进 plan。实际实验完成后，`code-idea-execution` 负责记录跑了什么、观察到什么以及有哪些偏差，`code-idea-iterate` 根据这些证据向用户解释原判断怎样变化、还有什么未知、下一轮值得查什么。

**对照预期的科学结论。** 检查实验顺利完成且得到预期读数时，现有对照是否足以回答 Step 3 的科学问题。分别标明能确认实现可用、能支持具体命题和有望带来新认识的观测。只测出组合更快时，科学结论仍要受测量条件和未排除的机制限制。可信的反例也可能界定已有结论的适用范围。将这些区别写进研究说明和本轮取证方案，供下游用实际数据重新判断。

**保存。** 按[取证设计记录模板](templates/design-record.md)将本轮设计和修订理由写入 `evidence-design/design.md`，按[独立核查模板](templates/design-review.md)将核查原件保存到 `evidence-design/reviews/`。需要并列比较多个方案时在 `evidence-design/` 分开保存，并注明各自要验证的问题和假设编号。若眼下只需补文献或取得观测材料，在 `spec.json` 记录具体任务、完成条件与续做位置。

### Step 5 提交草案，确认投入和交接版本

需执行实验时，按 [研究说明、取证方案与 claim 草案](research-handoff.md) 准备三份交接材料。研究说明（spec）写问题、假设、最接近工作差异及当前可能的主张。本轮取证方案（plan）写可执行的设置、对照、测量、成本、结果解释与必要的预先检查。claim 树的子论点对应本轮实际可检验的预测。初始 `evidence_assessment` 为 `pending`，`evidence_assessment_source` 与项目实验证据留空，`is_innovation` 为 `false`，表示贡献尚未确认。

**向用户汇报并确认。** 先用易读的说明总结五项内容。

- **当前研究问题与预期新增。** 这轮成功后能回答什么科学问题，与最接近工作的结果差别在哪里。
- **首轮实验与关键对照。** 先验证哪条预测，每个关键对照解决什么归因问题。
- **结果解释。** 哪些结果支持或削弱假设，哪些结果无法归因。指出结果将怎样影响下一轮。
- **投入与未决项。** 预计使用的资源、估算依据和仍待核实的成本或条件。
- **请用户确认的事项。** 附两份当前草案的路径，请用户确认研究问题、实验设计和投入范围。可以在一次回复中确认 spec 和 plan。

初始 claim 树与本轮实际能验证的预测逐条对应。将获准版本、取证范围和资源写入 `spec.json`。如果用户目前只同意研究方向，或下一步只是补文献或观测，在决策记录里写清依据、未获准的投入以及下一步何时继续。后续改动若影响研究问题、验证条件或投入，按影响返回检查并确认变更。

需要选型时，把任务、数据、模型、仓库线索和载体用途交 `baseline-survey`，前置准备完成后由 `code-idea-execution` 接手。达到现有预算或定向补查已难以改变判断时，保存已知、未知和继续的条件。

## 完整示例 · 边缘设备上的视觉模型加速

以下论文、观察及检索结果均为虚构。假定用户要研究批大小为 1 的端到端延迟，初步想法是把模型裁剪和算子融合组合起来。

1. **先复用调研中已核的现象和证据。** 从已有调研的比较和笔记定位 A 表 2 与 B 表 1。A 是设备 A 上的裁剪对照，B 是设备 B 上的批量子图吞吐。读取设置后发现它们各自提供方向线索，无法回答组合为何在单张场景下起效。
2. **主会话提出并筛选解释。** 一个解释是融合减少中间张量写回，组合效果随访存压力变化。另一解释是裁剪改变了算子形状，导致运行时为不同形状选择不同实现。前者预测跟踪中会看到中间传输减少且效果集中在访存压力高的配置；后者预测延迟随算子实现切换出现变化，即使传输量相近。推荐追查「不同访存压力下组合效果是否可预测」。单纯组合两个组件只作为待核的初步方向。
3. **用最接近的证据重评价值。** 上游调研已核到 C v1 §4.3 表 3 在设备 C 上验证了组合部署。直接引用这条证据，撤回「首次把二者结合」的预期新增。C 的对照同时切换两项改动，附录 B 只给设备信息，分项材料未取得。本轮专门补查访存归因、算子实现切换和分项对照。假设本次查询没有找到能区分机制的证据，而回答这个问题会影响是否启用两项改动，主会话带着实际检索范围给出继续建议。若补充材料已回答同一问题，应更新价值判断。用户在这里决定是否继续研究这个机制。
4. **设计能区分解释的取证。** 先在同一目标设备、运行时和批大小下对比原版、仅裁剪、仅融合、组合，记录端到端延迟、精度和执行轨迹。用重复基准估计测量波动，检查结果是否随写回量变化或与算子实现切换一致。如果两个因素始终一起变化，先保留归因未知，再考虑固定实现或设计能改变访存而保持实现的对照。低成本先选少量代表输入，保留设备和算子形状；是否扩大规模取决于目标条件能否复现。
5. **确认投入并保存。** spec 写清预期新增是解释并预测组合收益的条件，plan 写四组对照、诊断和结果解释，初始 claim 记录待验预测。未取得稳定轨迹或用户尚未同意投入时，在 `spec.json` 写待确认条件及继续路径。获准后交接对应版本，结果及偏差由执行环节保存，后续依据实际证据修订假设。

### Step 4 向用户讲解实验

> 我们要分清的是，组合配置的延迟变化主要与减少张量写回有关，还是由裁剪后的算子形状触发了运行时实现切换。原版给出参考，只有裁剪和只有融合两组分别说明单独开启一项时发生了什么，组合组测两项一起开启的效果。四组保持同一设备、运行时版本和批大小。延迟和执行轨迹一起记，这样可以先看写回量和算子实现分别怎么变。
>
> 若保持算子实现不变时，写回量下降伴随稳定的延迟改善，访存解释得到支持。若写回量相近而延迟差异主要出现在实现切换时，优先追查实现选择。若两者总是一起变化，这轮只能确认组合效果，下一步需增加能隔离两种机制的对照。

### Step 5 向用户汇报交接决定

> C 已验证过组合部署。我们要回答的是，什么条件下能预测组合收益，以及访存和运行时实现各自能解释多少。首轮方案先在一台目标设备上跑四组对照，确认能稳定取得延迟和执行轨迹。先用重复基准估算耗时和测量波动。实测成本还未知，取得基准后再确定正式测量的投入；如果拿不到能区分两种机制的轨迹，先停在测量可行性的判断。
>
