# 论文论证分析与讲解（Step 3–6，供 agent 使用）

先找出支撑论文结论的关键部分，梳理各部分的推理关系，再确定重点贡献。对每部分检查主张、证据强度和与下一部分的推理关系。

本手册供 agent 分析和组织内容。对话中直接向用户讲解论文，给出简明讲解和深读路线图，按具体问题分段。详见 `teaching.md`。

SKILL.md 介绍流程，本手册说明如何分析、讲解、核查证据和填写卡片。

---

## 一、Step 3 开始时分析论证

### 1. 识别关键论证部分

关键论证部分由它在推理中的作用决定。引言或附录这样的章节名本身不构成判据。判断标准如下。

> 设想省略这部分。若关键结论将失去依据，就单独分析。若推理仍成立，例如只省略了补充实验或顺带提及的失败情况，则在路线图里简要提及。

标志句式只是**辅助线索**（"We propose" → 方法类、"We find / show that" → 发现类、"We prove" → 定理类），可分离性不好判时参考，不作为依据。

常见论证类型包括方法设计、研究发现、定理、实证规律和评测基准。系统设计、数据集或理论框架等其他类型也可以单独分析，并使用第二节的通用步骤。

### 2. 梳理论证顺序

按推理关系排列各部分，确认哪些观察支持哪些判断、哪些判断导出设计，以及设计由什么证据支持。用这个顺序组织 Step 3 的路线图。给用户展示时，先列 ⓪ 背景，其余部分用它们实际回答的问题命名。

串不起来（两块之间没有依赖）往往意味着论文本身两张皮——这本身就是重要发现，记 `limitations`。

### 3. 确定重点贡献

找出对论文价值影响最大的贡献，有时可以有两项。重点讲解这些内容，其他部分讲到足以理解整体论证，并明确说明略过了哪些细节。

把各类论证、重点贡献和证据形式以自由文本记入卡片的 `paper_type`，用于确定讲解详略。向用户展示简明讲解和深读路线图。判断不清时，询问用户最关心的部分。

## 二、通用讲解与检查步骤（每个论证部分都要过的基本步骤）

所有论证部分都用以下五步。各类型的讲解重点见第三节。

1. **说明主张**。用一句话说明这部分提出了什么主张、用的是哪类证据。
2. **讲逻辑链**，不复述原文。形式随块换：方法 = 发现 X → insight → 机制 → 为什么有效；发现 = 问题设立 → probe 设计 → 发现 → 说明什么；定理 = 命题 → 关键假设/构造 → 支点一步 → 意味着什么；验证实验 = 逐实验走「设计 → 数字 → 结论」——先讲清对照设计（和谁比、唯一变量是什么、这个对照回答哪个质疑），再读数字，结论最后从数字里长出来（细则见 `teaching.md` 第六节）。
3. **检查证据的薄弱处**。验证实验检查对比公平性，分析测量检查混杂因素，证明核对假设，实证扫描核对控制变量。把具体疑点记入 `limitations`。
4. **记录可能的延伸**。先记下可行的后续方向。到 Step 6 再据论文具体内容筛选，提出 0–3 条，每条附已核实的 arXiv ID。
5. **验收**：用理解检查题，不问"懂了吗"——用户能复述这块的核心 + 指出最强质疑，才算过。

## 三、常见论证类型的讲解重点

各类论证都使用通用步骤，并按证据形式调整讲解重点。

> 各类论证下的「可能用途」供 Step 6 参考。按 SKILL.md 选择有论文依据的建议，最多提出 3 条。

### 方法设计（证据为验证实验）

重点讲清关键设计选择，以及方法如何使用或改进。

- **讲**：先看架构图，再讲核心逻辑链 + 关键设计选择（为什么不用更直接的方案）、方法依赖的假设强不强。细节优先级：设计动机高，完整实验数字低——数字不混进方法讲解，验证实验部分单独按「设计 → 数字 → 结论」逐实验讲透（见 `teaching.md` 第六节）。
- **讲解和核查的顺序**：先把每个实验讲懂（设计 → 数字 → 结论），再标证据不足——证据强度分层是内部评判，不能当首次讲解的结构（用户还没看懂实验就被告知"这层最弱"，理解就断了）。
- **记录可替换的组件**：给每个组件标「这篇的核心贡献」（记 `core_contribution`）还是「拿来即用的现成件」（记 `swappable_components`：组件名 + 当前朴素做法 + 为什么可替换）。只标记，不展开。
- **查**：只盯公平性——baseline 版本老、数据集选得有利于自己、关键消融没做。消融暴露某组件是瓶颈或可简化 → 和讲的时候的标记对上，强化替换点。
- **可能用途**：内向——用更强的同类方法替换现有组件、简化提速、修作者承认的局限；外向——将关键发现应用到其他任务；作为基线时记录已知问题和代码是否公开。
- **检查题示例**：「为什么不用更直接的方案 XX？」「去掉组件 Z 会怎样？消融验了吗？」
- **card**：重点 `swappable_components` + `key_findings` + `limitations`。

### 研究发现（证据为分析测量）

讲解分析过程时，一并说明证据能支持到什么程度。

- **在讲解发现时检查证据**：问题设立 → probe/测量设计 → 发现 → 证据强度。
- **证据可能存在的问题**：confound 没控制、probe 设计缺陷、over-claim（相关说成因果）、cherry-pick 例子、只在单一模型/语言/数据集上验证。
- **可能用途**：内向——修正它/利用它的方法（发现留出的方法空间，如"FFN 存键值记忆"之于 ROME，有潜力的选题起点）；外向——发现在别的 setting 还成立吗（验证边界本身就是工作）、探查实验设计可用于哪些其他任务（记 `connections`）；作证据引为动机，或检查自己的研究是否受同类问题影响。
- **检查题示例**：「这个发现有没有别的解释（哪个 confound 没排掉）？」「换个模型/语言还成立吗？」
- **card**：重点 `key_findings` + `limitations`；`swappable_components` 允许为空。

路线图示例（发现块论文，用具体问题写的标题）：

> ⓪ **这个问题是怎么来的**（§1）——FFN 到底在存什么，为什么这值得搞清楚。【铺垫】
> ① **怎么测出来的**（§2）——把 key 向量投影回词表的 probe 设计，新颖处在这。【重点讲】
> ② **存的是什么**（§3–4）——浅层句法、深层语义，这是核心发现。【重点讲】
> ③ **这个结论有多稳**（§5）——三个模型上都成立。【快速过】
> ④ **边界在哪**（§6）——只验了英文。【一句带过】

### 定理（证据为证明与数值验证）

重点精确说明数学内容及假设带来的适用限制。可以先用类比建立直觉，然后按论文原有记号解释定理和定义。详见 `teaching.md` 第五节。

- **讲（按序走）**：① setup 单独立一块——记号 + 关键定义，每个定义配 toy 例子算一遍，没立住不进定理；② 精确摆主定理——量词、条件、结论；③ 构造讲设计决策链（先试什么 → 撞什么问题 → 怎么解 → 为什么直接做法不行）；④ 证明只讲支点一步，其余给路线图；⑤ 假设讲成代价（排除了什么、放松了怎样）。
- **查**：数值验证把定理落地（预测拟合度、参数对比倍数）；informal 陈述省掉的条件、只在合成 setting 验证、gap 藏在常数/log 因子、构造与真实网络的差距。
- **可能用途**：内向——放宽一条过强的假设（每放松一条就是一篇新定理）；外向——结论指导设计、当检查自己 setting 的依据。
- **检查题示例**：「放松这个假设，结论怎么退化？」「为什么更直接的做法不行？」
- **card**：`key_findings` 换成"关键定理/引理"；重点 `limitations`（假设强度）。

### 实证规律（证据为大规模实证扫描）

重点说明实证扫描如何设计、归因如何成立，以及规律适用到什么范围。

- **讲解**。先解释控制了什么、改变了哪个变量、为什么有依据把规律归因于该变量。再说明图的横纵轴、趋势、斜率或拐点，并给一个具体数值例子。
- **查**：控制变量干不干净、有没有混杂因素跟着变、拟合区间外验了吗、只报平均趋势不报方差。
- **可能用途**：外向——规律外推到别的 setting（验证边界）；当约束——自己设计的边界条件（"在这个规模下别指望 X"）；失效边界往往就是方法空间。
- **检查题示例**：「这个趋势外推到 XX 规模还成立吗？凭什么？」「有没有别的变量跟着一起变了？」
- **card**：`key_findings` 记规律 + 适用边界；`limitations` 记外推风险。

### 评测基准（证据为评测结果）

重点说明评测设计是否公平，以及它是否测到了预期要检验的能力缺口。

- **讲**：想暴露什么短板 → 怎么设计才能暴露（任务/指标的关键设计选择）→ 测出来谁强谁弱说明什么。排行榜不是重点，**短板和结果的对应关系**才是。
- **查**：短板真实吗（有没有可能测的是别的能力/artifact）、任务设计偏向某类方法吗、指标真对应短板吗、测试集污染。
- **可能用途**：每个被暴露的短板都是方法块的 idea 种子（记 `connections`）；外向——评测协议 / benchmark 搬去测自己的工作；作动机（引为问题存在的证据）。
- **检查题示例**：「这个结果有没有可能是 XX artifact？」「换你来设计会怎么让这个短板更难躲？」
- **card**：`key_findings` 记暴露的短板；`connections` 记短板 → 方法空间。

### 其他论证类型（系统设计、数据集、理论框架……）

没有对应示例时，使用通用步骤。先说明主张和推理，再按证据类型检查薄弱处，记录可能用途，最后用理解检查题确认。判断不清时询问用户最关心哪部分。

## 四、组合规则（多块论文）

一篇论文往往包含多类论证。每部分按自己的类型讲解和检查，组合时关注以下三项。

- **顺序**：按论证链走（发现→方法、发现→定理→应用……），不按 section 顺序；用易懂的语言写入 Step 3 的路线图（见 `teaching.md` 第二节）。
- **重点贡献**：详细讲解重点贡献。其他部分提供理解整体论证所需的细节，并说明略过了哪些内容。
- **检查各部分的推理关系**。每次从一部分讲到下一部分时，都核对现有证据是否支持这一推论。
    - **发现 → 方法**：哪个发现推出哪个设计？论文是否说明了发现与方法之间的关系？
    - **发现 → 定理**：定理的每条性质真对上了观察到的现象吗，还是只解释了 toy 版本？
    - **定理 → 方法/应用**：定理的假设在应用 setting 里成立吗？
    - **方法 → 实验**：实验有没有回头验证 motivation 部分的预言？

例：分析先行论文（发现+方法）= 讲解发现并检查证据 → 衔接检查"发现→设计对应" → 方法块正常走；解释型理论（发现+定理+方法）= 定理块按序走，衔接查"定理有没有真解释现象""定理假设在方法 setting 成立吗"。

## 五、card 填写指导

- `paper_type`：自由文本，"论证类型与重点贡献"（如「包含发现和方法，重点贡献是方法，证据包括探查测量和验证实验」）。
- **各字段按块填，不适用就留空**——发现块 `swappable_components` 可空；定理块 `key_findings` 可换成"关键引理"。
- `novelty`：按重点贡献的类型记录。方法写构思是否新颖，发现写结果有多出乎预期，定理写结论的新颖性和强度。
- `connections[]` 每条延伸建议单独记录，并附经核实的文献依据。`kind` 沿用原有值，内向为「方法上」「证据上」「边界上」「解释上」，外向为「搬思想」「推结论」「借工具」「当约束」。
