# 论点、代码与测量映射指引

本文件说明怎样从已批准的取证项追到实际代码、配置和测量，核对每个对照真正改变了什么，并把证据能回答的问题和仍未知的前提讲给用户。

在[运行手册 Step 2](workflow.md#step-2-核对方案能否落地)调查时使用，用[映射模板](claim-code-map-template.md)写 `03-claim-code-map.md`。在 [Step 3](workflow.md#step-3-准备实现并审阅开跑条件) 把映射、实际 diff 和检查结果一起交给用户。

## 1. 从任务和实际命令追到读数

1. **先定这条记录回答什么。** 从已批准的研究说明和取证方案取 Q/H、子论点和取证项编号，核与 `claims.json` 的陈述相符。用一句话说明用户要通过此次观察判断什么。准备工作只需关联问题和任务，例如「T0 核轨迹和计时是否可用」。纯数据分析或理论检查沿实际数据、统计代码或推导记录追证据。
2. **从命令追生效配置。** 打开已经核对的运行命令和工作目录。读参数解析、配置合并和命令行覆盖，确认默认值、配置键和组间差异实际由哪一处生效。可以用 `rg -n -F -- "$config_key" "${paths[@]}"` 起步，先把变量设为真实配置键和项目里的搜索路径。命中后读调用上下文。
3. **沿正式路径查实际调用。** 从配置走到分支选择、模型或算子构造、数据处理及接口调用。若运行时会回退或另选实现，用能触发该路径的日志、轨迹或局部运行检查实际选择。记录 `文件:行`、函数名、commit 或 diff。代码尚未实现时标拟接入；静态可达时标已读源码；跑过时引用包含输入及生效条件的 run。
4. **追到原始读数和统计。** 查读数从哪里采集、计时边界、同步、单位、纳入与排除规则，以及从原始记录到汇总结果的代码。写清结果落在哪个文件、哪一列或哪段记录。多个取证项共用入口和测量时，登记一次，再分别引用各自要观察的对照。

## 2. 逐组确认实际改变和保持的条件

| 先问什么 | 怎样核实并写进映射 |
| --- | --- |
| 名义对照和实际对照是否一致 | 对照各组真实命令、配置覆盖及实际日志。配置声明固定算子时，同时核分派代码和实跑所选算子 |
| 哪些条件决定比较是否成立 | 写研究问题要求保持的设备、输入、模型、训练阶段或测量口径。逐项注明已核的证据，以及只能在正式运行检查的条件 |
| 读数能区分哪两种解释 | 写观测如何对应预测，以及还可能由哪些变化产生。比如写回量和算子同时变化时，可比较该条件下的配置收益，C1 所需的固定算子对照仍待补 |
| 缺证据时当前还能做什么 | 写现在能回答的范围和下一项具体检查。关键条件无法落实时，将原设计、实际差异和可行备选提交确认，保留原方案的版本和批准记录 |

继承上一版的实现时，可引用原映射和已核证据，再核本轮实际 commit、配置和调用条件。沿用的共用代码只补本轮相关变化和仍需检查的前提。

## 3. 用映射带用户审阅实际改动

1. **先讲需要区分的解释。** 说明这个对照为什么值得跑，以及哪个变化要单独观察。再打开实际 diff 和对应源码，带用户看配置、对照分支、输入输出及读数如何相连。
2. **给出检查和解释边界。** 说明已跑试验实际核到了哪里，正式运行还需要观察什么。解释得到预期结果、相反结果或条件未满足时各能支持什么。比如局部试跑只确认能触发分派并保存日志，实际条件是否覆盖所有正式输入还待核。
3. **记录用户决定和变更。** 写审阅对应的 commit 或 diff、获准任务、资源与顺序，以及还需满足的条件。实现、配置或测量变化后更新映射和相关证据，复核受影响的比较和开跑范围。
