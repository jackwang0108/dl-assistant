# 单实验报告模板

本文件说明怎样用一份简短的报告讲清单项实验的目的、实际观察、测量质量和解释范围，并让读者能回查原始证据。

保存为 `experiments/<experiment-id>/report.md`。在[运行手册 Step 4](workflow.md#step-4-登记并按阶段执行)开跑前，先填目的与取证计划，实际执行和结果各节标为「待回填」。运行后填真实结果，包括失败、受阻、有效范围和原始证据。用 [meta.json](experiment-meta-template.json) 和[台账](experiment-index-template.json)核身份与状态。

保留运行前写下的比较、判据和获批设计引用。看到结果后新增的分析注明时间、使用的数据和解释限制。重要证据由未参与设计和执行的子 agent 按[核查指引](acceptance-contract.md)检查，报告引用对应批次的独立核查与仍有分歧的地方。

## 可复制模板

```markdown
# {实验 ID} · {实验标题}

- **身份与批准**　{plan 任务、批准决定及设计修订、执行批次、当前状态}

## 本实验要回答什么

{拟核的前提、要区分的解释或拟检验的命题。注明为什么现在做。}

## 计划怎样取证

{各组改变与保持的条件、生效核查、读数与单位、重复与汇总、判据及依据、各结果如何解释、批准范围和停止点。引用冻结的 design.json 或获批设计副本。}

## 实际怎么做

{待回填。实际组别、代码、配置、run ID、进度与相对原设计的偏差。}

## 实测结果

| 比较组或尝试 | 实际读数或进度 | 有效范围、单位和原始证据 |
| --- | --- | --- |
| {组别或 run} | {待回填。失败或缺失时注明位置和已有材料} | {样本数、次数、波动、原始产物或日志} |

## 本实验能说明什么

- **执行**　{完成、失败或受阻到哪里}
- **测量**　{哪些数据有效，哪些条件或对照缺失}
- **命题证据**　{支持到哪里，最强替代解释，什么证据仍缺}
- **后续与出处**　{建议、停止点、实际核查或自查范围，链接元记录和主要产物}
```

## 完整填写示例 · edge-vision 的计时与轨迹准备

以下沿用[实验台账](experiment-index-template.json)和[元记录](experiment-meta-template.json)的虚构 baseline-timing。所列运行产物是该案例中的示范路径。

```markdown
# exp-baseline-timing · 轨迹采集会怎样影响计时

- **身份与批准**　任务及批次 baseline-timing。批准决定 approve-baseline-timing，设计 v1。已完成。

## 本实验要回答什么

Q2 要解释裁剪和融合的组合收益。正式比较同时需要延迟和执行轨迹，所以先检查目标设备能否取得两类记录，以及采集轨迹是否会改变计时。baseline-timing 只获准在一台设备上做准备检查。

## 计划怎样取证

按 approve-baseline-timing 批准，在一台目标设备上用同一原模型、输入、预热和同步边界对照有无轨迹采集。每种条件记三次端到端延迟。若开启后的读数与关闭时的组内波动明显分开，建议正式计时另行采轨迹。核完读数和轨迹可用性就停。见 [获批设计](design.json)。

## 实际怎么做

使用 c91b7e4 的代码、Vision-S r1 EMA 权重，在 approve-baseline-timing 指定的目标设备上执行。两组使用同一原模型、固定输入、单张请求、相同的预热和同步计时边界，只切换轨迹采集。在 attempt-01 记录每组的三次读数和实际执行轨迹。核查确认两组按准备方案的条件执行。

## 实测结果

| 比较对象或尝试 | 实际读数或进度 | 数据范围、单位及来源 |
| --- | --- | --- |
| 关闭轨迹采集 | 12.5、12.6、12.7 | 同一次准备尝试中的三次端到端计时，ms，[逐次读数](runs/attempt-01/metrics.json) |
| 开启轨迹采集 | 15.3、15.4、15.6 | 同一准备尝试的三次端到端计时，ms，[逐次读数](runs/attempt-01/metrics.json) |
| baseline-timing 实际耗时 | 18 | 单次准备任务的实际用时，分钟，[运行记录](runs/attempt-01/meta.json) |

## 本实验能说明什么

- **执行**　两种采集条件都已完成，共取得六次读数和执行轨迹。
- **测量**　所查条件下采集影响计时。正式计时建议关闭采集，另采的轨迹需核实际输入、配置和选中算子。
- **命题证据**　该任务只核测量准备，C1、C2 的隔离对照仍待运行。

- 记录 | [元记录](meta.json)、[baseline-timing 设计](design.json)、[生效配置](configs/baseline-timing.yaml)、[运行命令](scripts/run.sh)、[日志](runs/attempt-01/idea-edge-timing-01.log)、[轨迹](runs/attempt-01/outputs/trace.json)。
- 下一步 | 已到 approve-baseline-timing 的停止点。建议 configuration-comparison 将正式计时和机制轨迹分开采集，结合本次耗时估计正式预算，再交用户确认具体比较组、隔离对照和投入。
```

## 两种容易写错的结果

**执行失败，只取得诊断日志。**「备选轨迹解析器在读取当前格式时提前退出，完整分组统计没有生成。日志定位到解析失败的入口，供排查兼容性。使用原工具取得的 baseline-timing 读数有独立依据。若 configuration-comparison 需要备选解析器，建议先确认轨迹版本再决定是否重试。」

**测量有效，机制证据仍不足。**「假设 configuration-comparison 获批后四组按同一计时协议完成。基线 12.6 ms，组合 10.8 ms，在该设备和输入条件下低 1.8 ms。实际算子和写回量同时变化，可以报告这套配置下的收益。要判断 C1，仍需固定实际算子、只改变写回量的对照。要判断 C2，仍需比较写回量相近而实际算子不同的设置。」

回填时对照实际运行的配置、指标和来源。只在条件或偏差会改变读者的判断时展开。复用已有读数时保留实际出处及适用条件。结果、未完成原因和建议分别写清。
