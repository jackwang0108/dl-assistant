# 单实验报告模板

本文件说明怎样用一份简短的报告讲清单项实验的目的、实际观察、测量质量和解释范围，并让读者能回查原始证据。

保存为 `experiments/<experiment_id>/报告.md`。有结果、失败、受阻或暂停时，随[运行手册 Step 4](workflow.md#step-4-登记并按阶段执行)回填。实验身份、状态和关键读数与 [meta.json](experiment-meta-template.json) 及[台账](experiment-index-template.json)一致。报告写出理解结果所需的条件，完整命令、配置和原始产物可以用链接给出。

## 怎样写结论和边界

| 先说什么 | 写到什么程度 |
| --- | --- |
| 执行到哪里 | 写已完成的操作、仍受阻或未执行的步骤，以及相关尝试。进程退出状态用实际记录 |
| 读数能用到哪里 | 给比较组、主要数值和单位，注明实际样本或重复范围、测量条件和缺项。已有统计量时说明口径及来源 |
| 证据能说明什么 | 写结果怎样影响当前问题或命题，是否仍有能解释同一观察的因素。准备任务可写可测性、实测成本和正式取证还缺的条件 |

说明哪条先前观察、哪项计划或哪个未知促成了本实验。写清实际改变了什么、保持了哪些条件、怎样采集和汇总读数。偏离计划时指出受影响的组、读数或解释。事后发现的现象单列，明确区分实测观察与待检验解释。下一步建议写清拟补的证据和能解决的问题。

## 可复制模板

```markdown
# {实验 ID} · {一句话说清想回答的问题}

> **先看结果**　{已完成、失败或受阻到哪里}。{关键读数、单位和有效范围}。{这些观察说明什么，核心限制是什么}。

## 为什么做

{此前观察或批准设计中的问题，关联取证任务及 Q/H/C 编号。说明是测量准备、探索还是按预先规则检验。}

## 实际怎么做

{实际版本、配置、输入、基准和比较组。说明各组改变什么、保持什么，怎样测量与汇总，以及相对已批准方案的实际偏差。}

## 观察、解释与限制

| 比较对象或尝试 | 实际读数或进度 | 数据范围、单位及来源 |
| --- | --- | --- |
| {组别、run 或检查} | {数值、实际行为、失败位置或缺项} | {单位、分母、有效重复、日志或原始产物} |

{说明与设计预期的关系、支持或削弱哪些解释、仍缺什么。意外观察有内容时写明当时如何发现，解释和替代解释分别说明。}

## 证据与下一步

- 记录 | [元记录](meta.json)、[设计](design.json)、{实际命令、配置、日志、指标与分析入口}
- 下一步 | {建议补查、停在哪个已批准节点、什么需要重新确认，以及拿到证据后可判断哪项问题}
```

## 完整填写示例 · edge-vision 的计时与轨迹准备

以下沿用[实验台账](experiment-index-template.json)和[元记录](experiment-meta-template.json)的虚构 T0。所列运行产物是该案例中的示范路径。

```markdown
# exp-001-baseline-timing · 轨迹采集会怎样影响计时

> **先看结果**　D3 批准的 T0 已完成，用时 18 分钟。关闭轨迹采集时的三次延迟为 12.5、12.6、12.7 ms，开启后为 15.3、15.4、15.6 ms。该设备和计时口径下，轨迹采集会影响延迟读数。正式比较和 C1、C2 的机制判断仍待 T1。

## 为什么做

Q2 要解释裁剪和融合的组合收益。正式比较同时需要延迟和执行轨迹，所以先检查目标设备能否取得两类记录，以及采集轨迹是否会改变计时。T0 只获准在一台设备上做准备检查。

## 实际怎么做

使用 c91b7e4 的代码、Vision-S r1 EMA 权重，在 D3 指定的目标设备上执行。两组使用同一原模型、固定输入、单张请求、相同的预热和同步计时边界，只切换轨迹采集。在 attempt-01 记录每组的三次读数和实际执行轨迹。核查确认两组按准备方案的条件执行。

## 观察、解释与限制

| 比较对象或尝试 | 实际读数或进度 | 数据范围、单位及来源 |
| --- | --- | --- |
| 关闭轨迹采集 | 12.5、12.6、12.7 | 同一次准备尝试中的三次端到端计时，ms，[逐次读数](runs/attempt-01/metrics.json) |
| 开启轨迹采集 | 15.3、15.4、15.6 | 同一准备尝试的三次端到端计时，ms，[逐次读数](runs/attempt-01/metrics.json) |
| T0 实际耗时 | 18 | 单次准备任务的实际用时，分钟，[运行记录](runs/attempt-01/meta.json) |

已取得执行轨迹，两种采集条件的时间读数都有记录。正式计时适合关闭轨迹采集。另行采轨迹时，需要核两次实际输入、配置和选中算子能否对应。当前观察只用于评估测量准备，C1、C2 的隔离对照仍待运行。

## 证据与下一步

- 记录 | [元记录](meta.json)、[T0 设计](design.json)、[生效配置](configs/t0-baseline-timing.yaml)、[运行命令](scripts/run.sh)、[日志](runs/attempt-01/idea-edge-timing-01.log)、[轨迹](runs/attempt-01/outputs/trace.json)。
- 下一步 | 已到 D3 的停止点。建议 T1 将正式计时和机制轨迹分开采集，结合本次耗时估计正式预算，再交用户确认具体比较组、隔离对照和投入。
```

## 两种容易写错的结果

**执行失败，只取得诊断日志。**「备选轨迹解析器在读取当前格式时提前退出，完整分组统计没有生成。日志定位到解析失败的入口，供排查兼容性。使用原工具取得的 T0 读数有独立依据。若 T1 需要备选解析器，建议先确认轨迹版本再决定是否重试。」

**测量有效，机制证据仍不足。**「假设 T1 获批后四组按同一计时协议完成。基线 12.6 ms，组合 10.8 ms，在该设备和输入条件下低 1.8 ms。实际算子和写回量同时变化，可以报告这套配置下的收益。要判断 C1，仍需固定实际算子、只改变写回量的对照。要判断 C2，仍需比较写回量相近而实际算子不同的设置。」

回填时对照实际运行的配置、指标和来源。只在条件或偏差会改变读者的判断时展开。复用已有读数时保留实际出处及适用条件。结果、未完成原因和建议分别写清。
