# 组织轴定轴 操作手册（Step 3 用）

组织轴是信息收集筛选与组织漏斗的第二步——发散转收敛的支点。轴选对，后面分头深挖（Step4）和收拢（Step6）都顺；轴选错，全乱。骨架（多轮对话：agent 荐轴+理由、用户调、收敛后写进 spec.json 深挖方案）在主干，这里是全套机制。

**核心认知**：**轴是从这批文献里长出来的，不是从菜单里挑出来的。** 判据只有一个——"这批论文实际上沿哪个维度分得最干净"，这是经验问题，同一根轴对这个池子清晰、对那个就是糨糊。所以定轴的动作是**读池子、等轴浮现、拿四查检验**，不是认出一根最像的轴然后套上去。附录的常见轴型只是历史调研里长出来过的好轴，用来给浮现的轴**命名和校准**——池子若长出词汇之外的轴，就用那个。

> **语言**：和用户对话一律中文，说「子领域」不说 bucket。

---

## 一、轴从哪来：读池子的信号（浮现路径）

候选池（`pool.json`）只有标题 + 一句话相关性 + 年份 + 引用数（检索子 agent 把 摘要 要点写进了 `search/*.json` 的 `abstract_notes`，没带回主会话）。轴就藏在这些便宜信号里，两步把它读出来：

1. **先用便宜信号找分得最干净的维度**（多数情况够）：
    - **一句话相关性里的"走什么路子"标签**（`approach` 字段）是最强的信号——把标签摊开看它们沿什么聚簇：聚成几个方法家族 → 方法轴在浮现；聚成同一问题的几个侧面 → 子问题轴在浮现；
    - 标题常暴露方法名/任务名，辅助验证聚簇；
    - **年份分布**看有没有代际断点——有明显断点且前后承接，时间线轴在浮现；
    - **引用分布**看奠基作，也看池子的重心在哪个年代。
2. **信号不够再打 摘要 探针**：对**最高引/最代表性的 ~10 篇**读 `search/*.json` 里的 `abstract_notes`（或按需补拉）确认轴，**不是拉全部**。

读出来后，心里先有候选轴 + 子领域划分，再拿定轴四查检验（第三节），然后才进和用户的多轮对话（第二节）。**顺序不能反：先有池子的证据，后有轴**——带着菜单去套池子，套出来的每个子领域都会漏水。

---

## 二、定轴是一场多轮对话（不是单方面定好通知用户）

```
1. agent 从池子信号读出候选轴（第一节），内部过定轴四查，选出推荐轴 + 子领域划分
2. 给用户：推荐轴 + 理由（理由要落到池子证据上："路子标签聚成了 X 几簇"，
   不是"这种池子一般按 X 分"）+ 征求侧重（"有没有想侧重/拆分的？"）
3. 用户给调整 → agent 拿新划分重过定轴四查 → 诚实反馈：
     站得住 → 更新划分，确认冻结
     有问题 → 如实说、不硬从，给替代方案，来回收敛
4. 收敛到站得住的划分 → 写入 spec.json 深挖方案段
5. 信号不够定不下来 → 对最高引 ~10 篇打 摘要 探针，再判
```

**「评轴」是定轴的内功，不是单独步骤。** 定轴四查是 agent 心里挑轴、以及回应用户每次调整时用的判据，不是一道走给用户看的工序。用户只看到"推荐什么轴、为什么、调整后行不行"，不看到"我评测了一下轴"这种噪音。

---

## 三、定轴四查（轴分得好不好，查这 4 点）

前 3 条保"分得干净"，第 4 条保"分得有用"——一个过了前 3 但不服务用途的轴（如给找研究方向却纯按年份切），技术上对、目的上错。

1. **不重叠**：一篇论文能清楚归到**一个**子领域吗？（不是同时像 A 又像 B。重叠严重 = 轴选错。）
2. **均衡**：没哪个子领域吞掉大半、也没 1 篇的孤儿吗？
3. **完备**：合起来覆盖全池子、残留"其他"小吗？
4. **服务用途**（最易忽略、最重要）：按这个分，**用途要看的东西变显眼**了吗?
    - 定位自己的工作 → 让各家差异凸显（好定位差异化）→ 偏按方法
    - 找研究方向 → 让 gap/limitation 在哪凸显（哪个子问题没人碰）→ 偏按子问题
    - 选技术方案 → 让解法 vs 需求的对比成立 → 按 侧面
    - 学习理解（或用户基本陌生）→ 给最顺的学习路径 → 常按时间线

**用户调整时，就拿这 4 条重测他的新划分**——比如用户要把某组单拎出来，重测"均衡"发现只剩 3 篇 → 反馈"会很单薄"，给"并入邻组 / 设小节"两个替代。

**四查是"轴自然浮现"的检验器，因果链要拎清**：前 3 查查不过，第一反应是**轴错了**（这根轴不是池子自然分层的维度），回去重读信号换轴——**不是池子瘸了**（池子有问题该补搜，那是第五节的事，且补搜也救不了一根错轴）。

## 四、反模式（定轴最常见的死法）

- **菜单硬套**：从附录词汇表里挑一根"最像的"轴，不读池子信号就直接分。症状：大量论文"既像 A 又像 B"、硬塞后冒出孤儿——这不是池子乱，是轴根本不是池子自然分层的维度。
- **把轴的错怪到池子头上**：四查露馅后不去换轴，反而怀疑"是不是没搜够"——补搜救不了错轴（第五节：补搜解决的是"某子领域因没搜够而单薄"，不解决"轴选错"）。
- **把词汇表当穷举**：池子长出了词汇之外的轴（比如"按假设强弱"、"按评测对象"），却硬掰回表里的四根——词汇表是参考不是边界。
- **给用户看的理由是模板不是证据**："这种领域一般按方法分"——用户没法判断。理由要落在池子证据上："42 篇里 30 篇的路子标签聚成 3 个方法家族"。

## 五、回踢补搜的反馈边（轴影响检索的正解）

时序上检索（Step2）在定轴（Step3）之前，所以"轴影响检索"是一条**反馈边，不是前向依赖**：

- Step2 撒的是**用途导向但求全**的网，先把料备齐（与轴无关）。
- Step3 定轴后，若某子领域明显单薄（如选了按时间线却发现早期那段没几篇，或某方法家族只有 1-2 篇），**回踢一轮针对性补搜**专门填它，补够再进 Step4。注意前提：**先确认轴本身是站得住的**（四查过），单薄才归因为没搜够；轴站不住时先换轴。
- Step5 覆盖度自检若发现漏了某流派/别名，同样触发定点补搜。
- **Step5 补搜后要重测定轴四查**（修"补搜不重组→乱"的 bug）：补搜拿回的新文献不能直接硬塞进已冻结的子领域——先拿**扩充后的池子重测定轴四查**：
    - 老轴还站得住（新论文干净归位）→ 塞进现有子领域，补深挖新篇，继续 Step6。
    - 老轴裂了（新论文归不进 / 出现孤儿或失衡 / 漏了一整个流派该单列）→ **回 Step3 重新定轴**（主会话重推 + 用户再确认），再重排 Step4 深挖。
    - 触发判据 = 四查里任一条在扩充池子上不满足了。只填厚某子领域（不破坏轴）的不算裂，不用回 Step3。

这样既不用预知轴，又不会让某个子领域因没搜够而瘸腿，也不会因补搜撑破轴而乱。

## 六、粒度与二级轴

- **子领域数 = 3-5**，正好对上深挖子 agent 数。
    - 分出 ~9 个家族 → 归并成 4-5 个超家族。
    - 只分出 2 个 → 信息量不足，换轴或下沉二级轴。
- **二级轴**：主轴按方法、家族内部再按时间，常见好用。**最多两级**，再深就碎了。
- **平铺特例**：对话式速览 → 不分、不进 Step4，主会话直接列代表作 + 阅读顺序。

## 七、按轴写深挖 任务简报（写进 spec.json，Step 4 执行）

收敛后，spec.json 深挖方案段为每个子领域写一条 任务简报。**梳理重心从轴自身的逻辑写**——轴回答"这批论文沿什么分"，梳理重心就回答"沿这个维度，每个子领域该梳理出什么"。下面四个是常见轴型的示例写法（`{}` 填具体内容），池子长出别的轴时照着这个思路自拟，不套表：

| 轴（示例）     | 子领域 =       | 深挖 任务简报 重心                                                       |
| -------------- | -------------- | --------------------------------------------------------------------- |
| 按方法         | 一个方法家族   | "梳理 {X 家族}：核心机制、代表变体、相对其他家族的取舍与适用场景"     |
| 按子问题/侧面 | 问题的一个侧面 | "针对子问题 {Y}：有哪些解法、各自优缺点、适用条件"                    |
| 按时间线       | 一个发展阶段   | "刻画 {2018–2020 阶段}：什么定义了它、解决了什么、为何被下一阶段取代" |
| 按生命周期     | 一环           | "梳理 {任务定义与 benchmark 这一环}：怎么定义、有哪些基准/指标"       |

所有 任务简报 共享同一产出契约（写 `notes/<子领域>.md`【中文】+ 返精简摘要 + 路径，结构见 `templates/notes-template.md`）。**每条 任务简报（写进 spec.json）都要含**：

- 该子领域的论文清单（标题 + arXiv key，从 `pool.json` 里划给它）。
- 服务的用途（让子 agent 知道该把什么写显眼：找研究方向就重点挖每篇的 limitation/future work）。
- 产出契约（写 `notes/` + 精简摘要 + 路径）——见 `templates/notes-template.md`。
- 纪律：`notes/` 里交的是**结构化素材（逐篇笔记 + 写作素材包），不是替主会话写好的报告段落**——Step6 由主会话亲自执笔；但也别把论文嚼成一句话，细节要够主会话做机制层面的归纳。

## 附录：常见轴型参考（不是菜单）

历史调研里长出来过的好轴，供给浮现的轴**命名、校准粒度**用。池子沿哪个维度分得最干净是读出来的（第一节），不是从这张表里选的；池子长出表外的轴，用表外的。

| 轴              | 子领域 =                          | 适配什么池子               | 默认服务的用途       |
| --------------- | --------------------------------- | -------------------------- | -------------------- |
| 按方法/技术家族 | 一个方法家族                      | 多种并存技术路线、名字清晰 | 定位自己的工作、找研究方向 |
| 按子问题/侧面  | 问题的一个侧面                    | 大家在攻同一问题的不同方面 | 选技术方案           |
| 按时间线/阶段   | 一个发展阶段                      | 有明显代际断点、前后承接   | 学习理解             |
| 按任务生命周期  | 定义/benchmark → 方法 → 应用 一环 | 新任务，论文天然分三层     | （新领域调研）       |
| 平铺（不分）    | —                                 | 池子小或对话式速览，只列代表作 | 学习理解 + 对话式速览 |
