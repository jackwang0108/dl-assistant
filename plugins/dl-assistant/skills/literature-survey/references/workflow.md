# 文献调研的运行步骤

本文件说明怎样把用户的问题变成检索与阅读计划、执行并核查文献、交付有依据的报告和阅读清单。 检索接口、记录字段和合并规则见 Step 2；来源与模板参考中的旧规则与 Step 2 不一致时，以 Step 2 和 paper-search v2 的接口说明为准。

## 选择入口

- **正式调研**从 Step 1 开始。先确认检索方案，再确认分类和详细阅读方案。
- **对话式速览**按用户问题选少量有依据的查询，直接回答领域现状、代表作和建议阅读顺序。说明实际检索与阅读范围。用户要求保存时可以只保存简短的 `report.md`。
- **继续已有调研**先核对原报告的日期、范围、原始查询、候选池与未完成事项。已有证据能回答时直接回复；需要追新或补查时，复用已核结果，确定本次要补的日期、来源或问题。已批准的未完成批次可从原步骤继续，扩大范围则先确认。保留原始批次，另存新增结果。先读 `spec.json` 里的确认范围与进度，再按实际文件确定恢复点。

| 已有状态 | 从哪里继续 |
| --- | --- |
| 已确认的查询批次仍未执行、失败或未保存完 | Step 2。补未完成的查询或续页，保留此前记录。 |
| 新检索批次已落盘，但 `pool.json` 缺失，或未包含这些批次及其最新内容 | Step 2。按 `merged_from` 与已保存批次及修订记录核对，必要时重跑合并。 |
| 候选池已更新，但相关分类或详细阅读范围还需确认 | Step 3。展示受影响的部分，请用户确认。 |
| 阅读方案已确认，但笔记只覆盖部分论文或证据 | Step 4。用阅读计划和 `notes/` 对照，只补缺少的内容。 |
| 阅读完成，查漏或定向补查尚未结束 | Step 5。按 `coverage-review.md` 的待补项继续，新增批次后重新合并。 |
| 查漏完成，报告或阅读清单尚未交付 | Step 6 或 Step 7。按实际已完成的文件继续撰写或交付。 |

续做需要新增时间窗、来源或研究问题时，回 Step 1 确认新增范围。

## Step 1：明确范围并确认检索方案

复用已有信息，只问会影响调研的未知项。区分用途（入门学习、寻找方向、定位已有工作、技术选型）与熟悉度。拟定包含与排除范围、日期口径、起点论文、来源与查询组、预算、查漏方式和停止条件。向用户说明「为什么搜这些来源、各查什么、准备何时停」，并给出输出目录。正式调研应同时覆盖领域发展和近期进展。拟定近作时间窗及截至日期，说明选用哪些来源、各自以首次提交、更新还是正式发表为准。用户明确限定历史时段时，在该范围内说明截至上限的进展。按 [来源选择](source-strategy.md) 和 [检索策略](search-strategy.md) 拟定方案，用户确认后按 [方案模板](templates/spec-template.md) 写 `spec.json`。

## Step 2：检索、记录与合并候选论文

1. **实际调用检索工具。** 按 [paper-search v2](../../paper-search/SKILL.md) 先调用 `get_capabilities`，再按已批准方案用 `search_papers` 执行查询。依查询能力与日期语义选择 arXiv、Semantic Scholar、Scholar、OpenAlex 等来源。以一篇论文为起点时先核身份，再按需调用 `get_paper_citations`、`get_paper_references` 或 `find_related_papers`。需要 HF 补查时按 [HF 检索说明](hf-papers.md) 另行执行。
2. **检查快照覆盖。** 查 `source_reports`、`coverage` 和预算。用 `get_query_results` 及真实游标读完所需本地快照；经批准的上游补查用 `extend_query`。分别记录没执行、失败、有效空结果和部分结果。最新命中日期只描述结果。
3. **分批写文件。** 各批使用独立的 `search/<query-group>.json`。按 [检索记录模板](templates/search-template.md) 的现有纳排记录组织，并使用下面的 v2 对接规则。按规模分批执行或委派，每批保存完整结果，汇总时报告查询组、数量、代表性路线及覆盖限制。
4. **合并及复核。** 运行：

   ```bash
   python3 <skill目录>/scripts/merge_pool.py <调研目录>
   ```

   脚本按共享标识关联，单纯标题相同只提示可能重复。检查 `pending`、`identity_conflicts`、`possible_duplicates` 和字段冲突。人工核对后记下理由，修正原检索分类记录并重建 `pool.json`。引用数使用带来源的观测值。报告原始记录数、纳入合并数量、排除及待核查数量，并注明覆盖限制。

### paper-search v2 到 search/*.json 的对接

- 每批写 `query_group`、`requests[]`、`included[]`、`excluded[]`、`pending[]`。每次调用在 `requests[]` 保存实际参数、`query_id`、`snapshot_id`、获取时间、`source_reports`、`coverage`、预算消耗及分页状态。某个命中只在该批的一个纳排数组中出现，身份或范围尚不明确就先放 `pending`。
- MCP 的返回 `items[]` 先转换成检索记录。把 `identifiers` 中的 `arxiv:` 和 `doi:` 标识分别填入 `arxiv`、`doi`。可另存已核的论文页面 `url`。标题、年份和日期用实际返回值；日期精度以返回为准。保留原始条目（例如 `mcp_item`），包括 `paper_ref`、版本、`field_provenance`、`conflicts` 和带来源的 `citation_counts`，并写纳排理由。单条标有来源的引用计数可写入 `citations`、`source`、`observed_at`；有多条时保留原数组供比较。快照和游标只作查询记录，跨任务引用用稳定论文标识。
- 输入条目至少有可用的 `arxiv`、`doi`、`url` 或 `title`。仅有标题的条目可入池，但标题相同不证明是同一论文。`pool.json` 是从批次文件重建的结果。需要追查某条结论时回看对应 `observations` 及原查询批次。

### 对接示例

例如，实际 MCP 查询返回了以下论文标识。这里只摘出用于示范的字段，正式记录保留完整原始条目和请求信息。

```json
{
  "query_group": "种子论文核对",
  "requests": [{
    "params": {"queries": [
      {"text": "id:2112.10752", "syntax": "source_native", "sources": ["arxiv"]},
      {"text": "High-Resolution Image Synthesis with Latent Diffusion Models", "sources": ["semantic_scholar", "openalex"]}
    ]}
  }],
  "included": [{
    "title": "High-Resolution Image Synthesis with Latent Diffusion Models",
    "arxiv": "2112.10752",
    "doi": "10.1109/cvpr52688.2022.01042",
    "reason": "用户指定的种子论文",
    "mcp_item": {
      "paper_ref": "arxiv:2112.10752",
      "identifiers": ["arxiv:2112.10752", "doi:10.1109/cvpr52688.2022.01042"]
    }
  }],
  "excluded": [],
  "pending": []
}
```

将条目写入 `search/seed.json` 后运行上面的合并命令。在 `pool.json` 的 `papers` 找到该论文，从 `observations[].file` 回到原批次，再查 `observations[].record.mcp_item` 和该批的查询覆盖记录。如另一批只有相同 DOI，脚本也可以关联。以下情况须核查：

- `possible_duplicates` 只有同名提示时，核对作者、年份和稳定标识；身份尚未确认时分开保留。
- 输入的 `pending` 表示该批尚未做出纳排判断。合并后的 `pending` 还可能来自不同批次的纳排分歧或身份冲突。回看各条观测和纳排理由，核实后记录更正依据、更新相应批次记录，再重建论文池。证据仍不足时保留待核查状态。

## Step 3：分类并确认详细阅读方案

按 [分类与分析分工](organizing-axis.md) 根据 `pool.json` 提出主分类维度。用代表作验证分类是否能解释论文之间有用的差异，标出交叉和待确认项。标题和摘要可做初分，依赖机制或证据时回查原文。分类数随领域和用途确定，不必均分。给出详细阅读清单、每篇要读的内容、要回答的问题、工作量和未覆盖范围。向用户说明「为什么这样分类、选哪几篇、读哪部分、每篇回答什么」。用户确认后写入 `spec.json`。阅读清单应包含与调研问题相关的代表作及近期工作，标明各篇的核查重点。小方向可直接安排一批阅读。

## Step 4：逐篇核查并比较

按确认的计划读文，引用关键结论前查相关正文、图表、证明或附录。arXiv 用 [tex-mcp](../../tex-mcp/SKILL.md) 打开固定版本、定位和按节读取。只有 PDF 或需核对原排版时用 [pdf-mcp](../../pdf-mcp/SKILL.md) 核对应页面。每个分组或阅读批次按 [详细阅读笔记模板](templates/notes-template.md) 保存 `notes/<批次>.md`，注明论文身份、已读范围、关键证据位置和不确定项。

汇总时区分作者主张、跨篇比较和自己的推断。比较方法、假设、数据、评测、成本及限制；数据集、指标或预算不一致时说明差别。关键比较、争议或数值冲突由主会话回查原文。获取失败的材料记为待核查。

## Step 5：检查覆盖、定向补查与停止

核对批准范围、实际查询记录、候选池与分类。若方案包含独立检查，把范围、纳排规则、查询记录和候选池交给检查者，保留其独立判断；由主会话执行时也按实际记录逐项核查。重点查遗漏的术语或别名、社区、日期段、代表作、失败或截断的来源。单独检查近作时间窗是否实际执行过检索、是否触达约定的截至日期，以及是否有失败或截断。近期覆盖不足时，按批准方案用支持相应日期条件的来源定向补查。区分最新命中日期和实际查询的截至日期。近期没有命中时，报告查询范围与结果。

写 `coverage-review.md`，记录本轮已查的来源和时间窗、遗漏或截断、补查的具体查询与结果、待补范围和停止理由。补查记录写成新批次并重新合并。局部新增按原方案补充阅读；影响主分类或扩大工作量时回到 Step 3，与用户确认后继续。

覆盖记录可用以下短表。失败、截断或未执行的范围单独列出。

| 检查范围 | 实际查询和来源 | 状态与缺口 | 补查结果 | 待补项或停止理由 |
| --- | --- | --- | --- | --- |
| {技术路线、来源或日期窗} | {查询批次、来源和日期口径} | {已执行、空结果、失败、截断或未执行} | {新增了什么，或在哪个范围内未命中} | {下一次从哪里补，或为什么此处可以停止} |

**停止条件。** 已完成批准范围、主要路线有代表性证据、近作窗口已核对，且定向补查没有改变主要判断时，可进入写作。能增加一条未覆盖的路线、改变关键比较，或找到用户关心的近期工作，都算实质新增，应先判断是否需要补读。达到预算仍有缺口时，按已查范围交付，记录具体待补项。再次扩大范围或预算须经用户确认。

## Step 6：撰写报告、结构化记录和阅读清单

- 按 [报告模板](templates/report-template.md) 写 `report.md`。主会话比较各路线、梳理发展和代表作，并给出依据和限制。每个重要比较注明支持材料的版本、位置和阅读深度。证据仅来自摘要时写明。比如可写「作者在摘要中称方法面向低算力场景」；要写「路线 A 比路线 B 更省算力」，先核查双方正文中的模型、数据、成本指标和评测条件。条件不一致时分别报告数值及适用范围。结合时间和引用证据描述发展，先后出现本身不足以证明继承。
- 最终报告设独立的 **近期进展** 章节。列出实际查询的时间窗、截至日期和日期口径，说明核实的新论文做了什么、和原有路线有什么关系、证据已读到哪里。失败、截断或补查仍无命中的范围如实列出，并指向 `coverage-review.md`。这项要求与现有报告模板一并使用。
- 按 [结构化结果模板](templates/survey-template.json) 写 `survey.json`，使分类、论文和开放问题与报告一致。在 `coverage_notes` 记录剩余缺口并指向 `coverage-review.md`。开放问题区分作者表述、跨论文归纳和待验证猜测。
- 按 [阅读清单模板](templates/reading-list-template.md) 写 `reading-list.md`。按用户需求选入门、专题和可后读的论文，为每篇写推荐理由、前置和要带着读的问题。适用时给 Mermaid 阅读依赖图，箭头表示建议阅读顺序。需要导出时用 `mmdc -i reading-list-tree.mmd -o reading-list-tree.png -b white -w 3840 -H 2160`，若不能渲染，保留 Mermaid 源码并说明。

## Step 7：交付并说明还可怎么用

给出主要发现、三份主要产物和覆盖记录的位置，说明纳入数量、实际阅读范围、仍待补查的内容。用户可按清单交给 `paper-reading`，也可用开放问题继续做 `idea-find`。将未完成项保存在原目录供续做。


## 小型调研示例：边缘设备上的视觉模型加速

以下演示方案和记录写法。查询结果与数字为假设情形，只用于说明如何执行。

1. **确认检索方案。** 用途是了解单图推理加速。用支持发表日期的来源找路线代表作，再用 arXiv 按首次提交日期查截至本次调研日的近作；以 `on-device vision inference` 和 `single-image inference latency` 为两个查询入口。先查计划内的来源和时间窗，后续补查优先处理别名、缺失时间段及失败来源，达到用户确认的预算时停止。
2. **确认详细阅读方案。** 结果先按「模型级改动」「运行时与算子优化」初分，混合方法加交叉标签。各选一篇有真实设备测量的代表作，再读一篇相关近作。模型论文读结构与延迟表，回答收益是否来自轻量化；运行时论文读配置和测量口径，回答收益是否依赖特定算子实现。近作核对它是否研究了以往未覆盖的设备或条件。
3. **核对证据。** 假设论文 A 在设备甲上报告批大小 1 的端到端延迟，论文 B 在设备乙上报告批大小 16 的吞吐量。两篇分别记录设备、批大小、指标和原文表格。报告可说明它们验证了不同场景，各自的数字不足以给两条路线做速度排名。
4. **记录近期覆盖和待补项。** 假设 arXiv 的近作查询执行成功，但另一来源的最新日期窗请求失败，且已到预算。覆盖文件记录成功查询的时间窗与命中、失败来源和待重试查询。报告的「近期进展」只总结实际查到的近作，并注明该来源的覆盖仍待补。
