# 检索策略 操作手册（Step 1 query 设计、Step 2 执行检索）

---

## 一、按用途 × 熟悉度的检索侧重

**用途**决定检索query往哪撒重。检索（Step2）在定轴（Step3）之前，所以这一步**用途导向但求全**地把基础信息备齐：

| 用途           | 检索重心                                              | 必做                                              |
| -------------- | ----------------------------------------------------- | ------------------------------------------------- |
| 学习理解       | 奠基作 + 好综述 + 清晰代表作                          | **survey 优先**；务必含奠基作（不限时间）         |
| 找研究方向     | 近年前沿 + 引文链 + 各家明说的 limitation/future work | 多拉近 1-2 年 + 滚雪球；留意论文"未来工作/局限"段 |
| 定位自己的工作 | taxonomy 完整 + SOTA + 各家差异点                     | 广度铺满主流路线，别漏小流派                      |
| 选技术方案     | 围绕具体问题的各类解法 + trade-off + 适用条件         | 按问题的不同 侧面 分别搜解法                      |

**熟悉度做修正**（与用途正交，叠加生效）：

- 用户**基本陌生** → 无论用途，把奠基作和好综述的权重拉高——用户没地基，定轴、报告、阅读清单都缺支点；
- 用户**就在其中做** → 把扫新和"最近发生了什么"的权重拉高——人家要的是更新，不是地基。

---

## 二、query 分组设计（Step 1 在 spec 里写，附设计理由）

一组 query 派一个检索子 agent。3-5 组，覆盖不同角度，组间尽量正交（别都是近义词换皮）。再给用户呈现query设计方案以及写入spec的时候**都要写出"为什么这么设计"**，因为这是给用户看的：

- **核心概念**：领域最常用的叫法
- **方法/技术名**：主流方法的专有名称
- **任务/benchmark 名**：任务定义、常用数据集/榜单名
- **同义词 / 别名叫法**：换一个社区的叫法——最容易被忽略，却是覆盖度的关键（见 Step5 自检）

**用哪个来源搜、各来源什么特征、按用途怎么加权**：见 **`source-strategy.md`**（核心：SS/scholar 语义查全、arxiv 精确扫新、hf-papers 语义召回 + 近期兜底，第一轮并肩）。用 `filters.date_range` 指定日期类型与起止范围，并核对各来源实际支持的条件。

---

## 三、滚雪球 / 引文链迭代

关键词搜只能召回"用词撞上"的论文。引文链能挖出**用词不同但实质相关**的工作，往往更准：

1. 候选池里识别 2-3 篇**核心/高引论文**，核对稳定标识。
2. `get_paper_citations`（谁引了它，看后续发展）+ `get_paper_references`（它引了谁，看思想源头）。
3. 新捞到的核心论文再迭代一轮（最多 2-3 轮，新论文里已知占比高就停）。
4. 引文链尤其服务 **找研究方向**（顺引用链摸技术演化脉络）和 **基本陌生的用户**（references 里常含奠基作）。

> 用 `get_query_results` 浏览当前快照，需请求更多上游结果时用 `extend_query` 并检查覆盖。

---

## 四、survey 优先

一篇好综述顶 20 篇原始论文——它已替你做了一轮分类和脉络梳理：

- 检索时显式找综述：query 带 "survey" / "review" / "a comprehensive"，或 `arxiv` 用 `ti:survey`。
- 找到的综述**自己读**（值得就 tex-mcp 读它的 taxonomy 章节——`tex_open` 打开固定版本 → `tex_outline`/`tex_read`，源码不可用时降级 `download_paper_asset` + pdf-mcp），它的分类法是 Step3 定轴的强先验。
- 但**别只信一篇综述的分类**——综述有作者视角偏向，仍要拿候选池跑定轴四查（见 `organizing-axis.md`）。

---

## 五、时间配比

默认搜索偏向近年高曝光论文，**容易全是近 2 年、漏掉奠基作**。硬要求：

- **任何用途**都要主动补该领域的**奠基性工作**（不限时间）——它们定义了问题、是理解后续的地基。
- 判断奠基作：引用数异常高 + 年份偏早 + 被综述反复引用 + 在引文链 references 端反复出现。
- **学习理解 / 按时间线轴** 对时间配比要求最高：早期/中期/近期都要有代表，不能头重脚轻。
- 在候选池里**标注每篇角色**（奠基 / 里程碑 / 近期前沿），供 Step3 定轴和里程碑判断用。

---

## 六、去重（同一工作多版本）

同一工作常有多个版本，必须合并，否则候选数虚高、对比表重复：

- **arXiv 预印本 vs 正式会议/期刊版**：标题高度相似、作者相同 → 合并为一条，**优先记正式版 venue**，但保留 arXiv ID（下游 bibtex-on-the-fly 和读 PDF 都要用）。
- **扩展版**（会议版 → 期刊扩展版）：内容明显扩充时可保留两条，但显式标注关系。
- **多来源重复**：paper-search 通常已去重，跨来源标题措辞差异要人工核一眼。**检索子 agent 落 json 后，组间去重由 `scripts/merge_pool.py` 统一做**——本节的多版本合并在组内检索时就处理好。

---

## 七、检索子 agent 的产出契约（写盘 + 返回）

检索子 agent 和深挖子 agent 走**同一个模式**：完整结果写盘，精简结果返回。

**① 写** `search/<query组-slug>.json`（字段值中文，机读，结构见 `templates/search-template.md`）：命中并纳入的论文（摘要 要点 + 走什么路子 + 角色）、以及检索到但排除的（附排除理由）。写 json 是为了让 `scripts/merge_pool.py` 脚本合并去重——`arxiv` / `doi` / `title` 三个去重键至少填准一个。

**② 返回**主会话一张紧凑清单，**每条**包含：

```
- 标题
- arXiv ID / DOI / URL      （稳定 key；没有就留 URL）
- 年份 / venue
- 引用数                     （有就带，用于判奠基作/里程碑）
- 角色标注                   （奠基 / 里程碑 / 近期前沿，可空）
- 一句话相关性               （这篇走什么路子 / 为何纳入）
```

**返回里不带 摘要 全文**（摘要 要点已写进 `search/` 的 json）。主会话归纳 taxonomy 主要靠"标题 + 一句话相关性 + 年份/引用分布"；不够时去读 `search/` 或对最高引 ~10 篇打 摘要 探针（见 `organizing-axis.md`），而非让 摘要 涌回主上下文。

> 相关性那句话要让检索子 agent **写出"走什么路子"**——一个点明技术路线的短标签（如"基于 {某机制}"、"{某范式} 的变体"），粒度到方法家族、不泛泛说"很相关"。这是 Step3 定轴的关键便宜信号，轴往往能直接从这些路子标签聚出来。
