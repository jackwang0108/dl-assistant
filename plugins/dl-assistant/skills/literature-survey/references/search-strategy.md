# 查询设计与检索策略（Step 1 和 Step 2）

---

## 一、按用途 × 熟悉度的检索侧重

先按用途确定检索重点，同时覆盖主要相关工作。根据检索结果，在 Step 3 再确定分类。

| 用途           | 检索重心                                              | 必做                                              |
| -------------- | ----------------------------------------------------- | ------------------------------------------------- |
| 学习理解       | 奠基作 + 好综述 + 清晰代表作                          | **survey 优先**；务必含奠基作（不限时间）         |
| 找研究方向     | 近年前沿 + 引文链 + 各家明说的 limitation/future work | 多拉近 1-2 年 + 沿引用关系补查；留意论文"未来工作/局限"段 |
| 定位自己的工作 | taxonomy 完整 + SOTA + 各家差异点                     | 广度铺满主流路线，别漏小流派                      |
| 选技术方案     | 围绕具体问题的各类解法 + trade-off + 适用条件         | 按问题的不同 侧面 分别搜解法                      |

**熟悉度做修正**（与用途正交，叠加生效）：

- 用户**基本陌生**时，增加奠基作和优质综述，供分类、报告和阅读清单参考。
- 用户**就在其中做**时，增加近期工作的覆盖。

---

## 二、query 分组设计（Step 1 在 spec 里写，附设计理由）

将查询分成 3-5 组，每组由一个子 agent 执行。各组从不同角度检索，避免整组只换同义表达。向用户呈现方案及写入 spec 时，都说明分组理由。

- **核心概念**：领域最常用的叫法
- **方法/技术名**：主流方法的专有名称
- **任务/benchmark 名**：任务定义、常用数据集/榜单名
- **同义词 / 别名叫法**：换一个社区的叫法——最容易被忽略，却是覆盖度的关键（见 Step5 自检）

**用哪个来源搜、各来源什么特征、按用途怎么加权**：见 **`source-strategy.md`**（核心：SS/scholar 语义查全、arxiv 精确检索近期论文、hf-papers 语义召回 + 补查近期工作，第一轮并肩）。用 `filters.date_range` 指定日期类型与起止范围，并核对各来源实际支持的条件。

---

## 三、沿参考文献和引用者扩展检索

沿参考文献和引用者查找措辞不同、但有实质联系的工作。

1. 候选论文清单里识别 2-3 篇**核心/高引论文**，核对稳定标识。
2. `get_paper_citations`（谁引了它，看后续发展）+ `get_paper_references`（它引了谁，看思想源头）。
3. 对新找到的核心论文重复查询，最多 2-3 轮。新结果中已知论文占比较高时停止。
4. 引文链尤其服务 **找研究方向**（顺引用链摸技术演化脉络）和 **基本陌生的用户**（references 里常含奠基作）。

> 用 `get_query_results` 浏览当前快照，需请求更多上游结果时用 `extend_query` 并检查覆盖。

## 四、survey 优先

优先找已有综述，参考它对领域分类和发展过程的整理。

- 检索时显式找综述：query 带 "survey" / "review" / "a comprehensive"，或 `arxiv` 用 `ti:survey`。
- 找到的综述**自己读**（值得就 tex-mcp 读它的 taxonomy 章节——`tex_open` 打开固定版本 → `tex_outline`/`tex_read`，源码不可用时降级 `download_paper_asset` + pdf-mcp），它的分类法是 Step3 确定分类方式的强先验。
- 但**别只信一篇综述的分类**——综述有作者视角偏向，仍要拿候选论文清单跑分类的四项检查（见 `organizing-axis.md`）。

---

## 五、覆盖不同发表时期

默认搜索偏向近年高曝光论文，**容易全是近 2 年、漏掉奠基作**。硬要求：

- **任何用途**都要主动补该领域的**奠基性工作**（不限时间）——它们定义了问题、是理解后续的地基。
- 判断奠基作：引用数异常高 + 年份偏早 + 被综述反复引用 + 在引文链 references 端反复出现。
- **学习理解 / 按时间线轴** 对时间配比要求最高：早期/中期/近期都要有代表，不能头重脚轻。
- 在候选论文清单里**标注每篇角色**（奠基 / 里程碑 / 近期前沿），供 Step3 确定分类方式和里程碑判断用。

---

## 六、去重（同一工作多版本）

同一工作常有多个版本，必须合并，否则候选数虚高、对比表重复：

- **arXiv 预印本 vs 正式会议/期刊版**：标题高度相似、作者相同 → 合并为一条，**优先记正式版 venue**，但保留 arXiv ID（下游 bibtex-on-the-fly 和读 PDF 都要用）。
- **扩展版**（会议版 → 期刊扩展版）：内容明显扩充时可保留两条，但显式标注关系。
- **多来源重复**：paper-search 通常已去重，跨来源标题措辞差异要人工核一眼。**检索子 agent 落 json 后，组间去重由 `scripts/merge_pool.py` 统一做**——本节的多版本合并在组内检索时就处理好。

---

## 七、检索子 agent 保存和返回的内容

检索和子领域分析都将完整结果保存到文件，只向主会话返回简要结论。

**① 写** `search/<query组-slug>.json`（字段值中文，机读，结构见 `templates/search-template.md`）：命中并纳入的论文（摘要 要点 + 采用什么技术路线 + 角色）、以及检索到但排除的（附排除理由）。写 json 是为了让 `scripts/merge_pool.py` 脚本合并去重——`arxiv` / `doi` / `title` 三个去重键至少填准一个。

**② 返回**主会话一张紧凑清单，**每条**包含：

```
- 标题
- arXiv ID / DOI / URL      （稳定 key；没有就留 URL）
- 年份 / venue
- 引用数                     （有就带，用于判奠基作/里程碑）
- 角色标注                   （奠基 / 里程碑 / 近期前沿，可空）
- 一句话相关性               （这篇采用什么技术路线 / 为何纳入）
```

完整摘要要点保存在 `search/` 的 JSON 中。主会话先按标题、相关性说明和年份与引用分布提出分类。需要核查时，读取相应检索文件，或查看约 10 篇高引论文的摘要，见 `organizing-axis.md`。

> 相关性说明写明论文采用的技术路线，具体到方法家族。例如「基于某机制」或「某范式的变体」。主会话可据此在 Step 3 识别分组。
