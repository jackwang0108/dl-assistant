# 代码整理方案与保留范围

保存cleanup-spec.md。先说明本轮要减少的具体负担和保留范围，再列候选及证据，不以评分/删除行数代替必要性。已有具体授权可沿用，未定支持范围和实质变化需讨论。

```markdown
# 本轮代码整理方案
> 实际日期、用户目标、项目/组件、改前commit及未提交diff，setup/reproduction来源和证据范围。

## 1. 目标、收益与实际边界
什么妨碍当前阅读/开发，哪些范围被授权处理，成本依据/未知；不改是否更合适。
缺环境/行为对照或用户已有改动如何处理，不强制固定tag/文件存在才开工。

## 2. 保留范围清单
ID | 需保留用途/接口/配置/历史资产 | 对应需求/来源与版本 | 实际使用证据 | 未知与影响
包含本轮操作、已约定其他用途、公开/命令行/配置接口、模型保存加载和必要历史兼容。
必要用途不因本次覆盖未命中而删除；有意不再支持的用途另列决定，不称从未使用。

## 3. 候选调查
候选位置/依赖 | 当前用途线索 | 动态配置/注册/外部入口/副作用/保存关系 | 覆盖范围和遗漏 | 处理建议与依据
保留、可提议移除、不确定分别说明；工具无引用结果不是删除许可。

## 4. 逐项变更—受影响行为—验证
变更ID | 类型 | 实际diff范围 | 理由与来源 | 保留/移除或新行为 | 受影响用途 | 验证输入/预期/依据 | 未覆盖/成本 | 授权 | 局部撤销办法
类型：preserve_behavior / remove_out_of_scope / behavior_fix。
需改变研究设计的只提建议并返回讨论；有意修复独立记录，不称等价。

## 5. 批次与实际执行
按可分离改动和依赖安排，不固定批数/每批训练；能发现相关退化的低成本检查优先。
记录改前对照/改后运行的条件、日志/输出位置、预算与停止/报告条件，不覆盖原数据和用户改动。

## 6. 执行前自查与实际决定
保留范围清楚吗？删除是否只凭未覆盖？类型/影响诚实吗？检查相关且有依据吗？撤销和用户原改动能分开吗？
逐项判断、来源/版本、未知与行动影响，状态clear/limited/needs_revision；需要修正就缩范围/补调查/讨论。
用户实际答复和获批范围，未决定保留待定；不要求固定两次审批或merge。
```

依赖删除需考虑运行/安装/插件/命令入口和间接用途，不能只凭没有Python import或当前环境仍能跑。配置、调试脚本、旧模型兼容材料不是默认可删。无删改时保存调查与建议即可，不制造空清理或tag。
