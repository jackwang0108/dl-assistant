# 研究代码整理运行手册

每一步写清执行什么操作、从输出检查什么、异常时回到哪一步、把证据记在哪里。按 [SKILL 的流程图](../SKILL.md#运行流程图)推进。命令从当前仓库、已验证的运行和已审方案取得，本文中的仓库和读数为虚构示例。

## Step 1 核对现场、保留用途和改前对照

从当前仓库和用户指定的记录开始。先执行只读核对：

```bash
git rev-parse --show-toplevel
git branch --show-current
git log -1 --oneline
git status --short --branch
git diff --stat
git diff --cached --stat
```

记录实际仓库、分支、commit、涉及的未提交改动和已运行任务。核当前机器上的解释器或容器、数据和权重能否由拟保留的入口读取。续做时比较已审方案版本、工作区差异、已完成的批次和仍运行的任务，从实际证据继续。

| 到哪里查 | 取什么信息及行动 |
| --- | --- |
| `setup.json` 与 setup 报告 | 读实际环境、数据和权重、`operations`、`checks` 或历史 `ready_commands`。确认哪些入口完整运行过、哪些只验证到试跑 |
| `reproduction.json` 与复现运行 | 按 `targets` 找目标与协议、`use_scope` 找可用用途、`runs` 找命令、工作目录、实际配置和读数。需要 reduced 时核它的基线 run、子集和适用范围，同时记录仍要保护的正式条件 |
| 研究记录与用户给出的用途 | 列出要使用的入口、配置、资产兼容和输出。把各用途与能够支撑它的改前证据对应起来 |
| 只有旧报告或现有仓库 | 从可取得的命令、代码版本、日志和原始结果核现有证据的范围。先说明缺项如何影响本轮，按需要补对应检查 |

| 当前状态 | 怎样开始或续做 |
| --- | --- |
| 原运行与当前起点的相关条件一致，证据覆盖拟保留的行为 | 记录可直接沿用的 run、协议和产物。接着调查该行为和相关入口 |
| 入口可用，现有 run 只核了部分行为或版本有变化 | 定位受影响条件，补能区分本次改动影响的改前检查。缺训练更新证据时，评测对照仍可用于评测路径 |
| 正式入口缺实际环境、数据或权重，或启动被工程问题卡住 | 记所缺条件、受影响的入口和恢复位置，交 setup。已有独立证据的工作按实际范围推进 |
| 缺对应的参考结果或改前行为证据，且本轮无法补齐 | 交 reproduction 补指定检查，或提出有证据支持的较小整理范围 |
| 已有清理方案或存在运行中的检查 | 对照确认过的范围、已完成的批次和实际变更。先查原任务及已有日志，从下一项未完成的检查继续 |

**核对后先向用户汇报。** 说清当前仓库和版本、可复用的环境与入口、改前对照实际核到哪里、有哪些缺项、建议先调查哪些路径。将核对依据记入 `cleanup-report.md` 的开工记录。

例如：「当前在 edge-vision 的 c91b7e4。可以沿用复现的 EMA 权重和 500 个样本的评测结果。我建议先调查评测入口和配置加载。训练更新与保存恢复还缺改前对照，如果要整理训练循环，需要先补对应检查。」

## Step 2 调查源码、入口和保留用途

1. **先画出与本轮有关的源码结构。** 按[研究代码清理指引](cleanup-guide.md)从保留用途确定调查范围，再分类查代码、配置和依赖。用 `rg --files` 或 `git ls-files` 查目录，从正式命令追参数解析、配置覆盖、数据构建、模型与注册、训练或评测入口、checkpoint 和记录输出。记下每条相关命令实际使用的配置和主要调用位置。优先查用户明确会读或会改的路径。
2. **逐项查删除候选。** 先定位声明和直接引用，再查配置键、CLI 和安装入口、注册名、动态导入、脚本和文档所示的调用，以及历史资产的读回兼容。从候选供应的功能反查用户和项目是否还依赖它。使用 `rg -n -F -- "$candidate" "${search_paths[@]}"` 时，先把变量设为候选符号、配置键或注册名以及真实搜索目录，按需要逐项查别名和调用构造。命中结果回到源码和配置核实际用法。
3. **按需收集执行观察。** 已有 run 的日志或证据足够时引用。确需借助覆盖工具时，从实际命令选能经过候选行为的输入和配置，明确覆盖进程及边界。对注册查找、多进程加载和编译扩展，结合实际入口、日志或局部探针补证。保存原始输出及 `coverage/operation-paths.md`，写命令、版本、入口、运行条件、执行到的位置及仍未知的路径。
4. **调查结构和错误处理问题。** 按[结构整理与行为修复指引](quality-guide.md)核实际触发条件、调用方和兼容影响，提出值得做的质量改动。
5. **输出一份整理建议。** 对每个重要入口和候选给出保留、提议移除或用途待核的建议。写实际证据、可能受影响的用途、需要补的证据以及下一步成本。说明本轮最值得做的改动。无需整理时，交付调查结论和可用版本。

调查时用一条具体调用链组织证据，例如「复现 run 的 `command.sh` → `tools/eval.py` 的配置解析 → 生效的模型配置 → 构造函数与注册表 → 运行日志中实际使用的模型」。对未执行的正式配置，继续查它的配置值和解析分支，区分静态查到的支持范围和本次运行观察。

| 候选 | 查过的证据 | 当前建议及依据 |
| --- | --- | --- |
| 旧模型 `legacy_small` 及对应注册项 | `eval-attempt-02` 的实际配置选择 Vision-S。另一份正式配置 `configs/eval-legacy.yaml` 仍指定 `legacy_small`，源码中的模型构建会按该名字进入对应注册项 | 保留模型和注册项。已确认正式配置存在该调用路径，旧模型的实跑行为留待单独验证。若用户要停止支持该配置，另列移除的接口和影响 |

能指出仍受支持的用途及依据时，就可以给出保留建议。提议移除前，要查与候选相关的正式入口、配置和调用机制，并写清受影响的用途和有无迁移需要。查不到外部调用方或历史资产兼容性时，记录缺口并建议先保留。只有补查可能改变建议时才继续调查。

## Step 3 写方案和前后验证办法

1. 按[清理方案模板](cleanup-spec-template.md)写 `cleanup-spec.md`。涉及结构、校验、错误处理等质量工作时另按[质量方案模板](quality-spec-template.md)写 `quality-spec.md`。方案逐项写代码位置、理由、类型、保留及影响范围、改前证据、改后要观察的结果与局部撤销办法。
2. 在首次改动前留够本轮要用的对照。选择能观察对应行为的已验证运行或经确认的补查。给出实际命令、配置、样本或输入、判断规则、成本和证据路径。当前判据按本次行为及改前证据确定。
3. 交审前逐项核对方案是否说清 **改哪里、要保持什么、跑什么、看到什么算达到预期、失败时撤哪一批**。改前记录只有总指标而改动可能触及逐样本行为时，先保存实际参与统计的 ID、标签或逐样本输出，再改对应代码。若当前只能取局部证据，写明继续需要的证据或建议缩到哪一部分。
4. 给用户说明推荐先做哪几项、为什么按这个顺序、预计减少什么负担、哪些功能将移除或改变行为、哪些入口和配置必须保留，以及如何看出退化。清理和质量改动可同次审阅，有意改变行为的修复须单列其影响和确认范围。记录用户实际确认的版本和投入。

| 改动类型 | 检查前怎么准备 | 检查后用什么判断 |
| --- | --- | --- |
| 保持行为的整理 | 固定改前配置、工作目录、资产、实际输入和可观察的行为。例如整理预处理时，保存实际 ID、标签和进入模型前的输出 | 用同一输入沿相同入口执行，核对应输出、配置或调用路径。涉及训练、保存加载时加相应检查 |
| 经确认移除的功能 | 固定拟移除功能的已有入口、配置和受影响调用方，同时列出要保留的操作 | 核移除和相关文档是否按方案处理，复跑保留的操作。遇到未预见的调用方，先调查，再决定缩范围或撤销 |
| 有意改变行为的修复 | 用具体输入重现问题，记录原行为和预期行为。例如缺标签原先会被跳过，拟改为报错 | 用异常输入核新行为，用正常输入核相关回归。若影响旧结果的样本覆盖或指标口径，记录需重新核的复现范围 |

## Step 4 按批修改并运行受影响的检查

逐批检查覆盖本次改动直接影响的行为，尽早发现退化。Step 5 再用下游实际配置复核所有约定保留的用途。

### 修改项目代码前先开整理分支

方案确认后，在首次修改项目代码前，从方案记录的改前 commit 新建本地 `code/baseline-cleanup` 分支。先检查工作区，确认当前任务的起点和是否已有同名本地分支。以下示例中的起点是 `edge-vision` 的改前版本，实际使用时替换为当前方案记录的 commit。

```bash
verified_start=c91b7e4
git status --short --branch
git rev-parse --verify "${verified_start}^{commit}"
git branch --list code/baseline-cleanup
```

首次开工且同名分支空闲时，执行：

```bash
git switch -c code/baseline-cleanup "$verified_start"
git branch --show-current
git log -1 --oneline
```

检查分支名和实际 HEAD 是否对应方案，再开始修改。续做时，先核已有分支确实属于本轮，且基准版本与已完成批次可追溯，再用 `git switch code/baseline-cleanup` 切回。如果同名分支属于其他任务，从本轮已核起点选一个独立分支名，例如 `code/baseline-cleanup-<任务名>`。

切分支可能携带当前未提交改动。先核这些改动归属及它们是否属于已确认的改前状态。若基准包含相关 diff，记录并验证实际分支上的起点也包含它。切换会冲突或混入与本轮无关的改动时，保留现场，先解决如何分离。无需修改项目代码时，可直接交调查结论。

### 分批修改与检查

1. **每批对应一个可核查的意图。** 先做可单独验证的改动，把有意修复与保持行为的整理分批。记录改前版本及本批差异，用 `git diff -- <本批实际路径>` 回读变更，复核影响和局部撤销边界。
2. **按影响运行检查。** 从 setup、reproduction 或已审方案取命令。改入口时核参数解析和实际调用，改数据时核样本、标签和预处理，改训练循环时核参数更新、调度和保存恢复。按需用[验证策略](verification-strategy.md)选择检查。导入或 `--help` 可核入口存在，实际行为由适用的运行或定向检查确认。新尝试在 `runs/` 记录启动与运行证据。
3. **随批回填。** 把预期、实际观察、是否满足判据、运行和差异位置写入报告与机读记录。遇到不符先按 Step 5 的办法排查。需撤销时只处理能归到本批的改动，核用户改动及后续批次后再重跑受影响的检查。

预计超过 5 分钟、耗时不确定或重跑代价高时，在实际机器用 tmux 或集群调度器。记录会话、工作目录、命令和输出。比如从仓库根目录运行已保存的检查命令，替换为真实脚本和本次运行目录：

```bash
run_long=/srv/skills/dl-assistant/scripts/run-long.sh
run_dir=/srv/research/edge-vision/docs/code-idea-prepare/edge-vision-2026-11-24/runs/after-eval-01
session=cip-edge-vision-after-eval-01
printf -v run_command 'bash %q' "$run_dir/command.sh"
bash "$run_long" "$session" "$run_dir" "$run_command"
```

启动后核对 `tmux has-session -t "=$session"`、运行日志和退出码。任务已退出时核实际输出，状态不明时查进程、日志或调度记录。重连先查原任务，再决定续跑。每次重试另存 run。详见[共享长任务说明](../../dl-assistant/references/long-run-ops.md)。

## Step 5 用后续实际配置验证保留行为

1. **按已确认的用途逐项比。** 以未来实际使用的评测、训练、reduced 配置或其他入口为准。通过 `command.sh`、`meta.json`、实际配置和资产身份核前后条件，再比预定的输出、覆盖、参数更新、资源或指标。正式入口只保护了结构、未实跑时，在报告写明已核范围。
2. **发现差异先核可比性。** 用日志、样本 ID、配置、运行环境、权重和生效分支判断是否能作前后比较。若仍有数值差异，核实际指标、单位、误差依据及随机性。先做最能区分原因的检查。例如以同一权重、同一清单分别跑两个版本，比较样本覆盖和逐样本预测。
3. **按证据决定下一步。** 从受影响的路径和最早出现差异的点开始核查。需要比较批次时，使用隔离或可恢复的版本，保留各次运行和已观察到的差异。

| 实际情况 | 怎样处理及记录 |
| --- | --- |
| 前后输入、环境、权重或生效配置对不上 | 先核原始记录和实际使用的条件，按约定条件复跑受影响的一侧。记录失配原因以及该次运行可用的范围 |
| 改前版本也出现同一问题 | 回 Step 1 核基准与输入。记录两侧观察，重新确认哪条改前证据可用。若要修复原问题，按有意改变行为另行确认 |
| 已定位到某批改动 | 记录最早出现差异的批次、代码位置和依据。在原范围内修正或局部撤销，再复跑该批受影响的检查及相应的最终复核 |
| 需要改范围或追加投入，或预算内仍无法归因 | 有可区分原因的下一项检查时，写明所需范围与成本，回 Step 3 确认。暂无法继续时交付有证据的版本和用途，列出无法判定的行为 |

## Step 6 定稿并交接

按[报告与机读模板](cleanup-report-template.md)定稿 `cleanup-report.md` 与 `cleanup.json`。逐项核对改前、改后版本和实际 diff、保留和移除的用途、对应的运行证据、可复跑入口、未验证或撤销的改动，以及合并状态。在机读交接中记录实际运行入口和执行路径记录的位置及版本。早期待办或失败批次以实际状态记录。

首次准备研究仓库时，在项目根的 `docs/research/` 初始化缺少的 `PROJECT_CONTEXT.md` 和 `research-rounds.json`。按[项目背景模板](../../dl-assistant/references/project-context-template.md)记录已核的长期问题、基线和资料位置。轮次索引按[轮次登记说明](../../dl-assistant/references/research-rounds.md)初始化为 `{"rounds": []}`，已有索引和背景沿用。首轮获批开立后再由 execution 登记。

交接前逐项回查：

| 要交代什么 | 从哪里核 |
| --- | --- |
| **已验证的保留行为** | 改动位置、指定版本与实际 diff，改前与改后 run、命令、配置、观察和判据互相对应 |
| **已确认保留、尚未实跑的用途** | 入口、配置、源码或资产兼容性依据，以及下一步该跑的具体检查 |
| **已批准移除的功能** | 方案确认范围、受影响的接口和依赖、实际变更及保留用途的回归证据 |
| **仍待核的项或已撤销的批次** | 当前保留的实际版本、原因、各次证据、问题影响与接手阶段 |

先给用户说明哪些整理已经验证、还没有覆盖什么、接下来可以使用哪个版本。交 `code-reading` 时提供入口、源码与配置、改动理由、执行路径和未覆盖项。后续 `code-idea-execution` 接收可实际复跑的命令与配置、应保持的比较条件和需要补证的范围。无需改动时交付调查结论与可沿用的基准。分支合并由用户决定。

## 贯穿示例 · edge-vision 的评测入口整理

1. **核起点。** 复现目标 `EVAL-01 v1` 的 `eval-attempt-02` 已验证 Vision-S r1 的 EMA 和 Vision-Val v1/val 的完整 500 个样本，Top-1 为 392/500，即 78.4%。可用它核评测入口的整理。训练循环需要单独的改前对照。
2. **调查。** 从该 run 的实际命令找到 `tools/eval.py` 的配置、权重选择、loader 和指标调用。旧模型没经该次评测执行，正式配置仍可通过注册表构建，因此保留。把发现和源文件位置写入调查记录。
3. **建议与确认。** 本轮只提议整理评测入口的配置读取和调用结构。方案要求前后保持 EMA 加载分支、500 个样本各计一次、实际指标定义和正确数。拟改训练循环时先补训练更新、调度及保存恢复的证据，再交审。
4. **执行。** 获准后从 c91b7e4 新建整理分支，再按批修改。先用适用的试跑核实际入口和加载，再复跑批准的完整配置。为改后运行保存独立记录。
5. **发现差异并重验。** 第一次改后运行仍是 392/500，但把实际参与统计的 ID 与原清单按出现次数比对，发现一个 ID 重复、另一个遗漏。核对生效配置及 loader 输出后，沿筛样和聚合路径找首次出现差异的位置。假设确认是本批整理漏传了聚合器的 ID，恢复该字段映射，再保存独立的复跑记录。
6. **交接。** 复跑核实完整清单的 500 个 ID 各计一次、日志实际加载 EMA、正确计数为 392。报告引用失败和复跑两次记录，并交付实际版本、复跑命令和已验证的评测范围。训练路径留在未覆盖清单。
