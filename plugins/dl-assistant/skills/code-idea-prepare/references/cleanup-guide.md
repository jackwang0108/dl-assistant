# 研究代码清理指引

本文件说明怎样从要保留的用途出发，调查代码、配置和依赖的实际使用情况，决定哪些可以提议移除，并为每批清理准备可核查的前后证据。

在[运行手册 Step 2](workflow.md#step-2-调查源码入口和保留用途)开始调查，在 Step 3 用[清理方案模板](cleanup-spec-template.md)汇总建议和验证计划。执行时按运行手册逐批记录实际结果。

## 1. 从要保留的用途找范围和候选

1. 从用户目标、研究记录、setup 和 reproduction 列出正式训练、评测及后续迭代命令、配置和数据权重。沿实际入口解析参数、配置覆盖和默认分支，把要保留的代码路径、接口和资产兼容性写进清单。
2. 用 `git ls-files` 或 `rg --files` 找与本轮用途有关的代码、配置、脚本、依赖声明和测试。记录具体负担，例如同一评测入口存在几个用途相似的脚本，难以判断该从哪个开始。独立工具或历史配置是否值得调查，按实际影响决定。
3. 对照全量与 reduced 的调用路径。比如 reduced 没启用某个算子，正式配置还会调用它，就保护算子、注册和相关环境依赖。旧 checkpoint 仍须读回时，连同其参数名、构建配置和加载路径一起核。只查本轮涉及的范围，较大范围由用户目标决定。

## 2. 按候选类型追实际使用方式

| 候选 | 怎么查 | 接下来根据什么判断 |
| --- | --- | --- |
| 函数、类、模型或算子 | 查定义、直接调用、重新导出与别名，再查注册名、配置里的 `type` 或 `_target_`、工厂和动态导入。构造历史模型时，回查保存配置和参数加载路径 | 有正式入口能构造或读取就保留对应范围。覆盖没有命中时，说明查了哪种运行，追配置分支和实际用途 |
| 脚本、CLI 或配置 | 查脚本名、命令名、完整配置路径和文件名。再读包的命令入口、任务脚本、README、配置继承和默认选项。旧文档也要追到仍受支持的命令 | 查明调用者和原用途。引用若只出现在拟一并移除的旧示例，仍要核该示例是否受支持，并把受影响文件列进方案 |
| 依赖或扩展 | 查项目实际使用的清单、锁文件、构建文件和环境配置。分别查发行包名、导入名、CLI、插件入口和动态加载。检查保留的依赖是否还会间接安装或使用它，核编译扩展、原生库及相关运行日志 | 明确是仅移除直接声明，还是也要停止支持依赖它的操作。包是否仍装在当前环境、测试是否碰巧通过，只能作为线索。验证按实际安装链和受影响入口做 |
| 调试分支与历史兼容 | 查开关默认值、被哪些配置覆盖、是否在启动或导入时注册组件、是否用于读取旧资产。需要时触发相关入口观察实际分支 | 确认调试入口和共享实现的边界。默认不开的功能也可能是受支持入口。继续保留的部分和计划移除的部分分别列明 |

检索从实际仓库根目录开始。例如在虚构的 `edge-vision` 中，可以这样查一个候选在已知目录里的字面引用。把关键词和路径换成当前仓库存在的位置，按需要检索公开别名、入口名和配置键。

```bash
candidate='legacy_small'
search_paths=(tools configs models scripts README.md)
rg -n -F -- "$candidate" "${search_paths[@]}"
```

打开命中的配置和加载代码，追到具体调用。遇到由字符串拼接、配置合并或插件发现生成的名字，回查生成位置和实际生效配置。执行观察可复用已有 run，或按范围跑定向检查。运行过哪些进程、覆盖不到哪些条件，记入 `coverage/operation-paths.md`。外部调用方、动态分支或历史资产范围无法确认时，把这个缺口写入建议。

## 3. 把证据变成可审阅的清理建议

1. 每项记录候选位置、已查范围、找到的用途、可能受影响的调用方和推荐处理。确认用途仍在保留范围就给出「保留」。只缺某条会改变决定的证据时，写「待核」并列补查办法。
2. 推荐移除时，把依据写到具体用途。例如「只供早期的人工可视化，当前正式入口与部署脚本均走另一条路径，建议连同对应文档说明一起退役」。仍有调用的功能也可提议停止支持，列出会失去的入口、现有调用者、迁移方式和用户要决定什么。
3. 比较清理收益和取证成本。能解释具体负担、影响边界和验证办法时提交建议。未知用途较重要而补查暂不可做时，建议保留并说明原因。范围很小或维护收益有限时，可交调查结论。

## 4. 设计批次和改前、改后检查

1. **按影响和依赖分批。** 可独立验证的脚本、配置或依赖分别安排。若一条旧入口和它唯一依赖的配置必须同时退役，可以放在同一批，并写清各自影响。给每批列出实际路径、相关用途、预计成本和撤销范围。
2. **选择能发现退化的检查。** 移除独立脚本时，核退役入口、对应文档和自动化引用，再实际跑一条受影响的保留命令。变更配置时，核继承、覆盖和生效值。清理依赖时，在独立环境按项目的安装或构建入口验证，并实跑涉及的保留操作，避免现有环境中的残留包掩盖缺项。
3. **给最终复核留改前证据。** 若改动可能影响正式评测，记录实际输入、数据覆盖、权重分支及指标；若改动影响训练的更新或保存加载，补对应检查。用后续实际配置完成约定的复核，逐批检查只回答该批的影响。检查与证据深度见[验证策略](verification-strategy.md)，比较依据以已审的本次方案为准。
4. **按结果决定继续或撤销。** 先核实际使用的输入、环境和配置，再定位影响。能确认由某批引入时，按方案修正或局部撤销并重验。记录实际差异和未决用途。需要变更批准的支持范围或投入时，回 Step 3 审阅。
