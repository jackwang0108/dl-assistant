# 结构整理与行为修复指引

本文件说明怎样从实际阅读和开发困难中选择值得做的质量改动，判断它会影响哪些行为与兼容性，并为每项建议设计能发现退化的检查。

在[运行手册 Step 2](workflow.md#step-2-调查源码入口和保留用途)调查质量问题时使用，在 Step 3 用[质量方案模板](quality-spec-template.md)提交建议。分批执行和差异处理沿用运行手册。

## 1. 从能指出的问题开始

从用户实际要读或要改的入口顺着调用看源码。记录具体负担、代码位置和触发条件。例如，默认参数在入口和包装函数各被覆盖一次，导致读完启动配置仍难判断生效值。错误处理问题要记录观察到的原行为，给出可复用的输入、最小配置或原日志。只在静态阅读中看到可能的问题时，先确认触发条件，再决定是否需要实跑。

沿相关调用往下查数据与实际分支，往上查调用方、配置和下游如何处理输出。比较拟议改动能省下的工作与需要补的验证。已有结构能满足当前用途或验证成本过高时，把暂缓的理由记进调查结果。

## 2. 按实际影响判断类型

先写一句「在什么输入和配置下，哪个调用方会看到什么变化」。保持已约定行为属于整理。结束对某个入口或选项的支持，按经确认移除的功能处理。有意改变错误、数值或其他可见行为，按修复处理并单列确认。改动影响研究方法或实验设计时，带证据交回研究设计阶段。

| 建议 | 先追什么 | 用什么证据来判断 |
| --- | --- | --- |
| 提取配置读取、简化包装层 | 从正式 CLI 追默认值、命令行覆盖、配置合并顺序、实际函数和公开签名。若涉及模型包装，同时追参数命名与序列化路径 | 用同一配置和样本核解析后的配置、输入或输出。使用旧 checkpoint 的用途需要实际尝试读回，检查对应参数和输出。修改键名时写迁移办法和覆盖范围 |
| 增加输入校验或收窄异常捕获 | 用实际输入追旧分支，读调用方如何处理异常、退出码、跳过样本、重试和部分产物 | 用能触发该分支的输入记录原处理方式。若拟改变报错、退出或样本统计，交审说明影响，验证新行为及正常输入的回归 |
| 调整日志与错误消息 | 查实际查看或解析这段输出的脚本、用户操作和实验记录。项目使用 W&B 时，核现有 run 身份、指标和同步流程 | 对照实际日志、记录字段和调用方期望。日志格式、退出状态或记录内容有意变化时分别写明 |
| 加 `epsilon`、`clamp` 或换精度、算子 | 沿实际执行分支定位受影响的计算、输入范围、数据类型和后续损失、梯度或统计 | 用能触发问题的边界输入记录旧值或错误，再核新预期。用正常输入回归关键计算，必要时补目标配置的评测或更新检查。说明哪些原复现证据需要重核 |

## 3. 先定证据，再提交方案

1. **保持行为的整理。** 用同样的资产、配置和输入保留改前证据。选择能反映改动影响的观测，例如生效配置和实际分支、逐样本 ID、模型输出或保存读回。已有复现只有总指标时，补能区分行为变化的观测。
2. **有意改变行为的修复。** 用一组异常输入重现旧行为，写预期的新处理方式及依据，再用一组正常输入选回归检查。比如缺标签从跳过改为报错，异常检查要核实际退出状态、错误消息和是否写出部分指标。正常检查要核正式配置的样本覆盖、权重和指标。
3. **准备用于审阅的决定。** 每项说明推荐做或暂缓、要改的位置与范围、预期保留及改变的行为、检查成本、受影响的原证据和局部撤销办法。分别记确认情况。旧报告与实际检查可直接引用。
