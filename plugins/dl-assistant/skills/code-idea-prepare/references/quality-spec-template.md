# 可选结构整理与行为修复建议

只有本轮确有这类工作时保存quality-spec.md，可引用cleanup-spec的保留范围、统一变更表与授权，不重复材料。不以“健壮性/优化”名称认定无行为影响，也不强制每次做第二轮优化。

```markdown
# 结构整理与修复建议
> 用户目标、实际位置、改前版本、保留范围与来源。

## 1. 具体问题及是否值得改
用户/开发实际遇到什么，证据在哪；没有必要则不改，不全仓库追求形式整洁。

## 2. 逐项建议
ID | 类型 | 原行为/问题 | 拟议变化 | 受影响用途/接口/资产 | 理由/来源 | 验证及依据 | 未知/成本 | 授权与状态
- preserve_behavior：旨在保持已约定行为，需实际检查，不靠名称认证。
- remove_out_of_scope：有意缩减支持范围，说明调用/文档/历史兼容影响和实际批准。
- behavior_fix：有意改变行为，说明原问题、新预期、依据及退化检查，单独记录。

## 3. 行为与兼容影响
加校验是否改变可接受输入和异常？收窄异常是否改变失败处理？模块扁平化是否改变参数/保存键/公开接口？
epsilon、clamp、精度、数据处理或算子替换影响哪些计算/比较？哪些原复现结论需要再核？
不能从最终指标接近推导等价，不能编预测偏差说明代价。

## 4. 执行与验证
引用统一变更—验证表，选择实际相关输出/接口/数据/参数更新/保存恢复/任务结果检查。
新增行为按明确要求验证；修改研究方法/对照时返回idea-find/iterate，不能借质量优化实施。
实际授权与暂停条件清楚后执行，超出范围先讨论；未批准建议保留，不偷偷修。

## 5. 结论边界
实际采用/未采用/撤销什么，验证覆盖到哪里；哪些未知和原参考失效项交setup/reproduction或研究讨论。
```

输入校验、错误消息或异常处理的改变也属于可观察行为。可以是合理且获批的改进，但不能称毫无行为变化；“用户同意”说明授权，不证明正确或等价。未覆盖代码不一律禁止整理，但没有足够用途/行为依据就不改，不能只因覆盖命中才拥有修改许可。
