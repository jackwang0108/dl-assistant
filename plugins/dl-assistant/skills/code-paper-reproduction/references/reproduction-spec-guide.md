# 复现规格分析指引

本文件说明怎样从后续需要使用的比较基准出发，确定要复现的结果或行为，核对参考条件与实际实现，并据此制定取证方案、判断规则和预算。

在[运行手册 Step 2](workflow.md#step-2-定位准确的参考结果与协议写复现规格)使用。原始核查过程写在 [alignment.md](alignment-template.md)，供用户决定是否开跑的建议写进 [spec.md](reproduction-spec-template.md)。

## 1. 从下一步的用法倒推复现目标

1. 读用户任务、选型和 setup 记录。写一句「后续要在什么条件下改变或比较什么，因此本轮需要哪一项可重复的结果或行为」。只想先跑通论文代码时，按用户想看的结果或行为确定目标。没有已提出的研究假设时，以本轮实际用途定范围。
2. 找到对应的参考对象。固定权重下比较推理或后处理时，找使用对应模型变体、发布权重和评测协议的结果。研究会重新训练时，另核论文的训练起点、训练终点和权重选择，判断是否需要建立重训基准。只验证一段组件行为时，从论文、发布说明、参考实现或已知答案取得具体预期。若参考或资产不足，判断能否取得有意义的局部检查，记录它还能回答什么。
3. 有多个候选时，先看哪一条能支撑后续决定，再查它的条件能否重建，最后比较取得证据的成本。给推荐目标分配 ID，写参考版本、精确行或行为出处，以及其他候选留待什么时候用。

| 后续要做的决定 | 有哪些候选 | 怎样推荐 |
| --- | --- | --- |
| 清理代码后，确认固定权重的推理和评测行为是否保持 | 论文的重训结果、与发布权重对应的评测结果 | 推荐能核到发布版本、权重变体和实际评测协议的那一行。先检查它是否覆盖清理涉及的入口和输出 |
| 加入方法后，要比较重训带来的收益 | 发布权重的评测、完整训练、小设定训练 | 从后续需要的训练和评测条件确定正式比较目标。若当前预算只能跑小设定，说明该小设定能支持哪项决定，以及正式目标还差哪项验证 |
| 用户拿到论文代码，只想跑一次看看 | README 的试跑入口、论文表格结果、组件行为 | 先判断用户想观察输出、体验正式评测，还是核论文读数。给一个建议目标，说明现有资产能支持哪种检查 |

## 2. 顺着参考和入口核条件，决定怎样补证

- **从参考结果向外追条件。** 固定表格行后，顺着图注、实验设置、附录和发布记录确认数据划分、模型与权重、输入处理、指标和结果选择。比如表格写 Top-1 时，要查是哪个验证集、是否做多次预测、如何聚合。
- **从计划运行的命令向内追实现。** 从 setup 实际核过的操作或仓库正式入口开始，读默认配置和命令行覆盖，跟到权重加载、loader 和指标调用。训练目标另外核初始化、实际更新、调度和 checkpoint 选择。把「setup 已实际核过」「当前配置或源码显示」「这次还需实跑确认」分别写进 `alignment.md`。
- **把差异转成待审决定。** 保留参考条件及出处，写明应该恢复参考条件、在新条件下建立基准，还是先做局部检查，并说明理由。计划另用划分或指标时，明确新协议的用途与和原结果的可比范围。

按下表把未知变成行动。每条在 `alignment.md` 写出处、影响和当前结论，在 `spec.md` 写会改变本轮执行的条件。

| 现在知道什么 | 下一步查什么 | 对本轮有什么影响 |
| --- | --- | --- |
| 论文正文与发布脚本指向不同划分 | 先回查图注、附录、版本对应关系和维护者说明，记录两份来源 | 若仍有冲突，交审时说明哪一条参考受影响。可建议在已确定的划分做本地测量，并列明恢复原表格比较所需的证据 |
| 源码支持 raw 和 EMA，实际生效分支待核 | 从拟执行命令追配置覆盖，确认怎样从日志或运行记录看到实际加载的参数 | 换成运行时检查项。加载证据到手后再按协议判断可比性 |
| 目标 checkpoint 缺失或身份无法确认 | 查对应发布项和 setup 的资产记录，写清所需版本、变体及可取得的来源 | 该目标按 Step 1 补资产。若已有可独立验证的组件行为，可另提范围，并说明它能回答什么 |
| setup 只验证了评测子集 | 查已核的样本统计、正式清单和正式入口配置，确定需要新增的实跑证据 | 如果资产齐备、参考范围已明，计划按正式清单运行，并保留实际参与统计的 ID 和分母 |

## 3. 先写结果解释，再决定跑几次

1. **选择最直接的证据。** 按[复现验证策略](reproduction-strategy.md)选评测、训练或组件检查。对每项运行写清它要解决哪个未知、需要保存什么，以及它能让用户做什么决定。若全量训练超预算，优先挑能回答本轮具体问题的检查，分别注明覆盖到的条件与阶段。
2. **把可比条件和结果解释分别写清。** 先写哪些证据到手才可比较，例如实际样本覆盖、权重变体和指标实现。再写数值接近、有差距和证据不足时分别怎么解释。论文只报四舍五入后的结果时，保留分子、分母、实测未舍入值和论文显示精度，按同单位报告差异。需要设阈值时给出本项目依据。缺少误差或波动证据时，交付实测差距及其解释限度。
3. **指定触发下一项检查的观察。** 如实际加载 raw，而参考要求 EMA，则先核加载分支，再按原协议确认修正和复跑。若条件已对齐却仍有差距，按[差距排查](trust-traps.md)挑能区分原因的一项。需要了解固定权重评测的波动就重跑评测，需要了解训练间波动就另规划独立训练。分别说明重复单位、固定条件和预计能解决的疑问。
4. **把预算和停止条件绑到决策。** 根据目标机试跑、实际吞吐、样本或更新数和固定开销估成本，区分实测、估算和未知。写明先跑什么、什么观察值得追加、最多投入多少、何时停。达到目标、预算用完或关键参照仍不可得时，写明当时可交付的证据与未决项。

把运行后的判断拆成三个问题。**条件允许直接比较吗？本地结果与参考差多少？这次测量能供下游做什么？** 例如，条件已核且读数有差距时，保留实测差距与未决解释。若本轮也需要代码清理前的对照，再判断该运行是否满足改前改后比较的要求，包括入口、权重、样本、指标和需要的重复性证据。满足时可把「可用作本地改前对照」和「与论文读数仍有差距」同时记在规格的解释规则中。读数碰巧相同、关键条件仍未知时，先补证或限定用途。

## 4. 把建议写入规格并交审

用[复现规格模板](reproduction-spec-template.md)写 `spec.md`，引用 `alignment.md` 的条件核对。检查目标 ID 和协议版本是否一致，计划的命令是否来自当前环境和仓库，保存的证据是否足够应用判据。执行前说明哪些入口已经试跑、哪些只查过源码。交审前用三个假设结果反查规格。数值一致但关键条件未确认时，能否指出要补的证据？条件一致但读数有差距时，能否指出是否还要查、查哪一项？预算用完时，能否写清哪些结果仍可交付？遇到答不出的情形，先补具体行动和解释范围。

给用户一个具体建议，说明对照哪项结果、什么条件下能比较、首轮预计投入、何时需要追加或停下。把仍待确认的关键条件、它为何会改变决定，以及你建议怎样处理一并讲清。记录用户确认的规格版本和预算后进入 Step 3。

## 示例 · 全量训练超预算，先验证哪一项

以下为虚构场景。同机试跑推算全量训练约 40 小时，本轮可用 8 小时。论文另报一个小设定的完整训练结果，所需配置和数据已找到，预计约 5 小时。用目标全量配置跑到首个需要核查的调度节点，预计约 2 小时。

1. **确定当前决定。** 下一步要先建立一个有论文参考、可在同条件下复跑的小设定训练对照，因此推荐先做一次小设定完整训练。把小设定的表格行、初始化、数据、训练日程、权重选择及最终评测写入规格。若后续要在全量条件下比较方法收益，把全量训练保留为待验证目标。
2. **给短训明确的触发条件。** 若下一步的工作也依赖全量入口是否能完成真实更新、调度是否在应有的更新步生效，再建议在余下预算中安排约 2 小时短训。事先写下要核的更新步、学习率和可见的运行证据。两项都需要时，单独估算各自成本，按实际剩余时间和确认范围决定能否追加。
3. **写清预期交付与停止条件。** 小设定条件可比时交付该次完整训练的读数和差距。若追加短训，单独交付目标配置实际走到的阶段、更新和调度证据。若缺关键条件、已回答当下问题或预算不足以完成下一项检查，记录剩余未知和所需资源。一次小设定训练的读数只描述这次运行，跨次波动需要重复观测。

交审时可以这样说明。「建议先用约 5 小时跑完论文的小设定，建立供下一轮比较的同设定对照。如果下一步还需要确认全量入口的真实更新和调度，我建议在余下预算里加约 2 小时，跑到指定更新步。那次短训能核到该阶段的运行行为。要判断全量最终性能，仍需在目标条件下跑完一轮并按正式协议评测。」
