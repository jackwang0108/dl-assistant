# 目标 2：design-story（蓝图初建或重新确定提纲）

## 何时用

两个触发：**初建**（从零写，init-setup 后）和**重新确定提纲**（故事线实质变更——贡献变了、总论点变了；或 write-section 标了「蓝图脱节」；或修改清单含 re-frame 项；或 ingest-results 报**实测结果改变了最有证据支持的贡献**——数据揭示更强卖点/原证据最充分的贡献被证伪，见 blueprint-design 蓝图更新规则）。蓝图是**随工作进展更新的文档**，不是一次写完的。

## 读哪些

- `references/sections/blueprint-design.md`（蓝图 schema + 节清单四步程序 + 三位一体 + refuted/abandoned 用法 + 随工作进展更新的文档规则）。
- 初建读取 `docs/research/paper-package.md` 或等价材料，沿引用查 `claims.json` 和关键运行。重新组织论证时读现有 `blueprint.md`、当前稿件和触发材料。
- `paper-state.json`（venue 页限用于页数参考；节状态用于评估波及面）。

## 子动作

形成提纲之前，先逐项对应科学问题、已有认识、候选主张、实际观察、证据所在版本、适用边界和最强替代解释。如果核心主张缺少能区分解释的证据，将具体问题和缺口交 iterate。已有判断明确、只需一项具体比较时，登记需补的证据和受影响的章节或图表。

1. 读材料 → 出（或改）`blueprint.md` 的叙事主体：**故事线（一段连贯散文，人读核心）** + 总论点 + **最有证据支持的核心贡献**（一句话：论文在哪个维度、场景或约束下贡献最明确，全文叙事围绕它组织；证据不足以支持优势的维度不作为主要比较维度）+ contribution 清单（2~3 句白话 + 对账字段：挂 claim / 验证维度 / 实验类型）。**不写段级大纲**；叙事主体禁工作语言（见 blueprint-design 写作纪律）。
2. **定节清单（设计决定，走 blueprint-design「节清单怎么定」四步程序）**：故事线拆叙事任务 → 先尝试把任务分配到常见的七个章节（无法合理归入现有章节的任务过三条判据：任务独立 / 合并后会削弱相邻章节的论证 / 内容足以独立成节）→ venue 对标校准（authorkit 填充 tex 节结构 + 1~2 篇同 venue 同方向近两年论文）→ 节清单 + 每节角色标注定稿。随后按实际节清单写每节叙事任务（读者该相信什么 + 3~5 要点）+ **页数参考（消费 venue 页限，量级分配，软约束不硬卡）** + **首图（teaser）信息意图**（一张图说清问题+方法+效果——首图塑造故事线，蓝图阶段就定，不进正文才想）+ locked_decisions（末节对账区）。
3. 和用户逐项过：故事线讲得通不通、总论点立不立得住、**最有证据支持的核心贡献抓没抓对（论文在哪个维度、场景或约束下贡献最明确）**、**节清单（有没有该立的节没立 / 该并的没并）**、contribution 分组、每节叙事任务、首图意图、页数参考量级对不对。用户质疑/调整 → 改 → 循环。
4. **更新提纲时**：对比新旧蓝图，列出受影响的章节（术语/gap/named-abstraction/contribution 变了的；**节清单变了的——新增/合并/删除节本身是实质变更**），**自动生成这些节的修订项进 backlog**（source=user 或 review-response，type=write-section）——故事变了，受影响的章节必须排队回改，不许靠人记。

## 产出

`_draft/blueprint.md`（初版或新版）；重新确定提纲时外加一批受影响章节的修改任务。

## 状态更新

`blueprint_version` 递增；初建——注册各节写作项 + 首图项进 backlog（source=blueprint-init），sections 各节置 planned + 写 page_budget（参考量级，软约束）；重新确定提纲——受影响节 status 置 needs-revision + 修订项进 backlog。

## 确认点

逐项请用户确认论文提纲，包括章节安排。确有已明确的证据缺口时转入 design-experiment。更新后按已登记的任务修改受影响章节。

## 易错点

- **蓝图是人读优先**——故事线段必须写连贯散文，叙事主体禁工作语言；产出先过「故事线一段读完不看其他材料能讲清论文吗」这条自查。
- **节清单是设计决定，不是默认七节照抄**——走四步程序（拆任务 → 按三项判据决定是否独立成节 → venue 对标 → 定稿），和用户过；新节要有角色标注，决定 write-section 读哪个指南。
- **不写段级大纲**——段级结构留给 write-section 的方案子步即兴定。
- named-abstraction 必须**非 generic 词**（禁 "novel framework" 等），否则总论点立不住。
- **每个 contribution 必须有验证维度+实验类型**——没验证路径的 orphan contribution 蓝图层就标出来（补实验维度或砍）。
- **总论点/contribution 必须答得出「为何不是拼接」**——方法由多个组件/insight 构成时，说清组合产生了什么单拎任何一边都没有的东西（新能力 / 新视角 / 互相解除瓶颈）；答不出 = 缝合怪立论，reviewer 一问就塌，蓝图层就要打回故事线重想，别带着进写作。
- **围绕证据最充分的贡献组织论证。** 据此安排故事线、主结果和首图。若证据无法支持原先强调的贡献，先在提纲里重新确定论证重点和章节安排。
- **页数是软约束**——蓝图只记页限 + 参考分配（量级感知）；不在蓝图层砍 contribution/消融，取舍统一留给 finalize 定稿时压缩篇幅（用户确认）。
- 三位一体在蓝图层就要锁（intro gap ↔ RW 定位 ↔ method 机制名 ↔ experiment 组件名）。
- **更新提纲后，为受影响章节登记修改任务。** 按任务同步修改正文。
- **首图意图蓝图阶段定**——它塑造故事线；写正文时才想首图，故事已经散了。
