# Blueprint Design：论文蓝图设计（随工作进展更新的文档，op-2-design-story）

把论文准备材料 + 中期两层 claim 展开成**论文蓝图** `_draft/blueprint.md`。蓝图是**人读优先**的文档——用户读它要能看懂「这篇论文讲一个什么故事」，并据此确认；它不是字段表单的填答。蓝图也是**随工作进展更新的文档**：初建于 **op-2-design-story**，之后论证有实质变化时更新提纲（见「蓝图更新规则」），不是一次写完就封存。全文前期对齐用，**不写段级大纲**。

> **不另造 claim 树**。消费中层 `claims.json`（两层：总论点 `paper_claim` + 子论点 `claims[]`）+ iterate 论文准备材料（创新点清单 + 故事线骨架 + refuted/abandoned + Roadmap 终态 + locked_decisions）。writing-paper 只产蓝图，不重复造 contribution / locked_decisions。

## 写作纪律：人读叙事在前，机器对账在后

- **叙事主体（故事线 / 总论点 / contribution 白话 / 每节叙事任务）用自然语言写**，面向「只看蓝图、不看其他材料的读者」——禁用工作语言：C-ID、orphan contribution、三位一体、验证维度这类词只许出现在对账字段里，不许进叙事句。
- **对账信息（C-ID / 验证维度 / 实验类型 / locked_decisions）降级为附属字段或末节**，供 agent 一致性核对用，不是阅读主体。
- **别照模板机械填空**。schema 里的方括号是内容指引不是格式牢笼——写出来的每一段都要是读得通的句子。

## 共同打磨（确认点·用户确认）

蓝图定错后面全歪，初建时和用户一起定：

1. agent 出 `blueprint.md` 初版。
2. 和用户过：故事线讲得通不通、总论点立不立得住、contribution 分组对不对、每节叙事任务清不清楚、首图信息意图抓没抓住。
3. 用户质疑/调整 → agent 改 → 循环。
4. **用户确认** blueprint.md，才进 op-4-design-experiment 实验规划。

后续每次实质性更新提纲（见「蓝图更新规则」）同样过这个确认点。

## blueprint.md schema

````markdown
# 论文蓝图
blueprint_version: v[N]（初建 v1，提纲有实质性变化时递增，见「蓝图更新规则」）

## 故事线
[一段连贯散文（5~10 句）：问题是什么 → 现有方法为什么不行 → 我们的洞察是什么
 → 方法怎么做 → 靠什么实验证明 → 预期效果。读完这段不看其他材料就能讲清这篇论文。
 这段是全文叙事核心，也是 teaser 图和 Introduction 的种子。]

## 总论点
[一句话，白话：针对 X 问题，现有因 Y 不足，我们提出 [方法名] 通过 Z 解决]
> 方法名硬约束：能唤起直觉的复合名词（如 "Discrete VASD"），
> 禁 generic 词（"novel framework" / "unified approach" / "simple yet effective"）。

## 最有证据支持的核心贡献
[用一句话说明论文在哪个维度、场景或约束下贡献最明确，例如新能力、新问题、新机制、
 更低成本、更高效率、更好扩展性或更有意义的权衡。
 用证据最充分的贡献组织主结果、teaser 和摘要的关键数字。
 证据不足以支持优势的维度按 experiment-writing-results 的弱结果指南呈现。]

## Contribution 清单
### C1：[创新点小标题]
[2~3 句白话：做了什么、为什么重要、靠什么实验证明]
> 对账字段（小字段，非阅读主体）：挂 claim [claim-id...] · 验证维度 [主性能/组件有效性/效率/泛化…] · 实验类型 [主表/消融/分析/efficiency/case]
### C2：…
> 每个 contribution **必须有验证路径**——没验证路径的 = 没东西证明的 contribution
> （要么补实验维度，要么降级/砍），蓝图层就标出来，别留到实验规划/将实验结果写入论文才发现。

## 节清单与每节叙事任务（读者认知顺序）
节清单：[本文的实际节清单——design-story 按「节清单怎么定」程序定，确认点确认；
  每条标注角色（动机/定位/铺垫/方法/证明/收束/压缩/仓库）]
- <节 1>（角色：…）：[这节读完读者该相信/知道什么]——要点：…；…；…（3~5 个）
- <节 2>（角色：…）：…
- …（按实际节清单逐节写，不照抄默认七节）
> 只到「叙事任务 + 要点」级，不写段级大纲。
> 常见默认起步（可增删合并）：Introduction / Related Work / Method / Experiment /
> Conclusion / Abstract（最后写）/ Appendix；非默认节例：Background/Preliminaries（铺垫角色）、
> Problem Formulation、Method 拆多节、Theory/Analysis 节。

## 首图（teaser）信息意图
- 一张图说清：[问题是什么 → 方法怎么做 → 效果如何，三个信息单元各一句]
- 视觉钩子：[读者第一眼看到什么——对比 / 流程 / 结果]
> 首图在蓝图阶段就定信息意图——**首图塑造故事线**：它逼你把"问题+方法+效果"
> 压进一个画面，压不进去说明故事线还没收敛。具体视觉 spec 由 op-6-make-visual 展开。

## 页数参考（消费 op-1-init-setup 的 目标会议要求，软约束）
- 总页数：[venue 正文页限，如 CVPR 8pg / NeurIPS 9pg（不含 refs/appendix）]
- 参考分配（量级感知，不硬卡）：<按实际节清单分配，如 Intro ~1 / Method ~2.5 …>
> 页数在蓝图层只做**量级感知**——知道是 8 页会还是 14 页会，影响写作密度预期，
> **不是逐节硬预算**。写作期先完整写出各节内容，初稿超页是正常状态；删减或移入附录 appendix/精简
> 是 finalize 定稿时压缩篇幅的事（op-8），由用户逐项确认——agent 不替人做内容取舍。

## 对账区（机器核对用，非阅读主体）
### locked_decisions（消费论文准备材料，不另造）
- baseline：[…]
- metric：[…]
- 已做消融：[…]
````

## 节清单怎么定（design-story 的设计决定，四步）

先把论文的论证拆成读者需要理解或接受的任务，例如理解问题及其重要性、明白论文定位和方法、评估实验依据、记住结论。再决定这些任务分别由哪些章节承担，常见的七个章节可用作起点。

1. **拆任务**：从故事线段拆出叙事任务清单——每个任务一句话（读者读完该知道/相信什么）。
2. **为任务安排章节。** 先尝试归入常见的七个章节。某项任务或一组任务只有同时满足以下三项条件，才考虑独立成节。
    - **任务独立**：有自己一句话说得清的叙事任务，和邻节不混（例：「让读者具备理解方法的预备知识」——既不属于 RW 的「锚定定位」，也不属于 Method 的「讲我们的东西」）；
    - **合并后会削弱相邻章节的论证**：并进相邻节会破坏那个节的叙事纯度（RW 里讲背景知识就写成教科书；Method 里先铺三节预备知识，贡献被稀释）；
    - **内容足以独立成节**：能撑起大体一节——半页以下的内容安排为小节（每多一节有固定开销：标题、过渡段、页数切片）。
    用同一组判据判断常见章节能否合并：RW 任务太小或 venue 惯例如此 → 并入 Introduction；结论三两句 → 并入 Experiment 末尾。
3. **用目标会议的材料核对章节安排。** 对照 author kit 示例 TeX 的章节结构，以及近两年 1~2 篇同一会议、方向相近的论文。用 paper-search 查找这些论文，确认章节安排符合会议要求和读者预期。
4. **定稿进蓝图**：节清单 + 每节角色标注（动机/定位/铺垫/方法/证明/收束/压缩/仓库）+ 每节叙事任务写进蓝图，随蓝图确认点一起确认。角色决定 write-section 读哪个写作指南（见 op-3）；页数参考按实际节清单分配（量级感知，软约束）。

## 三位一体（全文一致性总纲，agent 侧纪律）

Introduction / Method / Experiment 是**同一个论点的三个面**，必须锁死：

| section | 讲论点哪面 | 锁死关系 |
|---|---|---|
| Introduction | 为什么重要（动机） | gap = RW 定位 = Abstract 第 2 句 |
| Method | 怎么实现 | 核心机制名 = intro 方法名 = experiment 消融组件名 = 方法图模块名 |
| Experiment | 是否成立（证明） | 每个 contribution 有实验；主结果数字 = Abstract 第 4 句 |

术语 / gap / contribution 在三个 section 全程一致——op-7-audit 每次必核的核心检查项。

## 各角色叙事定位（一句话，写作指南按角色参照）

非默认节（Background/Preliminaries 等）没有专属写作指南——按蓝图里的角色标注参照最近角色的定位与 `references/sections/` 下对应指南（铺垫节借 related-work 的锚定纪律 + method 的符号纪律）。

- **Introduction（动机）**：动机（漏斗：大问题 → 缺陷 → 洞察 → 方法 → 贡献）。
- **Related Work（定位）**：锚定位（本文在哪条线、gap 在哪）；**不是综述**；每节末尾两三句把本文放进去。refuted/abandoned 子论点 = "别的路走不通" 的素材。
- **铺垫节（Background/Preliminaries，若有）**：让读者具备理解后文的预备知识——只讲后文要用的，不写成小综述；术语符号与 Method 的符号体系同源。
- **Method（方法）**：源头是代码核心改动的几个 part，可呼应动机，part 间逻辑递进。
- **Experiment（证明）**：针对总论点拆成可验证维度（主性能 / 消融 / 分析 / efficiency / case）。
- **Conclusion（收束）**：回扣已证明的 + 诚实局限 + 具体未来工作。
- **Abstract（压缩）**：全文压缩（最后写）。
- **Appendix（仓库）**：正文塞不下的（额外消融 / 实现细节 / 定性 / 证明）。

## refuted/abandoned 子论点怎么用

论文准备材料带的 refuted/abandoned 子论点（证伪 / 放弃的）**不进 contribution**，但是金矿：

- **Related Work**：讲"为什么别的技术路线走不通"（用 refuted 子论点支撑 gap——有实验背书，不是 strawman）。
- **答复审稿意见的依据**：预判 reviewer 问"为什么不试 X"，refuted 子论点就是"试过，因 Y 不 work"的现成回答。

## 蓝图级自查（出 blueprint.md 前）

- [ ] **故事线一段读完，不看其他材料能讲清这篇论文吗？**（人读第一检查）
- [ ] **最有证据支持的核心贡献明确吗？**（一句话说清论文在哪个维度、场景或约束下贡献最明确；故事线、主结果、teaser 都围绕它组织；重点比较的维度有足够证据支持）
- [ ] 叙事主体无工作语言（C-ID / 对账术语只在对账字段）？
- [ ] 总论点立得住（方法名非 generic 词）？
- [ ] contribution 清单和论文准备材料创新点对得上？每个有验证路径（对账字段齐全）？
- [ ] 节清单过了四步程序（拆任务 → 按三项判据决定是否独立成节 → venue 对标）？每节有角色标注？该立的节立了、该并的并了？
- [ ] 每节叙事任务清楚（读者该相信什么 + 要点）？
- [ ] 页数参考量级记了（软约束：总量 + 参考分配，不做逐节硬预算）？
- [ ] 三位一体锁死（intro gap ↔ RW 定位 ↔ method 机制名 ↔ experiment 组件名）？
- [ ] refuted/abandoned 子论点规划进 RW 了？

## 蓝图更新规则（随工作进展更新的文档）

- **初建**于 op-2-design-story，用户确认后成为全文对齐基准。
- **行文级 drift 不回蓝图**：改句子、换例子、调段落顺序——随便改正文，蓝图不动。
- **实质变更必须回 design-story 重新确定提纲**：贡献变了（增/删/改 contribution）、故事线变了（总论点 / 叙事重心 / 首图意图改）→ 不许只在正文里拐弯，必须回蓝图重新确定提纲。
- **实测结果改变了最有证据支持的贡献也算实质变更**：将实验结果写入论文时发现比原叙事更强的卖点（或原证据最充分的贡献被数据证伪），主动回 design-story 换证据最充分的贡献/重排故事——不围着旧故事防守，故事服务于最强证据（正向触发见 op-5）。
- 重新确定提纲时：
  1. `blueprint_version` 递增，蓝图里留变更说明（变了什么、为什么）；
  2. **自动生成受影响章节的修改任务进 state 的 backlog**——哪些已定稿节被这次变更波及，逐节列修订项排队回改。**不许只改蓝图不排回改**（蓝图改了正文不跟 = 蓝图成摆设）。
  3. 更新后的提纲同样遵守「人读叙事在前」的写作纪律，故事线段同步重写。
- **write-section 发现实质 drift 当场标「蓝图脱节」**：写到一半发现正文要做的和蓝图说的不是一回事，不硬写也不悄悄绕开——当场标注，带回 design-story 裁决（更新论文提纲 or 收敛正文）。
- **audit 每次核蓝图↔成稿一致性**：op-7-audit 每跑一遍，都把已定稿各节和当前版本蓝图对一遍，脱节项进问题清单。

## 推荐起草顺序（非硬流程，按实际节清单裁剪）

```
定位节（锚定位）→ Introduction →（铺垫节，若有）→ Method → Experiment setup（结果待数据批回填）
→ Abstract（最最后）+ Appendix（随各节沉淀）
```

只是推荐顺序，理由是**内容依赖**：RW 先锚定位 intro 才好写 gap，Method 定了术语 experiment 才好对齐组件名，Abstract 压缩全文必须最后；铺垫节服务于 Method，排在它前面。依赖关系允许时（如 Method 图与 Experiment setup）可并行。节清单里有非默认节时，按同样的内容依赖逻辑插入合适位置。

## 输出

`blueprint.md`（`_draft/blueprint.md`）。op-3-write-section 写各节时 ref 它的故事线 + 总论点 + contribution + 每节叙事任务 + 首图信息意图。
