# 网络与镜像策略

本文件说明怎样在实际执行机器上检查依赖、数据和权重的下载路径，定位访问失败的原因，选择可复用的代理或镜像，并记录后续怎样继续。

`code-project-setup`、`code-paper-reproduction` 和 `code-idea-execution` 可共用这套流程。开始长任务前，先在实际执行的服务器、容器或计算节点上验证所需资源。登录节点和计算节点使用不同网络时，分别核对。各 skill 在本轮报告中记录实际采用的配置和结果。

## 1. 核对现有配置

先确认工作目录、执行环境、实际客户端和配置来源。下面的命令只报告变量和 Git 代理配置是否存在。变量已设置时，在本机核对其作用范围、代理地址和端口，报告只记录脱敏后的信息。

```bash
pwd
command -v curl git hf conda
for key in http_proxy https_proxy all_proxy no_proxy HTTP_PROXY HTTPS_PROXY ALL_PROXY NO_PROXY HF_ENDPOINT PIP_INDEX_URL PIP_EXTRA_INDEX_URL PIP_CONFIG_FILE CONDARC; do
  if printenv "$key" >/dev/null; then
    printf '%s is set\n' "$key"
  fi
done
if git config --get-regexp '^http(\..*)?\.proxy$' >/dev/null 2>&1; then
  printf '%s\n' 'Git proxy configuration exists'
fi
```

检查项目的环境文件、容器启动或作业脚本里是否覆盖了配置。通过 tmux 或调度器执行时，用最终的解释器、客户端和实际启动配置做一次轻量检查。远程机器上的 `127.0.0.1` 指向那台机器。若使用本地代理，先确认远程执行环境可通过已有配置连到代理，再探实际资源。

代理密码、令牌、含凭据的索引 URL 和带签名的重定向链接留在获准的本机私有配置中。共享终端输出、报告和日志前先去除这些值。定位配置来源时避免直接打印环境变量全集、Git 代理值和完整请求头。

## 2. 探测实际资源

站点首页可达只能说明站点本身有响应。优先检查计划里的**实际仓库、依赖版本、发布附件或数据和权重文件**。先记录仓库或包名、提交或版本、文件名和目标平台，再选下面适用的检查。

| 资源 | 探测方法 | 输出要检查什么 |
| --- | --- | --- |
| Git 仓库 | 用计划中的实际 URL 运行 `git ls-remote "$repo_url"`，按需指定分支或 tag | 能否读远端引用。要核指定 commit 时，再用待用的本地仓库或相应发布记录核身份 |
| HTTP 发布附件、数据文件或权重 | 用下面的限时探测检查实际文件链接和重定向。若服务不支持 HEAD，改用原下载客户端的元数据查询，或用已知很小的公开文件测试实际传输 | curl 退出码、HTTP 状态、是否重定向到文件服务。出现登录页时核授权状态。需要真正取得文件才能验证传输与内容 |
| Hugging Face 文件 | 用实际执行环境的客户端探固定版本与文件，例如 `hf download "$repo_id" "$filename" --revision "$revision" --dry-run`。数据集另加 `--repo-type dataset` | 仓库类型、指定版本、文件和大小是否匹配。dry run 查计划与缓存，文件传输仍待验证 |
| PyPI 或 conda 依赖 | 用实际环境的包管理器及选定索引或频道查询对应版本和构建。有锁文件时按锁定版本、平台、Python 和设备相关构建核对 | 版本是否存在、构建是否适配、解析过程是否选到预期来源。需要时在准备阶段下载实际构建并核落盘 |

对外公开、无凭据的实际文件 URL 可以用以下命令初查。变量 `asset_url` 填原始发布链接。curl 错误与 HTTP 状态分别记录。

```bash
curl --silent --show-error --head --location \
  --connect-timeout 8 --max-time 20 --output /dev/null \
  --write-out 'http=%{http_code} redirects=%{num_redirects} total=%{time_total}s\n' \
  "$asset_url"
```

收到 HTTP 错误响应时仍要看状态码。HEAD 得到 2xx 表示这次请求被接受，实际下载或加载还要单独核验。HEAD 返回 405 时改用客户端探测。私有或受限资源用已配置授权的官方客户端核查。命令选项见 [curl 手册](https://curl.se/docs/manpage.html)和 [Hugging Face 下载说明](https://huggingface.co/docs/huggingface_hub/en/guides/download#dry-run-mode)。

查询公开包源时，可用下面的命令列版本或构建。`setup_python` 指向计划采用的 Python，`index_url` 和 `channel` 为本轮选定的公开源。对照锁文件查看实际构建。索引中列出了版本时，仍需用实际环境核依赖能否解析、构建能否下载。

```bash
"$setup_python" -m pip index versions --index-url "$index_url" "$package"
conda search --override-channels -c "$channel" "$package=$version"
```

## 3. 按错误原因处理

| 观察到什么 | 下一步怎么查 | 何时重试或请用户介入 |
| --- | --- | --- |
| 域名解析失败、连接超时或代理连接失败 | 核失败发生在仓库、代理还是重定向后的文件服务。在同一执行环境复查实际地址、路由和代理设置 | 已定位到临时故障或有新的可用网络路径时再试。需要服务器网络权限时说明目标地址和影响 |
| TLS 校验失败 | 查系统时间、执行环境的信任链、代理提供的证书和客户工具使用的 CA 配置 | 有项目认可的 CA 或配置更正后再试。保持证书校验 |
| 401、403 或跳转到登录页 | 查是不是预期账号、资源访问许可、授权范围或签名过期。有些受限资源也会返回 404，需结合客户端错误判断 | 已有授权时用原客户端从原始资源地址重新请求。确需用户登录、申请权限或接受条款时指出操作与资源 |
| 429 或临时 5xx | 查服务端错误、等待提示以及客户端是否在重复请求 | 有等待提示时遵循提示。临时错误可有限重试并记录各次结果，多次无新信息时停止重复请求 |
| 文件不存在、镜像缺版本或构建不匹配 | 回查仓库类型、文件名、commit、发布页以及 Python、平台、依赖构建条件 | 能确认同一版本的官方文件或可信镜像时改用对应地址。换模型、数据版本或构建会影响实验含义时回当前 skill 审议 |
| 下载中断、大小或校验不符 | 查磁盘、文件完整性与断点记录，核是否下到了错误版本或错误页面 | 支持续传时沿用原版本、原路径和客户端的缓存。校验仍失败则保留失败记录，重新取可信副本 |

把具体错误摘要和受影响的任务写入报告。继续处理已有文件和不依赖该资源的任务，按依赖关系恢复受阻部分。

## 4. 选择代理或镜像并核资产身份

优先复用项目已确认可用的官方源、代理或镜像。需要更换时，先用实际客户端对固定版本或构建做轻量探测，再开始下载。公开镜像只在确认本次身份、版本、适用构建和访问条件后使用。受限资源的凭据按原服务授权范围提供。

将代理和镜像配置限定在单次命令、任务环境或项目配置。Hugging Face 客户端可在已核对的任务环境中设置 `HF_ENDPOINT`，pip 可按任务指定 `--index-url`，conda 则按项目锁定的频道与优先级选择来源。持久修改 shell、Git、pip 或 conda 的全局配置前请用户确认。tmux 或调度器的实际命令显式指定经过检查的环境和源。

下载后按原计划核实际版本、文件大小和发布方可用的校验值。包按实际平台和构建核对，数据按发布版本及划分核对，权重按模型配置和文件核对。下载完成后再按项目入口验证实际读取与加载。大文件按[长任务托管与恢复](long-run-ops.md)执行，保存日志与退出码。日志成功也要对照目标产物。

## 5. 记录受阻项与续做条件

每项记资源身份与目标路径、执行机器或环境、实际试过的来源、脱敏命令和错误、受影响的入口、下一步及负责人。只有已定位为网络问题且目前缺少可用路径时，使用 `blocked-by-network`。鉴权、版本或构建不匹配、完整性失败分别写实际原因。

确需用户处理时，说明需要哪项权限、网络条件或文件。可以提供可执行的脱敏命令、保存路径和版本。拿到结果后沿原记录核文件身份和完整性，再用实际入口验证，不重复准备已确认的部分。

## 示例 · Hub 首页可达，指定权重仍下不来

以下为虚构的 `edge-vision` 权重下载场景。实际使用时从发布页取项目自己的仓库、固定版本和文件名。

1. 在目标机器的 setup 环境核客户端和代理。Hub 首页有响应，实际权重下载报连接超时。用客户端检查发布页对应的模型仓库、固定 commit 和文件，dry run 能列出目标权重及预期大小。
2. 核实际下载日志。此例中目标机器可以查文件元数据，请求跳到文件服务后连接超时。将失败记为文件传输路径问题，保留目标服务的脱敏主机名。若实际收到 401 或 403，回查登录、访问许可和链接有效期。
3. 在目标机器使用项目已有且可达的代理，保持同一 commit 和文件，用实际客户端重新探测并托管下载。例如，将以下命令及已核对的任务环境放入执行计划。重连时先查原会话、日志和退出码。

   ```bash
   hf download "$repo_id" "$filename" --revision "$revision" --local-dir "$weight_dir"
   ```

4. 任务结束后核文件路径、大小和发布页给出的 SHA-256，再按 `edge-vision` 的实际配置加载权重。把来源、版本、校验和加载记录写入 setup 报告。若目标机仍无可用路径，就记录 `blocked-by-network`，继续准备其他资产。有授权的替代路径可用时，取得同一文件后回到校验与加载继续。
