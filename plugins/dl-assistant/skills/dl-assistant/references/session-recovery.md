# 恢复研究与执行上下文

本文件说明怎样在新会话或换机器后，核对当前研究版本、代码、运行和批准范围，并从已有证据恢复到正确的下一步。

开始或续做时，先用只读操作核对实际现场。新机器上的代码副本和原机器上的运行分别核实。恢复结论写回已有的报告、运行台账或交接记录。

## 1. 先定位项目、版本和当前任务

1. **从用户指定的项目与任务开始。** 用用户给出的仓库或版本目录定位。如果只知道当前工作目录，先确认 Git 根、实际分支、commit 与有影响的未提交改动。换机器时也记下机器名和工作目录，用来区分本地副本与实际运行所在处。

   ```bash
   hostname
   git rev-parse --show-toplevel
   git status --short --branch
   git log -1 --oneline
   git diff --stat
   git diff --cached --stat
   ```

2. **按当前任务找对应版本。** 有用户指定版本时先核该版本与仓库的关系。否则用当前分支、已有交接和版本记录共同定位。打开对应的 `01-idea-spec.md`、`02-research-plan.md` 和实际批准记录，确认当前命题、允许执行的任务、预算和停止点。首轮尚未形成版本目录时，查看上游交接里的实际草案及批准范围。后续轮查看 `00-from-previous-version.md` 和上一轮结论，弄清变了什么。
3. **再核已经发生的事。** 读本轮的 `claims.json`、`experiments/index.json` 和已保存的结论。按相关任务查实际 run 的代码、配置、数据、权重与原始观察。读取 `ideas/PROJECT_CONTEXT.md` 找稳定背景和上游指针。需要确认环境、基准或清理结果时，打开相应的 setup、reproduction 或 cleanup 记录；需要确认研究依据时，读对应文献或调研原记录。
4. **把下一步落到实际代码。** 从研究说明、本轮取证方案、映射记录或实际命令定位入口，打开当前版本的源码、配置及相关 diff，核实现或测量接入点。准备下一轮研究时，也核上一轮产生相关读数的代码和数据。

用下面的办法处理不一致。修改时间可以帮助定位文件，继续哪个任务要由文件身份、实际版本和批准记录共同确定。

| 发现什么 | 先核什么、怎样继续 |
| --- | --- |
| 当前分支是 v2，最近的日志属于 v1 | 从台账和 run 记录核日志绑定的研究版本、设计及实际 commit。v1 观察留在 v1，v2 从它已批准的任务续做 |
| 换机后新副本与原运行的代码或环境不同 | 分别记实际项目目录、commit、有效配置和环境。需要复用原结果时先核受影响条件。差异会改变关键比较时，带具体证据回审 |
| 报告、论点记录和原始结果不一致 | 核报告引用的 run、指标口径及实际产物，分开记录原先判断和新核实的事实。只更新有证据支持的范围 |
| 找到不同的方案版本或只找到部分批准 | 对照用户答复、批准的文件版本及实际任务。按明确允许的范围推进，把会改变目标、条件或投入的部分列为待确认 |

## 2. 到实际运行机器核长任务

从台账或报告取任务 ID、run 或尝试 ID、执行机器、工作目录、会话名或作业 ID、日志和产物位置。先查原任务。单机示例在原执行机器上运行，将会话名和日志目录替换为原尝试的值。

```bash
session=idea-edge-timing-01
log_dir=/srv/research/edge-vision/ideas/v1-edge-vision/experiments/exp-001-baseline-timing/runs/attempt-01
if tmux has-session -t "=$session" 2>/dev/null; then
    printf '%s\n' "找到原会话"
else
    printf '%s\n' "当前未查到原会话，继续核日志和退出记录"
fi
test ! -f "$log_dir/$session.log" || tail -n 30 "$log_dir/$session.log"
test ! -f "$log_dir/$session.EXIT_CODE" || cat "$log_dir/$session.EXIT_CODE"
```

集群任务用原作业 ID 查调度记录、退出状态及输出。会话检查和恢复命令见[长任务托管与恢复](long-run-ops.md)。

| 查到的状态 | 怎样恢复 |
| --- | --- |
| 台账写「运行中」，原会话或作业仍在 | 核确实是同一次运行及其最新日志、输出和阶段，按原任务继续监测 |
| 会话已消失，退出码也缺失 | 查原机器进程、调度历史、最后日志和已有产物。无法确定时保留「状态待核」，先解决这次运行的身份和进展 |
| 退出码为 0 或调度显示成功 | 核实际产物、预期记录数量和完整性，再回填执行状态。数据和测量的有效范围另按当前实验核 |
| 确认失败或中止 | 记录实际退出原因和可用结果。需要重试或恢复时，新建尝试，引用原尝试、checkpoint 及已验证的恢复范围。关键信息或授权变了，先核对应决定 |
| 无法访问原机器或产物 | 记录缺少的机器、作业、文件及影响。标明哪些独立工作仍可继续，哪些需要原记录才能决定下一步 |

用核实后的证据更新台账或报告。日志缺失、结果部分可用、执行结束但测量仍待核，分别记录。

## 3. 向用户汇报四项

| 汇报内容 | 要讲到什么程度 |
| --- | --- |
| **当前研究问题与依据** | 一两句说清这一轮想回答什么、要区分哪些解释。分别交代文献依据和本项目已有的观察 |
| **实际进展、测量质量和证据判断** | 说明什么已完成、什么仍在运行或受阻，数据能用到哪里。用 `evidence_assessment` 说清本轮证据对具体命题的影响及尚未区分的解释。总论点和研究贡献按[共享论点记录](claims-template.json)理解 |
| **正在用的代码、配置和基准** | 给实际分支、commit 或相关 diff、关键代码位置、基准 run 和当前配置。遇到原记录与现场不一致时，说明差异会影响哪一步 |
| **已批准的下一步与停止点** | 说清接下来准备执行哪项任务、剩余预算或资源、做到哪里回来汇报，以及仍需用户确认的决定 |

例如，换会话后要续做虚构的 `edge-vision` 项目。先核 D3 的批准范围和原机器上的 T0 日志、退出状态和计时结果，再按四项汇报：

> **研究问题** · 本轮先核目标设备上的稳定计时和轨迹采集对延迟读数的影响。
>
> **实际进展** · T0 已完成。固定的原模型和计时条件下，关闭轨迹采集三次为 12.5、12.6、12.7 ms，开启时为 15.3、15.4、15.6 ms。记录表明采集会影响这套条件下的计时。C1、C2 的正式机制对照仍待运行。
>
> **代码和基准** · 计时来自 `v1-edge-vision` 的基准尝试。以该 run 登记的 commit、命令、设备和有效配置为准，正式比较前仍要核实际算子身份。
>
> **下一步** · D3 只批准 T0，现已到停止点。建议正式计时和机制轨迹分开采。四组 T1 设计、隔离对照和预算仍需确认。

## 4. 维护项目背景与证据索引

默认位置是 `ideas/PROJECT_CONTEXT.md`。用[项目背景模板](project-context-template.md)记录项目级稳定信息：长期研究问题、已确认的目标会议或截稿、当前采用的基准身份，以及 setup、reproduction、cleanup 和调研资料的指针。首次缺少文件时，可以用已核事实补一份；现有记录足以定位任务时，先按记录恢复。

- 采用的新基准、环境或资产身份确实发生变化时，更新对应来源指针和简要说明。
- 用户与 iterate 确认调整研究方向或目标会议时，更新研究框架及依据。
- 已完成且会继续使用的调研或准备报告，可补入索引。核证据时直接打开对应记录。
- 当前轮的假设、批准范围、临时任务状态、执行结果和证据判断，写进本轮方案、台账、报告及论点记录。项目背景文件通过指针定位这些材料。
