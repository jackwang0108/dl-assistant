# plan 编写原则

> 写 `02-research-plan.md`（骨架见 `plan-template.md`）时遵循的原则。
> plan 有两半：**方法设计**（怎么做——研究决策，plan 的核心）+ **实验设计**（怎么验——证据工程）。本文件也按这两半组织。
> idea-find（v1）和 iterate（v2+）写 plan 时读；execution 读着理解 plan 为什么这么写（不据此改 plan——plan 对 execution 只读）。

## 上半：方法设计原则

spec 定「攻哪个子论点、赌什么方向」，并以**排除法**留下 2-4 个候选方案（见 idea-find / iterate 的方案生成手册）；plan 把**每个存活方案**落成具体可实现的方法，并组织实验赛马（下半「多方案赛马」）。以下每条都是 plan 里**每个方案设计节**的必填视角。

### 1. 设计选择显式化

方法的每个关键设计选择，写三样：**有哪些选项 → 取舍是什么 → 为什么选这个**。被否决的备选留痕（一句话写清为什么不选）。

这是 plan 里对论文最值钱的内容——method 节的「设计动机」段、rebuttal 的「为什么不走另一条路」，全从这里来。只写「用什么」不写「为什么、否了什么」的 plan，等于把研究决策丢了，只剩工程指令。

### 2. 单变量声明

本版相对上一版**只改一个主轴变量**，写死改了什么、其余冻结什么。一版改多个，裁决出来无法归因是哪个改动带来的——下版研究判断就失了据。确实需要组合改动时，必须配消融把各组件的贡献拆出来（见下半「消融」）。

**多方案赛马时**：赛马的「变量」是**机制选择**本身，各方案是这个变量的不同取值——声明写「本版只动机制选择这一轴，其余全冻结」；每个实验内部仍一次只动一个变量、同设置对比，归因依然干净（详见下半「多方案赛马」）。

### 3. 最小侵入 baseline

改动面最小化：写清**接入点**（改哪个模块 / 函数，概要；详细 file:line 在代码指引节）、新代码和 baseline 的边界。改模块前查在不在训练热路径上（在 → 实现方案要把开销算进复杂度预算）。不顺手重构、不顺手「改进」无关代码。

### 4. 复杂度预算

每个新增组件必须挣回它的复杂度：预期收益要抵得过「实现成本 + 调试成本 + 论文里讲清它的成本」。**删代码能持平也是赢**——更简单的方法达到同等效果，本身就是贡献（论文更好讲、后续更好迭代）。方案设计时主动问一遍：哪个组件能去掉？

### 5. fallback 预写

主方案的已知实现风险列出来，每个风险预写**降级 / 备选方案**（如「X 机制若在我们的 backbone 上梯度不稳 → 退到 Y 近似」）。execution 卡住时按 fallback 走，不临时拍脑袋改方法——临时改的方法没有经过 spec/plan 层的研究判断。

### 6. 实现自由度边界

写清哪些设计决定是 **plan 锁死的**（execution 不许动：机制、公式、架构改动、数据用法），哪些是 **execution 可自主的**（工程实现细节：显存优化、并行策略、不语义等价的重构之外的选择）。边界不写清，execution 要么缩手缩脚要么自由发挥，验收时对不上。

## 下半：实验设计原则

> execution 是**方法开发迭代循环**，不是出 paper 数字的环节——用 reduced 规模、单 seed、快反馈判断方向；full 规模 / 多 seed 出 paper 数字是论文实验阶段的事（`code-paper-experiment`，idea 阶段不管 full-scale / release）。

### 1. 双源驱动：claim + 方案风险点

**主轴：claim → 实验。** 每个 claim 想清楚"它要什么证据"，再设计能产出该证据的实验，把这对关系填进实验总览表（claim ↔ 实验、可证伪 / 可测）。例：C1"refinement 提升 cIoU" → 主训练实验（refinement vs baseline，同设置比 cIoU）。

**第二源：方案风险点 → 实验。** 方法本身的未知点也要实验 de-risk——「这个机制在我们的 setting 里能不能实现」「哪个组件是关键」「接入残差后梯度是否健康」。这类实验不直接验 claim，是给 claim 探路，总览表里标清是 de-risk。方案设计节的「预期工作原理」（补上缺口后哪个中间量怎么变）也在这里长成诊断实验——方案与实验的咬合点。

### 2. 所有实验都守的开发约束

- **reduced 规模快速迭代**：用 `code-paper-reproduction` 交付的 reduced 配置（~3h vs full ~3 天，继承 full baseline 可信度）、**单 seed**、快反馈。reduced 上稳定的 +X% 是有效方向信号（趋势保真，不要求数值精确）。**别用 full / 多 seed 烘进每次实验**（3x 成本拖慢迭代）；只在某结果 borderline（单 seed 分不清真本事还是噪声）、需要确认才能继续迭代时，临时多跑 1-2 seed 消歧。
- **可比性地基**：在同一 reduced 设置下对比 reproduced baseline（reduced baseline 已和 full 趋势对齐过）——验收审的就是这个。
- **最小必要**：每个实验必须服务某 claim 或某 de-risk / 解读条目；不服务任何 claim 的砍掉（实验总览表查"无主"实验就是这条）。
- **便宜先行**：能回答同一问题，优先设计便宜的实验（诊断优先于主实验、reduced 优先于放大）。先探路 de-risk 再跑贵的。

### 3. 合格的每实验原理（判据）

plan 里每个实验的「原理」节（骨架见 `plan-template.md`）必须含四要素，缺一就是没想清楚：

1. **变量是什么**：本实验隔离哪个变量（一次一个），其余条件冻结。
2. **为什么这个设计能隔离它**：对照组是谁、为什么说观察到的差只能归因于这个变量。
3. **预期信号长什么样**：成功看到什么**具体**信号（metric 升 ≥ X、某分布出现、曲线形态变化）——可测、有量。
4. **什么结果会证伪**：失败信号 + **到什么程度算没通过** + **判据三问**（①验什么假设——机制链：假设不成立 → 为什么这个量会呈现这个信号；②阈值来历——noise_floor 的几倍 / 论文消融幅度 / 量级估算，允许粗；**没有先验时允许只写方向性预期（如「曲线应上升」），但必须显式标注「无先验」**；③命中意味着什么——**支持哪种解读、嫌疑落在哪层（执行 / 设计选择 / 机制前提）、后路建议**——命中永远不直接判死 claim，claim 生死归 iterate + 用户验尸后拍板）。光写「< 0.3 点判死」不讲推导，用户在确认点只能点头不能审——三问就是给用户的审查抓手。

**预期承诺纪律**：四要素在**跑实验前写死**，之后不改。验收对照它裁、iterate 对照它判——没有预先承诺，任何结果都能被事后解释成「符合预期」，研究判断就烂了。预期要调，只能在下一版 plan 里调（留变更记录），不在结果出来后回头改。

**好示例**（完整四要素）：

> exp-002（验 C1「refinement 提升 cIoU」）：变量 = refinement 模块开/关，对照 = 同 reduced 配置、同 seed 的 reproduced baseline，其余（数据/schedule/lr）全冻结——观察到的 cIoU 差只能归因于 refinement。成功信号：reduced 上 cIoU 提升 ≥ 1.0 点（>> 单 seed band ±0.3）。证伪：提升 < 0.3 点（噪声内）→ C1 无证据；负提升 → 检查机制再判。

**反模式**（验收和 iterate 看到就打回）：

- **「跑 X 看效果」式无原理**："跑一下新模块看 metric 涨不涨"——没有变量隔离（baseline 不同设置）、没有预期量、没有证伪线，跑出来任何数都能自圆其说。
- **「因为 SOTA 这么做」式无验证逻辑**："X 论文这么加了有效，我们也加"——移植的是做法不是证据，没回答"它在我们设置里凭什么 work、怎么算 work"。

### 4. 辅助实验（按需加，不是每个 claim 都要）

- **诊断探路**：先设计便宜的诊断实验探路，de-risk 再跑贵的。诊断不直接验 claim、是给 claim 探路，映射表里标清是 de-risk。
- **消融**：方法多组件时，每个组件配消融（reduced 规模，去掉它看效果），验"哪个组件起作用"的子 claim——也是单变量声明的归因保障。
- **分桶 / 分析**：次 claim（如"小目标提升更大"）配分析实验（分桶算增量）。

### 5. Phase 怎么分

实验设计好后，按四原则分到 Phase：

1. **依赖**：诊断 gate 主实验、主实验 gate 消融、方案 A gate 方案 B 叠加——前面结果决定后面要不要跑。
2. **聚类**：一组紧密相关的实验（围绕一个 claim 或一个方案链路）归一个 Phase。
3. **早期信号实验前移**：spec §4 失败解读表涉及的实验排早期 Phase，快速暴露、不行早停，别烧完 GPU 才发现地基不对。这是资源保护——早期信号命中 ≠ 判死，只触发解读表对应行。
4. **每 Phase 一个 checkpoint**：Phase 跑完在一个决策点收敛（继续 / 停 / 调），用户在 execution 的 Phase checkpoint 拍板。

常见形态（按 spec 调，只是参照不是公式）：前置检查 → 核心假设 + 关键诊断（含失败解读表条目）→ 深化（消融 / 分桶 / 次 claim）→ 叠加扩展 → 总结交付。多方案赛马时按「多方案赛马」的节奏分。

### 6. 多方案赛马（spec 排除法留下 2-4 个方案时）

候选阶段人和 agent 的判断都靠不住——值得一试的方案交给实验裁决。赛马的组织原则：

1. **协议统一**：所有方案共享对照协议（同 baseline / 同 reduced 设置 / 同 seed / 同 metric——plan 的「共享对照协议」节跑前写死）。方案间唯一的差别是机制本身，否则赛出来的差异无法归因。
2. **早期信号前移**：每个方案先跑**最早能暴露失败模式的便宜实验**（spec §4 方案级解读条目 + 方案设计里的「死法+最早发现」），明显不行的早停——不全量烘每个方案，早期信号实验便宜，赛马才划算。
3. **资源随淘汰聚焦**：早期信号 Phase 过后，主实验只跑存活方案；消融 / 深化只配给赢家。输家暂停投入——**淘汰 = 暂停，不是判死**：iterate 复盘时可凭新证据复活；**输法和早期信号结果留痕**（进 conclusion + 下版 00-from-previous 的否决备选）——这是论文 rebuttal 的素材（"we tried X/Y/Z"）。
4. **赢家判定预登记**：跑前写死怎么算赢（哪个 metric、阈值——如 > baseline + 2×noise_floor，**阈值来历一并写清**）；**平局用简洁性判据决胜**（持平选简单的）。不跑完再挑好看的数。
5. **claim 是方案无关的**：「高频能提 cIoU」由赢家方案的实验证据支撑；方案被淘汰不是 claim 被裁决（方案淘汰 ≠ 子论点 refuted），所有方案都跑不出效应才轮到子论点级解读条目——而它触发的也是验尸，不是直接判死。

**典型节奏**：Phase 1 全方案判死实验（+ 共用诊断：验缺口 / 前提，不分方案）→ Phase 2 存活方案主实验（同协议对 baseline）→ Phase 3 赢家消融 / 深化。

### 7. 实验类型

- **training**：训练实验（主结果、消融、叠加都用它）。
- **diagnostic**：诊断实验（探路 / de-risk，不验 claim）。
- **ablation**：消融（去组件看效果）。
- **analysis**：分析（分桶 / 可视化 / 二次指标）。
