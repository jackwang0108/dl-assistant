# 本轮取证方案编写原则

本文件说明怎样把要减少的未知写成可执行的取证任务，选对照、规模和重复，并在投入前写清不同结果会怎样改变判断。

按[取证方案模板](plan-template.md)保存。idea-find 和 code-idea-iterate 负责研究设计和交审。code-idea-execution 核实际入口、实现和测量，按获批方案实施。发现设计落不到实际条件时，带上具体证据和调整建议回研究审阅。

## 1. 让关键未知决定任务

逐项讲清「要分清什么 → 为什么这个设计能分清 → 每个对照有什么作用 → 看见不同结果会怎样判断」。先核已有证据能解决多少，再选择足以改变决定的行动。方案数量由未知和可接受的投入决定。

| 要弄清什么 | 任务可以怎样开始 | 写清本次能回答到哪里 |
| --- | --- | --- |
| 环境、入口、测量或分组能否满足要求 | 用准备或诊断任务核实际配置、已知答案、测量范围或回退行为 | 验收的是哪个前提，正式检验还缺什么 |
| 现象在哪里出现、是否值得提出新假设 | 限定探索的数据、观察范围、指标、分析办法和预算 | 保留筛选过程、意外观察和停止条件。写明新假设从哪批数据产生 |
| 哪个解释更符合观察 | 用确认性比较写明相互可区分的预测、必要对照和事先定好的解释规则 | 哪些条件和观测支持、削弱或仍无法区分解释 |
| 已有结果能否回答当前问题 | 追原始读数、代码及条件，核哪些历史样本和运行可以比较 | 哪些数据已用来提出假设，哪些能独立核查，复用限制是什么 |

探索和确认都可以使用现有数据。复用产生假设的数据时，把选过的条件、指标或模型写清。需要判断能否重现时，安排尚未用于选择结果的样本、运行或其他独立证据。只验准备条件时，关联研究问题及后续前提。

## 2. 核实际对照、规模和重复

- **把比较写到能实查。** 列每组改变什么、保持什么、怎样从配置、日志、数据清单或实际执行路径确认。对照需对应具体的替代解释。单项干预适合检验一个可独立改变的因素。需要估计组合或交互时，按问题补组合组、析因设计或独立测量。若因素跟着一起变，写清组间比较还能回答什么。
- **按研究对象选规模。** 说明小规模、短训练或局部检查能否保留目标现象和关键条件。用 reduced 时引用实际档位、基准 run、各档条件和已有配对证据。先写哪些观察会触发升档，以及升档会补哪项证据。仅有小档结果时，将解释限在已测条件。跨规模比较按[低成本配置核查](../../code-paper-reproduction/references/reduced-setting.md)核同一个改动相对同一个基线的变化。
- **先定义什么算一次重复。** 例如独立训练、独立设备会话、配对输入或同次运行里的多条请求。分别记录样本波动、运行间波动和测量误差，用它们决定重复对象、次数和配对。共同 seed 可帮助配对，但还要核初始化、数据、运行及指标条件。单次试跑可核入口或测量能力，估计跨运行波动时要有相应的独立重复。恢复和重试保留原重复身份。
- **在看结果前写追加规则。** 按已有波动、所需精度、预算或阶段目标决定何时停止与何时加测。记录无效运行的处理和汇总规则。若结果已影响后续取样、模型选择、指标或调参，保留过程并交代对解释的影响。

## 3. 让判据能解释观察

先写验哪个预测或前提、从哪个读数判断，再写判据依据。区分测量精度、实测波动、统计不确定性以及研究上有意义的差异。已有基准只在可比条件下使用。没有足够依据定数字时，先核读数质量或写方向性预测及限制。

| 看到的情况 | 在 plan 中预先写清 |
| --- | --- |
| 有效读数符合预测 | 支持的是哪个命题、哪些条件下的判断，以及还有什么解释 |
| 有效对照与预测相反 | 哪部分假设或边界需要重审，哪些前提仍需核查 |
| 差异小到现有数据无法分辨，或两个解释都能产生该读数 | 当前未决的具体问题，以及何时值得补独立重复或追加对照 |
| 对照不成立、测量失效或运行受阻 | 受影响的比较、可保留的观察、修正后才能重开的任务 |

早期异常可以触发检查或暂停投入。命题判断须看实际对照和读数。结论分别记录执行、测量和证据判断，保留反例、偏差和意外观察，注明剩余未知。

## 4. 把设计写到可实现、可审核

涉及方法改动时，写接入点、预期改变的中间量、与基线的边界。对关键选择说明备选、取舍和依据。有先例时，核原文的前提是否适用。说明额外的运行、实现和调试成本。若简化方法本身是研究目标，写清等效范围及要测的成本。遇到已知风险，把最早可检查的信号、获批的备选实现及使用条件写进对应任务。

审阅时从关键输入或配置追到实际代码路径、测量输出和统计汇总。注明各步怎么核、哪些需试跑、哪些需用户看实际 diff。代码入口未确认时，先写应核的模块、输入输出和确认方法。核对实际入口后再绑定命令。[执行工作流](../../code-idea-execution/references/workflow.md)说明如何登记设计、运行和尝试。

## 5. 用真实依赖安排投入与交接

1. **先安排能省去无效投入的检查。** 说明哪项后续任务依赖哪条读数、检查或批准。成本引用实际运行、实测吞吐或资源记录。把预计用量和批准上限分别写清。可独立取证的任务按已批准范围继续。
2. **写好每个停点。** 任务到验收点、遇阻或用到上限时，汇报实际观察、影响的比较、已用投入及下一项建议。有效反证、未能区分解释或只核清准备条件都可以是本轮产出。
3. **保留原设计和修订。** 写清哪些工程调整已获授权、怎样核结果仍可比。影响假设、方法语义、数据、测量、统计或投入的变更，说明影响并按范围交审。保留原批准稿的 Git commit 或固定副本，并记变更的时间、理由、受影响任务和实际批准。当同轮新增任务时，为该任务登记明确的 slug、plan 修订及来源决定。执行记录绑定运行时使用的方案。
4. **回到研究问题。** 结论要能回查原先相信什么、实际观察和限制是什么、还有什么未知。问题收窄后重新说明还能回答什么、相对已有工作增加什么。下一轮由 iterate 结合实测结果和用户决定。

## 示例 · edge-vision 从测量核查到配置比较

baseline-timing 先核同一原模型、设备和输入下有无轨迹的逐次延迟。三次请求的读数用于检查计时和采集的影响，读数都来自同一准备任务。baseline-timing 的观测表明采集会改变延迟，因此正式计时关闭轨迹，机制信息另采。baseline-timing 到已批准的准备边界即汇报，四组比较的实际配置、成本和重复方案留给 configuration-comparison 审阅。

configuration-comparison 若得到有效的配置读数，可以回答目标条件下组合是否更快。若写回量和实际算子同时变化，结果只支持配置层面的比较。下一轮若要检验 C1，先确认固定实际算子时仍能保持目标条件，再决定能否建立改变写回量的对照。[首次取证示例](plan-template.md#完整填写示例--edge-vision-的计时和轨迹核查) · [configuration-comparison 实测结论示例](../../code-idea-execution/references/execution-conclusion-template.md)

同轮只补前置条件时，保持研究问题与已有命题，给新增诊断单独写获批范围及停止点。[同轮补证示例](plan-template.md#同轮补证示例--核固定算子分派)
