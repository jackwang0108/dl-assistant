# 论文预审与修改复查流程

本文件说明怎样固定审查材料、组织评审、核实问题的证据，以及把本轮意见交给作者处理。

## 1. 确认稿件、模式和评审标准

1. 从用户给的文件或已确认的写作交接开始。自己的论文优先用显式指定的论文根，其次核当前目录的主 TeX 与 `_draft/`，或 `papers/` 下的候选。候选不唯一时列出路径和版本请用户确认。外部文件按标题或用户指定名落到独立归档目录。
2. 核 PDF 是哪一版。用户给 Overleaf 项目时，按 [Overleaf MCP](../../overleaf-mcp/SKILL.md) 用 `overleaf_projects` 核项目，`overleaf_compiles` 和 `overleaf_compile_report` 核编译身份与日志，再用 `overleaf_download_output` 取选定编译的 PDF。草稿审查记录实际可见的章节和缺少的图表、附录。TeX 源稿涉及多个文件时固定相关依赖版本并列入材料。
3. 作独立预审时只提供本轮声明材料。修改复查先核旧问题清单、新稿、回应或实际差异，并登记要核的旧问题 ID。材料或任务范围变更时建新轮，历史轮次保留。
4. 目标已知时，核官方网站当年、轨道和审查阶段的评审说明、领域列表、评分定义和作者包。记录来源、实际读取位置、日期及适用范围。目标未定时可做一般内容预审，也可以结合稿件提出候选由用户确认。若只找到往年标准，把来源和限制写明，本轮按一般准则审查该项。
5. 按[运行记录](run-contract.md)和[运行记录模板](templates/review-run-template.json)写 `review-run.json`。示例使用当前会话审查，具备实际隔离条件时据实填写。用文件真实摘要绑定材料和本轮记录，可用 `shasum -a 256 "$paper_path" "$review_dir/review-run.json"`。输入或权限受阻时，先核阻塞会影响什么。只做有限检查时，把缺失材料和受影响判断写进准备检查。

## 2. 安排评审并逐项取得依据

按主要风险分配检查重点。例如新模型先核公平对照和相关工作，系统论文查测量边界与适用条件，理论论文查假设、推导和结论范围。多位审稿人仍各自理解全文，可用 [专长档案](pool/leanings/) 和 [检查视角](pool/philosophies/) 选取侧重。可另设反证任务检查最有力的替代解释，或设合规任务核适用官方要求和实际 PDF。按已获授权和宿主能力安排，记录每个任务所见材料、实际隔离状态和限制。

每个任务先写对贡献的理解，再按下列步骤检查：

- **核正文与图表。** 用 [PDF MCP](../../pdf-mcp/SKILL.md) 的 `pdf_open` 得到固定快照，`pdf_read` 读关键位置。图表先定位对象，必要时用 `pdf_render` 核原页或区域。结论与方法或表格矛盾时同时记两处。图表看不清时，标为未核实并写明缺哪一页或哪张图。
- **核新颖性和可比性。** 从具体主张拆出方法、任务和比较设定，用 [paper-search](../../paper-search/SKILL.md) 查最接近的工作，必要时沿引用核前序工作。对最相关来源打开原文并记录已读部分。比较研究问题、假设、预算或数据与实际结论，分别记查询、来源、阅读范围和限制。
- **核缺项和严重程度。** 查与该主张相关的正文、表注、实验设置和补充材料后，记录已查范围及没找到的信息。先判断当前依据支持什么，再说明若问题成立会影响什么。使用[问题清单示例](problem-list-schema.md#示例同预算比较)，逐条保存到任务 JSON。支持论文的证据和未决问题都保留。

宿主能执行 [paper-review.js](../workflows/paper-review.js) 时，给它 `run`、实际 `runSha256` 和 `reviewDir`。各任务完成后保存 `tasks/<task-id>.json`，协调者保存完整的 `workflow-result.json`，并核任务文件确实写出。手动组织或共享上下文时，用相同文件记录实际过程和限制。

## 3. 核综合结论与修改复查

待评审任务分别形成意见后，由综合者读取原意见和本轮材料。对重要意见定位原证据，逐条记录纳入、合并、排除或待核实及理由。合并时保留来源，排除时保存实际核查依据。存在分歧就写清各方依据、可判定的部分及还需什么信息。同一稿件上的多数意见只能提示重点。评分采用已核实表单的适用维度，记录分数依据和无法判断的地方。

修改复查逐条对照旧意见、实际修改与新稿证据。比如旧意见涉及测量预算，复查先看新稿是否补充预算口径及设置来源，再核对是否真的能支持同预算比较。分别登记已解决、部分解决、未解决或未检查，并记录新发现。

## 4. 验证交接并汇报

```bash
python3 "$skill_dir/scripts/check_review.py" \
  --run "$review_dir/review-run.json" \
  --workflow "$review_dir/workflow-result.json" \
  --output-dir "$review_dir/handoffs/rev-1"
```

退出码 0 表示计划内任务已完成且记录检查通过；1 表示内容或引用错误；2 表示参数错误；3 表示可交接的阶段结果。按计划直接交付单份审稿意见时可以返回 0，`synthesis_status` 记为 `not_planned`。核查得到的引文、图像和科学判断仍按原材料确认。

例如第一次审稿已返回，计划内的综合任务中断，先将阶段结果保存到 `handoffs/rev-1/`。恢复时核对原 `review-run.json` 摘要、任务文件和编排返回。传给编排的 `resume` 对象只保留文件与内容都核对一致的成功任务。综合完成后用同一条命令，把输出目录改成 `handoffs/rev-2/`。每次交接的清单都指向本次 `records/` 的固定副本，可分别回查当时的任务、稿件和依据。

向用户说明主要贡献、最影响判断的问题、分歧及未完成范围。给 response 本轮 `problem-list.json` 的确切路径和稿件校验值；有综合记录时同时提供。核心现象、贡献或目标条件下的效果尚未确定时，指出涉及的主张、已有证据和缺项，建议交 iterate 讨论。明确的文字或补充证据需求由 response 与用户定方案后交 writing-paper。
