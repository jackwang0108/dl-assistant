# Baseline Survey 运行手册

本文件说明怎样把本轮研究或复现目标转成可核查的必要条件，用论文、源码和社区记录比较候选，并把选择和实测待办交给后续准备与复现。流程对应 [SKILL 运行图](../SKILL.md#运行流程图)。

## 开始或续做

先使用用户提供的论文、仓库和上游文件。已存在本轮报告时，核对所选版本、原结论依据、仍待核的条件和用户决定，再从相关步骤继续。只补问会改变推荐的缺失条件。目标会议、设备规格或精确预算尚不明确时，记录未知及影响。

| 续做时发现什么变化 | 从哪里继续 |
| --- | --- |
| 目标设备、待测指标或比较协议变了 | 回 Step 1 更新受影响的必要条件，再复核引用这些条件的候选 |
| commit、模型权重、数据版本或划分变了 | 回 Step 3 核有关接口、加载兼容性和协议，标明原判断是否仍适用 |
| 原条件和候选证据仍适用，用户尚未选定 | 从 Step 4 继续比较和讨论，补会改变推荐的证据 |
| 选型已确认，版本及条件无变化，只剩实际验证 | 从 Step 5 核对原 clone 卡与实测待办，直接交对应下游继续 |

有变更时记下旧判断、新依据和受影响的条件。原来的选择仍适用时，复用其余核查结果。

## Step 1 从目标提取必要条件

| 入口 | 读取和记录什么 |
| --- | --- |
| 已有 `idea-find` 交接 | 按[研究交接说明](../../idea-find/references/research-handoff.md)读取研究说明、取证方案和批准范围。提取本轮需要的读数、干预或比较、任务、模型、数据、测量和资源条件。草案中的仓库 URL 用作线索 |
| 用户直接复现或选型 | 复现时明确目标论文、版本、实现、配置、数据与表格行。选型时明确预期用途、需要取得的结果和已知约束。已指定仓库时先查该仓库的适配性和风险 |

给必要条件编号，例如 R1、R2，并记清来源。区分必要条件、偏好和未知。每条要求写到这一层。

| 要求 | 为什么必须保留 | 什么证据算满足 | 改变它会影响什么 |
| --- | --- | --- | --- |
| R1 在目标设备上以批大小 1 测输入到分类结果的延迟 | 本轮要核单张请求的整体响应时间 | 源码和配置能定位计时起止及批大小。是否能在目标设备按该口径取得读数留待实测 | 改成批量吞吐或子图计时，会改变所回答的性能问题 |

条件可包括目标硬件、输入形状、模型、数据划分、对照、测量接口、训练阶段、指标和使用许可。纯复现时把要求关联到目标论文版本、配置、结果表格行、数据和指标定义。只需验证特定测量时，先查相关推理和测量路径。若核心比较还没有定义，明确当前只查准备条件，或回 `idea-find` / `code-idea-iterate` 澄清。

## Step 2 找候选与合理替代

- 优先核查用户或草案提供的真实线索。用 GitHub 仓库搜索、Hugging Face 项目或模型记录，以及论文、项目页和作者链接找合理替代。按用途记录论文官方实现、第三方实现、框架或测量工具。
- 核对候选 URL、与论文或作者的关联、拟检查的 commit 或 tag，记录搜索范围及纳排理由。名称相似、star 数或自称官方只能作为查找线索。
- 候选数量随相关性和调查目标决定。可以只有一个合适候选，也可以暂时没有。一个仓库可同时承担多个用途；需要组合时记录每个组件负责什么，后续一起核对接口和协议。用户已经选定仓库且只要求核风险时，围绕该仓库调查。

找不到完整实现时，按 [paper-search](../../paper-search/SKILL.md) 核论文身份，优先用 [tex-mcp](../../tex-mcp/SKILL.md) 的 `tex_open`、`tex_search` 和 `tex_read` 查实现来源及上下文。源码无法取得时，可用 `download_paper_asset` 获取论文材料，按 [pdf-mcp](../../pdf-mcp/SKILL.md) 定位相关文字或图表。记录论文明确说明的源仓库、与目标实现的差异、改造范围和未知。核心方法要重新实现或比较条件发生改变时，回到研究设计讨论。

**何时结束候选搜索。** 已有足以进入详细核查的候选、定向扩展很难改变候选范围，或已到约定预算时，收束搜索。记下查过的来源、仍缺的仓库角色或必要条件，以及未覆盖范围。详细核查发现所有候选均不匹配，且仍有合理的补查方向时，带着该条件回本步定向找替代。

## Step 3 先核适配性，再核工程条件

先逐项对照 R 编号，记录「有静态证据支持」「明确不匹配」或「待核」。关键条件有问题时，说明它会阻碍哪项测量或比较。适配性可以从固定版本的文件树、配置、代码调用关系和论文协议核对。例如，要判断仓库是否能采集某个中间量，应沿入口追到采集接口及输出。仅在 README 见到声明时，记为文档声明，并指出需要核实的代码或实际行为。

| 工程项目 | 具体查什么 |
| --- | --- |
| 代码质量与可接入性 | 在同一个 commit 或 tag 打开依赖清单、相关入口、配置和关键模块。按任务梳理实际需要的推理、评测、数据、测量或训练路径，写到 `文件:函数`。列扩展点、关键依赖、资源要求和改动范围。标明静态判断 |
| 权重与许可 | 核模型或权重标识、版本、配置、来源、公开或申请条件及代码对齐情况。记录权重与代码各自的许可出处及限制。链接可查看只说明当前访问状态，加载由准备阶段实测 |
| 数据与协议 | 核数据版本、划分、获取条件、许可、预处理、输入、指标定义及版本。目标是复现时，将参考数值关联到原文位置、模型、配置和协议；来源是维护者报告时也照实标注 |
| 社区复现记录 | 查 issue、discussion、PR 或独立复现报告。记版本、环境、数据、结果、解决状态和链接。重复转述按同一来源处理，缺少公开报告时标未知 |

详细检查项见[四项工程核查](due-diligence.md)。只查与本轮用途有关的调用链。源码核查用 GitHub MCP 等可用工具读取真实文件与版本，也可读用户已提供的代码和结果。文档声明、源码和配置、社区经历和本项目的实际运行记录分别标注。本阶段通过阅读取得材料和证据，仓库及实验资产的获取、安装和运行交后续阶段。

**证据出现冲突时。** 先核对是否指向同一仓库版本、配置、权重、数据、设备和测量口径。不同条件的记录并列保存，说明各自适用范围。条件一致时，沿实际入口追到对应代码，并写清原声明和所读实现的差异。例如，README 声称支持端到端计时，所核入口却只包住单个子图，就给出计时代码和配置的位置，写明这条入口能确认什么、端到端入口是否仍待核。需要运行才能区分时，列为具体实测任务。

需要分工时，发起前向用户说明数量、任务、候选及具体版本、必要条件、要查的文件、独立输出路径与理由。结果按[事实记录模板](fact-record-template.md)保存到 `facts/<候选>-<核查项>.md`，包含已查文件和位置、结论、未知与实测待办。主会话核对冲突后合并记录。

## Step 4 比较候选，给出有条件的推荐

从必要条件、证据和成本出发给建议。明确不匹配的条件应写进排除依据或返回研究设计。关键条件能靠有限准备验证时，可以建议先测，再决定是否投入。对组合方案逐项核接口、模型配置、数据身份与许可。注明接入成本来自哪些模块、依赖或资源，未知处留待实测。只看到一个合适候选时说明为什么，暂时没有合适候选时写清需要补查、调整资源还是重议设计。

| 推荐结论 | 怎样给出依据和下一步 |
| --- | --- |
| 推荐进入准备 | 关键条件有可追溯的支持，剩余未知可在常规准备中检查。说明适用用途，以及哪项实测不符时要重新选型 |
| 推荐先做有限验证 | 有一项关键未知会改变选型，且可以用范围明确的准备任务核实。写清为什么优先验证该候选、在哪个条件下测、什么结果会保留或撤回推荐 |
| 暂无可推荐候选 | 说明关键条件不匹配或缺乏可验证依据。提出最值得补查的来源、资源条件或需返回讨论的设计问题 |

向用户报告「为什么推荐、最关键的未知、什么结果会改变推荐」。如果只适合某一用途，明确推荐适用于哪一步。

完稿前检查三件事。必须保留的条件是否都得到实际依据或标为未知？关键判断是否能回到具体版本和原文或文件？每项实测待办是否会改变某个明确决定？按[报告与交接模板](report-template.md)写出候选对比、推荐、已知风险和足以复查的依据。用户初选、上游线索和 agent 推荐可以不同，写明差异的原因。

## Step 5 记录用户决定，交接准备与复现

用户确认后写入 `decision`，并在报告中附 clone 卡。卡上记录仓库 URL、确认的 commit 或 tag、用途、权重、数据版本与划分、指标协议、参考结果及已知风险。当前结构化交接保留 `decision.repo` 和 `decision.repo_role`。若实际选型含多个组件，报告和 clone 卡列清每项组件的版本与用途，交接时说明现有机读入口指向的主要仓库及额外依赖。未确认选择时保存结果和待确认事项。

每项实测待办附当前证据和关联的必要条件，在报告及 clone 卡写清「谁负责｜保留哪些条件｜如何观察｜满足什么可以继续｜不满足回哪里」。例如，由 `code-project-setup` 核实权重加载、运行入口和目标设备接口；由 `code-paper-reproduction` 在约定版本、配置和协议下核相应参考值。新科学对照按已确认的取证设计交 `code-idea-execution`。入口未运行时标为候选入口。实测与静态判断冲突时，先核版本和条件，再保留新证据和原判断的变化依据。

## 交接示例 · 单张视觉请求的基准核查

以下用于说明取证条件怎样决定推荐。候选和核查结果均为假设。

### 需求与候选证据

读取 `idea-find` 的批准范围。本轮只做 T0 基准核查，正式四组实验待确认。对比两种候选实现。

| 要求 | 候选 A 的已查证据 | 候选 B 的已查证据 | 怎样影响推荐 |
| --- | --- | --- | --- |
| R1 目标设备上，以批大小 1 测输入至分类结果的延迟 | 固定版本的 `tools/infer_one.py:main` 和配置可定位批大小及计时起止 | README 写支持推理计时，所核 `bench.py:profile_subgraph` 按批只计子图，目前未核到单张端到端入口 | 优先在目标设备核验 A 的计时入口。B 的已知入口无法回答 R1 |
| R2 取得写回量与实际算子实现的轨迹 | 文档提到轨迹接口，目标设备能否取得这两个字段仍未知 | 只查到子图吞吐和耗时记录 | A 只能给有条件建议。轨迹能否取得及是否扰动计时会改变选型 |
| R3 使用约定的模型权重及验证集版本 | 资产页面和配置能定位版本及划分，加载待测 | 权重与数据配置有出处 | 两者均需按实际用途核版本和加载。B 的资产齐全仍无法补足 R1 |

**向用户给建议。** 建议先用 A 做有限准备验证。它有单张端到端入口的源码依据，轨迹能力仍未知。若指定版本无法稳定取得所需字段，或采集显著干扰计时，就排查可独立采集的方式或重新比较运行时，先保留机制取证的未知。

### 用户确认后的实测待办

假定用户确认用 A 做 T0。clone 卡记录 A 的仓库路径、检查过的 commit、模型权重、数据版本和划分。报告附下列待办。

| 谁负责 | 保留哪些条件 | 如何观察 | 什么结果可以继续 | 不满足回哪里 |
| --- | --- | --- | --- | --- |
| `code-project-setup` 核 R1、R3 | A 的所选版本、约定权重和验证输入、目标设备、批大小 1、端到端边界 | 核权重实际加载和候选入口能否运行，保存实际配置、计时位置、读数及波动 | 同条件下能稳定完成单张推理并观察到完整请求耗时，可继续核轨迹 | 先核版本、权重和配置。口径无法对齐时回选型比较，勿用子图读数代替 |
| `code-project-setup` 核 R2 | 基准计时用同一配置，分别记录采集开启和关闭时的情况 | 核能否看到写回量及算子实现，保存字段、来源、采集方式和计时偏差 | 得到可解释的轨迹及可用的基准记录，带回讨论是否推进 T1 | 字段缺失或采集干扰计时时，记录限制和备选接口。替代方式会改变测量含义时回取证设计 |

T0 结束后回传设置、入口、读数、波动、耗时、轨迹范围和偏差，供用户判断是否继续。若需要复现参考结果，将所选版本和可比评测协议交 `code-paper-reproduction` 核查。T1 的科学对照及投入等用户确认后再交 `code-idea-execution`。
