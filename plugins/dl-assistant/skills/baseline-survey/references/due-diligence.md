# 四维尽调详述（baseline-survey）

对每个候选 repo 做四维尽调。基于**本地看得见的信息**——"看得见"包括**远程读 repo 里的真实文件**（文件树、requirements、入口脚本、核心 model 定义、README、issue）。**不 clone、不下载、不跑**，但**要逐个读关键文件**，不是扫一眼描述就下结论。

> SKILL 讲流程与概览，本份是四维的详细判据 + 血缘溯源（论文无可直接复现 repo 时）。

---

## 维度 1：代码质量与可接入性（用户最看重，做满做深）

> 用户是计算机专业、本身懂技术——这一维要给出**能判断"接手顺不顺、改起来疼不疼"的深度技术分析**，不是"star 多不多"那种表层信号。**对每个候选都做满**，且**必须真的去读文件**（GitHub MCP / WebFetch 拉单文件内容），禁止只看 README 拍脑袋。

**必查核心（每个候选都要给）：**

- **环境依赖分析**：读 `requirements.txt` / `setup.py` / `environment.yml` / `pyproject.toml`。列关键依赖 + 版本约束；**不常见的库逐个解释**——是什么、为何需要、安装难点（冷门 CUDA 扩展、需特定版本编译的自定义算子、绑死某旧版 PyTorch/CUDA、需从源码 build 的包）；标出依赖地雷（版本互锁、年久失修、需特定硬件/驱动）。
- **执行链骨架**（关键产出）：读训练入口、eval 入口、`model/` 核心定义、`loss`，**梳理出几条真实运行链**，`文件:函数` 级粒度（粗骨架，不下钻逐行）。至少梳理：
    - **训练链**：入口 → 建模 → forward → loss → backward/optimizer
    - **推理/eval 链**：入口 → 加载 checkpoint → forward → metric
    - **数据链**：Dataset/`__getitem__` → 预处理 → collate → dataloader
    - **（意图=改进时必给）方法接入点**：你的方法会接在哪条链的哪一环、那一环代码干不干净、有没有现成扩展点。
    - 标注"基于远程读文件推断、未运行验证"。
- **接入成本结论**：以复现/改进意图为前提，估"接进去/跑起来"的工程成本 **低/中/高** + 卡点在哪。

**按需深挖菜单（看 repo 实际情况和你的意图，相关才查——这是参考维度，不是逐条打勾的清单，agent 应增删）：**

- **可读性 / 可维护性**：命名 / 注释密度 / 抽象层次；有无劝退结构（god file、写死绝对路径、魔法数、复制粘贴的实验分支）。
- **可扩展性 / 改动友好度**：有没有干净扩展点（注册器、插件、清晰 base class），还是处处硬编码、改一处崩三处。对"要改"的意图比单纯可读性更关键——可读但牵一发动全身照样难改。
- **工程化成熟度**：有没有测试 / CI / 类型标注 / 规范 logging，还是一堆 notebook + 注释掉的实验代码。
- **复现基础设施**：有没有 config 文件 / 训练脚本 / seed 固定 / 训练日志 / 预期 metric——直接决定"照 README 跑能不能复现"。
- **计算资源足迹**：默认 batch/显存/卡数假设和你的资源约束对不对得上；有没有 grad accumulation / 混合精度 / 多卡，让你能在小卡上跑。
- **依赖健康度 / 技术债**：上游库是否还活着、有没有绑死已弃用版本（如只支持 PyTorch 1.x 的算子）、Python 版本要求。
- **历史与社区健康**：commit 是持续维护还是一次性 dump；PR/issue 响应否；有没有更活跃的 fork。
- **数据/权重加载链路**：dataloader、预处理、checkpoint 加载这条链清不清晰——DL repo 最容易藏坑、最容易和论文对不上的地方。

## 维度 2：权重可得性 & license

- 官方预训练权重是否提供、链接是否还活着（**意图=复现时重点看**）
- 下载方式：直链 / HuggingFace / 需申请 / 已失效
- license：能不能用于你的场景（学术 / 商用 / 是否需署名 / 是否禁止再分发）
- 权重和 repo 代码版本是否对得上（有没有人 issue 反映权重加载 key mismatch）

---

## 维度 3：数据集版本一致性

- repo 用的是哪个数据集、哪个版本 / split
- 下载源是否还活着、要不要申请
- **预处理协议、metric 定义是否和论文一致**——这是后续"可比性炸弹"的源头，能在 issue / README 里看到的不一致先标出来
- **顺手记论文报告的主指标**（metric / 值 / 数据集 split / 出处页码，落 `baseline-survey.json` 的 `paper_metrics`，复现意图必填）——code-paper-reproduction 的验收基准就是这条
- 是否有已知的 split 泄漏 / 标注问题（社区报告过的）

---

## 维度 4：社区复现报告（高价值，最容易被跳过）

- issue / discussion / PR 里有没有人报告"复现得出 / 复现不出"论文的数字
- 第三方复现仓库、paperswithcode 上的复现记录
- 常见复现失败的原因（环境、随机性、缺权重、数据不一致）
- **这一维往往比 star 更能说明 repo 可不可信**——一个 star 很多但 issue 区全是"can't reproduce"的 repo 是陷阱

---

## 特殊情形：找不到可直接复现的 repo → 血缘溯源

很多论文没放官方代码 / 权重失效 / 只放了残缺实现。**这时不要空手而归**，启动血缘溯源，找一个"改一小部分就能复现 baseline"的近亲 repo：

1. **读论文原文找代码祖先**（arXiv 论文首选 `tex-mcp`：`tex_open` 打开固定版本 → `tex_search` 搜定位 + `tex_read` 读上下文；源码不可用则降级 `pdf-mcp` 的 `pdf_search`）。DL 代码大概率是在之前某个 repo 上改过来的，论文正文 / 附录几乎一定会写——搜 "based on / built upon / our implementation follows / 我们基于 X 的代码库"，它直接点名了代码祖先，**比盲搜 GitHub 精准得多**。
2. **定位那个祖先 repo**，对它照常做四维尽调（尤其维度1，含执行链）。
3. **估改造成本**：从祖先 repo 到复现本论文 baseline 要改多少——小改（加个模块/换个 loss）/ 中改 / 大改。作为新字段连同祖先 repo 进对比表。
4. 这种"近亲 repo + 改造成本"是一个**带标注的退路候选**，和现成 repo 一起对比。

> 边界：baseline-survey 只**找到近亲 repo 并标注大概要改多少**，**不真的去改**——动手改到能复现是下游（`code-project-setup` / `code-paper-reproduction`）在服务器上的活。

## 特殊情形 2：组合 insight / 分析先行型 idea → 基座选型

idea 是多篇论文 insight 的组合、v1 是假设裁决的分析实验时，**不存在直接前驱 repo**——这时选型的目标不是"对打的 baseline"，而是**实验基座**：在它上面跑分析实验的载体。不要硬套血缘溯源（没有"要复现的那篇论文"），改走基座选型：

1. **候选来源两类**：
   - **离任务最近的论文 repo**——任务 / 数据链现成，分析实验直接长在上面；
   - **框架型 repo**（detectron2 / timm / HF transformers 这类）——工程扎实、model zoo 全、自带可信参考数字；适合 insight 跨多个方法族、或论文 repo 都太烂时。
2. **尽调维度权重变**：
   - **维度 1（代码质量 / 可接入性）权重进一步上调**——基座要承载自定义分析代码（表征探针、干预 hook、二次指标），**可扩展性 / 改动友好度 / 数据链清晰度**是核心判据；
   - 维度 2/3 照查，但问题换成"**基座自带的参考数字可不可信**"（官方 model zoo 数字 / 权重齐不齐）——CPR 基座模式的对齐目标就是它，顺手把候选参考数字记进报告（哪个模型 @ 哪个 benchmark = 多少、出处）；
   - 维度 4 照查（社区活跃度 / issue 健康对基座同样重要）。
3. **报告里显式标角色**：候选与 decision 都标 `repo_role: substrate`（对打 baseline 则 `baseline`）——下游 CPS 透传、CPR 据此定复现目标（基座自报参考数字，而非某篇论文的表格行）。
