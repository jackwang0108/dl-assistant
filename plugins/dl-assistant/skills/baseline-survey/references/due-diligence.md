# 候选适配性与工程核查

本文件说明怎样逐项核查候选是否满足本轮研究或复现条件，用原文、源码和发布记录支持工程判断，并把仍需实测的事项交给后续步骤。

在[运行手册 Step 3](workflow.md#step-3-先核适配性再核工程条件)按必要条件核候选。这里的证据来自论文原文、远程可读的文件、资产元信息、社区记录和用户已提供的实测。实际获取仓库和实验资产、安装和运行交后续步骤。

## 1. 先查研究适配性

从[本轮必要条件](workflow.md#step-1-从目标提取必要条件)取 R 编号、用途和判断依据，为候选逐项记录「有静态证据支持」「明确不匹配」或「待核」。与本候选职责无关的条件可标「不适用」，并写由谁承担。记录实际版本、文件或原文位置、证据内容、适用范围和对选型的影响。

- **追到条件落地的位置。** 对测量需求，查实现是否接收所需输入、能取得必要中间量或控制目标变量。对公平比较，核配置和预处理是否保持关键条件，目标指标如何计算。
- **先核会改变推荐的条件。** 已读入口和必要口径明显不符时，记录判断涉及的范围。有其他可能符合的入口时定向核查。若整个候选明确不适用，可据此收束该候选。对仍有可能采用的候选，继续查任务相关的工程条件。
- **说明证据层次。** 原文和文档说明作者的主张。源码、配置和发布清单说明静态可见的行为与资产。社区记录和项目已有实测注明各自版本、环境与协议。发生冲突时先检查条件是否相同。需要运行才能确认的内容写成实测待办。

## 2. 代码质量和接入成本

1. **固定读过的版本。** 用 GitHub MCP 等可用工具读取候选的目录树和单个真实文件。优先引用固定 commit 或不可变发布版本。使用 tag 或分支时，尽量记下本次解析到的 commit、读取时间和文件位置，无法固定时说明影响。
2. **按用途追到 `文件:函数`。** 从启动脚本和配置找到真实入口，跟读关键实现、输入输出和配置覆盖。在同一版本中记录实际追到的链路。遇到动态注册、插件或设备分支时，记录已找到的候选实现和触发条件。分支无法确认时，把具体未决点留给下游。
3. **查依赖和必要接入点。** 按仓库实际结构读 `requirements.txt`、`pyproject.toml`、`environment.yml`、构建脚本或部署配置。列关键版本、编译扩展、外部服务、驱动或硬件依赖和硬编码路径。解释不常见依赖的作用及其与本轮的关系。涉及方法改动时，定位可扩展的模块、接口或配置。
4. **说明成本的依据。** 以当前任务为参照，写需要改哪些文件或接口、准备哪些依赖和资产、哪些环节必须运行才能估计。可用低、中、高表达相对接入成本，附判断依据。测试、CI、维护记录和可读性用于判断维护与改造成本。耗时、显存和成功率缺实测时保留未知。

| 用途 | 重点追查的调用关系 |
| --- | --- |
| 复现评测 | 入口与配置覆盖 → 建模和权重加载 → 数据划分与预处理 → 推理 → 指标计算和聚合 |
| 测量或分析 | 输入与运行时入口 → 计时起止、设备同步及预热 → 采集接口 → 中间量、计时输出及汇总。查采集本身是否可能改变测量 |
| 训练或方法改动 | 按需追入口、数据流、建模、前向、损失、梯度和优化器。定位要修改或干预的位置及共享条件 |

## 3. 分别核权重、数据和许可

| 核查对象 | 具体记什么 |
| --- | --- |
| 权重 | 模型身份、训练阶段、发布 revision、文件名、格式、已公布校验值、匹配的配置与代码版本。区分直接访问、需认证或申请、链接失效、访问受限和当前未知。核对加载代码与权重格式的静态证据 |
| 数据 | 数据版本、划分或必要样本范围、目标标签、预处理、增强、过滤、采样及指标实现。注明出处、访问条件以及会改变比较的差异。发现论文和配置有不同设置时分别记下 |
| 许可 | 分别查看代码、模型权重和数据的原始条款及版本，记录与用户用途相关的限制和出处。未声明、未找到原文和适用范围不清楚分别记。仓库许可证和附带资产的条款逐项检查 |
| 参考结果 | 核目标论文版本和具体表格行，记录模型、权重、配置、数据划分、指标定义、测量条件和数值。引用维护者结果时同样记录对应设置。只有能支撑当前复现或准备目标的数值才列为参考 |

资产页面可访问或列有文件时，记录本次观察到的状态。实际获得权限、文件完整性、加载和参考指标分开核验。网络、认证和限流故障保留访问限制。型号相同但训练阶段或协议不明确时，写明它是否影响当前选择。

## 4. 社区证据和实现来源

- **社区报告。** 查相关 issue、discussion、PR 或可回溯的第三方复现。记录日期、仓库版本、环境、数据、指标、报告结果及处理状态。只有相同条件下的报告才能直接用于评估相应运行风险。转述指回原记录。没有公开复现记录时保留未知。维护活动可帮助判断支持与排障成本。
- **缺少目标实现。** 按[候选搜索与来源追溯](workflow.md#step-2-找候选与合理替代)查论文原文、作者项目页和代码引用。证据能指向基础仓库时，记录明确出处、已知差异、兼容条件和改造成本。将普通路径、格式或接口适配与重建算法、改变数据或更换对照分开。涉及研究设计变化时，回到研究设计讨论。
- **组合候选。** 逐项说明仓库、权重、数据和测量工具承担的职责及版本。核输入输出形状、数据格式和划分、指标单位、配置以及各自许可能否共同满足当前用途。组合接口只有文档声明时，指出待测连接点和可能影响哪个必要条件。

## 5. 将剩余未知变成实测待办

把能静态核实的事情查到证据位置，再按[交接步骤](workflow.md#step-5-记录用户决定交接准备与复现)安排实测。每项写关联 R 编号、当前证据、负责人、保留条件、观察方式、继续标准及不符时的回退位置。

| 需要实测什么 | 本阶段先查什么 | 谁继续核实 |
| --- | --- | --- |
| 资产与入口 | 资产身份、版本和获取条件，依赖约束、真实配置与候选入口 | `code-project-setup` 实际获得并核完整性，检查权重加载、数据读取、环境和最小入口 |
| 测量接口 | 从代码定位观测点、读数定义与配置分支，写出当前静态证据和未知 | `code-project-setup` 可在已批准的准备范围内检查接口、输出形状或测量可用性。正式的机制干预或科学比较按取证方案交执行 |
| 参考结果 | 明确该数值为何适用于所选设置，保存论文位置或维护者记录及协议 | `code-paper-reproduction` 在对应条件下核评测或训练结果。参考条件不明确时，先确定可用对照和判据 |
| 可疑改造 | 列出缺失接口、预期改动和对必要条件的影响 | 普通工程适配可在准备中核实。改变科学条件或重建核心算法时，先回研究设计讨论 |

能通过有限准备核查的关键未知，可作为有条件推荐的依据。未验证的命令和配置标为候选入口。提交待办时说清取得什么证据后继续、什么情况应停下重审。

按需使用[事实记录模板](fact-record-template.md)保存 `facts/<候选>-<核查项>.md`。模板包含可复制的记录格式与 T0 完整示例。
