# 四维尽调详述（baseline-survey）

对每个候选仓库做四项核查。远程读取文件树、依赖文件、入口脚本、核心模型定义、README 和 issue。**不 clone、不下载、不运行候选仓库。** 逐个阅读关键文件后再给结论。

> SKILL 讲流程与概览，本份是四维的详细判据 + 根据论文查找实现所基于的仓库（论文无可直接复现 repo 时）。

---

## 维度 1：代码质量与可接入性（用户最看重，详细核查）

> 用户熟悉计算机技术。对每个候选都要详细说明接手前需做哪些准备、改动会涉及哪些模块。所有必查项都要依据读过的文件，用 GitHub MCP / WebFetch 读取单个文件内容。

**必查核心（每个候选都要给）：**

- **环境依赖分析**：读 `requirements.txt` / `setup.py` / `environment.yml` / `pyproject.toml`。列关键依赖 + 版本约束；**不常见的库逐个解释**——是什么、为何需要、安装难点（冷门 CUDA 扩展、需特定版本编译的自定义算子、仅支持某旧版 PyTorch/CUDA、需从源码 build 的包）；标出已知的依赖安装或版本兼容问题（版本互锁、年久失修、需特定硬件/驱动）。
- **主要调用关系**（关键产出）：读训练入口、eval 入口、`model/` 核心定义、`loss`，**梳理出几条真实运行链**，`文件:函数` 级粒度（记录主要调用关系）。至少梳理：
    - **训练链**：入口 → 建模 → forward → loss → backward/optimizer
    - **推理/eval 链**：入口 → 加载 checkpoint → forward → metric
    - **数据处理流程**：Dataset/`__getitem__` → 预处理 → collate → dataloader
    - **（意图=改进时必给）方法接入点**：你的方法会接在哪条链的哪一环、该处代码是否易于修改、有没有现成扩展点。
    - 标注"基于远程读文件推断、未运行验证"。
- **接入成本结论**：以复现/改进意图为前提，估"接进去/跑起来"的工程成本 **低/中/高** + 主要难点在哪。

**按需核查的参考项目（看 repo 实际情况和你的意图，相关才查——这是参考维度，不是逐条打勾的清单，agent 应增删）：**

- **可读性 / 可维护性**：命名 / 注释密度 / 抽象层次；是否存在影响维护的结构（god file、写死绝对路径、魔法数、复制粘贴的实验分支）。
- **可扩展性 / 改动友好度**：有没有干净扩展点（注册器、插件、清晰 base class），还是处处硬编码、局部改动会影响多个模块。对"要改"的意图比单纯可读性更关键——即使容易读懂，改动涉及多个模块时仍难以接入。
- **工程化成熟度**：有没有测试 / CI / 类型标注 / 规范 logging，还是一堆 notebook + 注释掉的实验代码。
- **复现基础设施**：有没有 config 文件 / 训练脚本 / seed 固定 / 训练日志 / 预期 metric——直接决定"照 README 跑能不能复现"。
- **算力与显存需求**：默认 batch/显存/卡数假设和你的资源约束对不对得上；有没有 grad accumulation / 混合精度 / 多卡，让你能在小卡上跑。
- **依赖维护与兼容性**：上游库是否仍有效、有没有仅支持已弃用版本（如只支持 PyTorch 1.x 的算子）、Python 版本要求。
- **提交记录与社区维护**：commit 是持续维护还是只提交过一次；PR/issue 响应否；有没有更活跃的 fork。
- **数据/权重加载链路**：dataloader、预处理、checkpoint 加载这条链清不清晰——DL repo 容易出现与论文设置不一致的地方。

## 维度 2：权重可得性 & license

- 官方预训练权重是否提供、链接是否仍有效（**意图=复现时重点看**）
- 下载方式：直链 / HuggingFace / 需申请 / 已失效
- license：能不能用于你的场景（学术 / 商用 / 是否需署名 / 是否禁止再分发）
- 权重和 repo 代码版本是否对得上（有没有人 issue 反映权重加载 key mismatch）

---

## 维度 3：数据集版本一致性

- repo 用的是哪个数据集、哪个版本 / split
- 下载源是否仍有效、要不要申请
- **预处理协议、metric 定义是否和论文一致**——在 issue 或 README 中发现不一致时先记录，供后续判断结果能否直接比较
- **顺手记论文报告的主指标**（metric / 值 / 数据集 split / 出处页码，落 `baseline-survey.json` 的 `paper_metrics`，复现意图必填）——code-paper-reproduction 的验收基准就是这条
- 是否有已知的 split 泄漏 / 标注问题（社区报告过的）

---

## 维度 4：社区复现报告（高价值，最容易被跳过）

- issue / discussion / PR 里有没有人报告"复现得出 / 复现不出"论文的数字
- 第三方复现仓库、paperswithcode 上的复现记录
- 常见复现失败的原因（环境、随机性、缺权重、数据不一致）
- **这一维往往比 star 更能说明 repo 可不可信**——即使仓库的 star 很多，仍要查证社区报告的复现失败

---

## 特殊情形：找不到可直接复现的 repo → 根据论文查找实现所基于的仓库

论文没有发布官方代码、权重链接失效或实现不完整时，查找论文实现所基于的仓库，作为可能通过少量改动实现复现的候选。

1. **读论文原文查找实现所基于的仓库**。arXiv 论文首选 `tex-mcp`，用 `tex_open` 打开固定版本，用 `tex_search` 定位并用 `tex_read` 阅读上下文。源码不可用时降级到 `pdf-mcp` 的 `pdf_search`。在正文或附录找 "based on / built upon / our implementation follows / 我们基于 X 的代码库" 等明确说明来源的语句。
2. **定位论文所用的基础代码 repo**，对它照常做四维尽调（尤其维度1，含执行链）。
3. **估算改造成本**。判断从查到的仓库出发，复现论文结果需要改多少，标为小改（例如加模块或换 loss）、中改或大改，并填入候选对比表的改造成本列。
4. 将查到的仓库和预计改造成本列入报告，与其他候选一起比较。

> 本阶段查找仓库并估算改动量。实际修改和复现由 `code-project-setup` / `code-paper-reproduction` 在服务器上完成。

## 特殊情形 2：选择用于分析实验的代码仓库

构想结合多篇论文的发现、第一版用分析实验检验核心假设时，没有需要复现的直接前驱。此时直接选择适合开展分析实验的仓库，跳过前面按论文追溯实现来源的步骤。

1. **候选来源两类**：
   - **离任务最近的论文 repo**——任务 / 已有数据处理流程，可以直接在该仓库中开展分析实验；
   - **框架型 repo**（detectron2 / timm / HF transformers 这类）——工程实现完善、model zoo 全、自带可信参考数字；适合 insight 跨多个方法族、或论文仓库的工程条件均不满足要求时。
2. **尽调维度权重变**：
   - **维度 1（代码质量 / 可接入性）权重进一步上调**——仓库要能接入自定义分析代码（表征探针、干预 hook、二次指标），**可扩展性 / 改动友好度 / 数据处理流程清晰度**是核心判据；
   - 维度 2/3 仍需核查，重点看官方 model zoo 的参考结果是否可信、权重是否齐全。报告记录模型、benchmark、参考数值和出处，供 `code-paper-reproduction` 确定复现目标。
   - 维度 4 照查（社区活跃度 / issue 响应情况同样要查）。
3. **记录仓库用途**。用于分析实验的仓库在候选和 decision 中均标 `repo_role: substrate`，用于比较的基线代码标 `baseline`。`code-project-setup` 原样传递该字段。`code-paper-reproduction` 在 `substrate` 情况下以仓库维护者报告的参考结果为复现目标。
