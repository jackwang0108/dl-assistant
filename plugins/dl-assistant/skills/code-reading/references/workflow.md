# 源码阅读与运行观察流程

本文件说明怎样把用户的问题定位到实际代码，逐段讲清数据流和运行条件，并把讲解、依据和未决项保存下来。

## 1. 首次阅读先建立仓库坐标

用户已经指定入口时直接进入第 2 节。指定函数或报错位置时先解释现场，再定位能到达该处的入口。已有当前断点时从现场观察继续。续读从第 5 节接上。

第一次带用户认识仓库时，先核对源码版本、README、包入口定义、启动脚本、配置和已有 setup 记录，识别实际目录、技术栈和正式入口。按需检查工作区差异。

```bash
git -C "$repo" rev-parse HEAD
git -C "$repo" status --short
git -C "$repo" diff --stat HEAD
rg -n -- "$symbol" "$source_dir"
```

按以下顺序和用户推进。

1. **展示仓库结构。** 给一棵基于实际文件的精简目录树，标明各目录职责和值得先打开的文件或符号。覆盖项目实际存在的入口、配置、核心实现、测试和产物位置。
2. **确认背景和阅读目标。** 看过目录树后，复用对话或笔记里的已知信息。还不清楚时，在讲架构前问用户对实际框架的熟悉度，以及最想弄懂什么。例如「训练和评测都用 Hydra 加载配置。你之前用过 Hydra 吗？这次最想看清哪部分？」需要回答时先停在这一步。已有信息足够时可以同轮讲架构。用户跳过时，按首次接触相关机制的深度继续。
3. **按背景讲架构与正式入口。** 熟悉框架时直接讲本项目的模块关系和调用顺序，初次接触时在关键节点用一个具体例子解释框架怎样参与。每个正式入口写明用途、实际启动命令、入口文件或符号、按执行顺序排列的主调用链，以及该命令是否已在对应条件下试跑。共享主链可以合讲，每个入口标明从哪里进入或分流。动态分派依赖配置时，指明解析位置和待核分支。
4. **主动给出可跟读的入口。** 架构讲解后列出贴合用户目标的路径。每条给出入口、主要调用链、能观察到的对象或行为，以及运行条件。可推荐一条启动成本较低的路线。用户选定后直接进入第 2 节。用户明确只要概览时，按需保存导览。

## 2. 核对选定路径，准备首个观察点

先查 README、启动脚本、配置文件和入口源码。追入口参数怎么进入配置、覆盖项在哪生效、对象如何构造，以及数据怎样传到目标段。概览时用一两句标清每个关键调用的位置、职责、数据变化和下一跳。必要时看依赖清单和已安装版本放在哪里解释。

可以沿用以下记录，先核它们对应的代码、入口和配置：

| 来源 | 要查看的信息 |
| --- | --- |
| setup 的 `setup.json` 与准备报告 | `components`、`environments`、`operations`、`checks`、`supported_operations`，以及实际运行命令、环境、资产和限制 |
| reproduction 的 `reproduction.json` 与报告 | 实际目标、协议、运行和适用范围。核本次场景是否用目标设置或 reduced，说明缩减改变了哪些输入、分支或测量条件 |
| prepare 的 `cleanup.json` 与 `coverage/operation-paths.md` | 保留用途、实际版本、关键改动和此次观测过的入口、配置和条件。引用观察范围，另列尚未核的调用方 |
| 用户提供的断点、配置或输出 | 先确认当前运行入口、参数和实际停在哪个进程及源码位置，再解释可见结果 |

说明选定场景的输入、操作、输出和本次要回答的问题。选定入口就开始准备，调试经验用于决定操作提示的详细程度。按以下顺序交付。

1. **准备可启动的路径。** 优先复用项目真实入口及其配置。现有入口不能以合适的成本到达目标时，写最小脚本调用项目原实现。缺 GPU、预训练权重或数据时，按[最小运行条件](vscode-debugging.md#最小运行条件)尝试 CPU、随机初始化和可由原数据管线读取的落盘样本，只替换缺失条件。
2. **落盘并试跑。** 核对 `.vscode/launch.json`，复用适用的启动项，缺少时新建或追加，保留原有配置。按启动项的解释器、工作目录、参数和环境先试跑，用实际输出或调试观察确认到达选定的代码位置。MCP 可用时由 agent 预验断点。只启动成功或只读出 batch 时，按实际到达的位置记结果。
3. **交给用户动手。** 给出启动项名称、首个断点的文件和位置、要观察的一个变量或调用栈帧。用户在自己的 VS Code 会话启动和单步。若目标段仍受阻，优先让用户运行同一调用链可达的前段，并说明后续阻塞。若整条链都无法启动，记录已试条件、失败点和恢复所需依赖，保留能配置的启动材料供续做。

## 3. 逐段讲解实际源码

每一段围绕一个连贯动作，例如合并配置、从 registry 构造实际类、取一批数据、完成一个 forward、聚合指标或选择 checkpoint。交互跟读每轮给一个问题、一处停止位置和一个操作。请用户回报看到的值、栈帧、分支或卡点，再对照源码解释并决定下一跳。结果偏离预期时，留在当前段核对配置、实际入口或进程。

1. **说明当前动作。** 简短交待它要解决什么，为什么在流程的这个位置做。
2. **给真实源码。** 标文件、符号和代码位置，展示为理解所需的数行。说明谁调用、配置在哪里读、哪个对象实际执行，以及走到不同条件会跳向哪里。
3. **追数据和状态。** 说明输入输出、形状或类型、单位、坐标含义和关键状态更新。形状依赖配置或分支时先写条件表达，如 `[B, N, 4]` 中的 `N` 由保留下来的预测数决定。
4. **就地补框架知识。** 比如读到 registry 时先用一个最小例子说明「配置名称如何解析到类」，回到项目核具体注册和构造调用。遇到隐式 hook、父类训练循环、配置覆盖或其他版本相关行为，按实际源码或对应版本的官方说明核查。
5. **按需对照论文。** 用 [paper-search](../../paper-search/SKILL.md) 核身份。优先用 [tex-mcp](../../tex-mcp/SKILL.md) 定位固定版本的原文，只有 PDF 时用 [pdf-mcp](../../pdf-mcp/SKILL.md)。写清公式、实验条件和实现位置，说明一对多的实现、工程选择或与论文的差别。

把话说到实际依据支持的范围。下面的表用于需要区分的关键结论，讲简单片段时可以直接在解释中标明。

| 依据 | 例如 |
| --- | --- |
| 源码明确 | 分支在 `score >= threshold` 时保留预测，这条条件可直接定位 |
| 条件推断 | 若过滤后保留 `N` 个框且坐标维不变，输出为 `[N, 4]`。具体 `N` 待实际运行 |
| 独立小验证 | 用一组自造张量核 reshape 或过滤逻辑，记录脚本与输入 |
| 项目实际观察 | 写明真正跑的入口、配置、样本、运行模式和实际结果，附输出来源 |

## 4. 在断点观察和补充验证

先确定哪份运行观察能回答当前问题。

- **局部诊断。** Agent 可按[诊断脚本指南](diagnostics.md)补验 registry 对象、batch 键或中间特征，为下一处断点准备具体观察。只验证通用算子时可用独立小输入，结果只覆盖该算子。
- **VS Code 交互。** 按[调试说明](vscode-debugging.md)核现有 `launch.json`、解释器、真实入口、参数及工作目录。给用户断点位置、在 Debug Console 中要看的表达式、预期结果及理由。例如停在对象构造后用 `type(model).__name__` 识别实例，停在读取 batch 后用 `list(batch)` 查键。用户回报结果后标为用户观察，未提供的输出保留为预测。

运行前检查 import、迭代数据、模型模式切换、hook 或 forward 的状态影响。按任务选择隔离运行、防止覆盖现有配置、记录临时改动，并只恢复本次引入的内容。已有范围内的观察可以继续；超出范围的源码修改、资源投入或状态影响先说明目的、影响和恢复方式。局部观察回答不了的问题保留待核项。

### 追问、理解检查和修改影响

用户还在追问，就先解释这一段；希望先看全貌时，连贯讲完主要调用。需要检查理解时，请用户复述数据流、预测下一跳或用自己的话说明为什么某个分支会被调用，同时讲清判断依据。记录确认到的范围。

写清当前运行未经过的分支和仍待核的调用方。用户有明确修改目标时，再列实际接入位置、输入输出契约、调用方、注册或配置接口、隐式状态和待做验证。例如「评测命令未进入恢复逻辑，修改它前需另用训练恢复入口验证」。

## 5. 保存和恢复

按[中文笔记模板](notes-template.md)保存本次范围、运行场景、实际版本、入口与源码位置、已讲和跳过的内容、运行依据、用户提出的疑问以及下一处要读的符号或断点。主线给 execution 的是实际读过的路径、条件、未决项及相关验证。发生临时改动时记录实际恢复情况。

续做先核笔记里的代码版本、配置及环境，按入口和符号定位最新位置。复用用户已说明的熟悉度和已确认的解释，版本变化影响的段落局部重读。继续时先说上次停在哪、目前增加或缺少了什么，再回到实际源码。
