# 依赖安装、编译与验证

不保存未经当前项目/版本核对的固定安装配方或GPU兼容上限表。安装方案须来自实际项目、依赖官方文档/发布产物及目标环境；社区方案是线索，先核版本、影响和适用条件。

## 先核什么

- 本轮操作真正需要哪些包/扩展，不为跑少量评测安装全部训练依赖。
- 项目代码commit、依赖清单/锁文件、解释器、OS/平台、硬件/驱动、框架运行环境；需要编译时再查构建工具和实际编译目标。
- 已安装版本、实际使用的解释器/环境与构建日志；不把宿主信息、容器信息、运行库和编译工具版本混为一项CUDA版本。
- 当前官方二进制/容器是否覆盖目标组合，实际文件/版本/来源是什么；没有证据不承诺某个URL或版本组合可用。

按项目隔离环境选择conda、venv、容器或现有授权方式，不强制一种。下载与安装权限按实际任务；没有工具时记录缺失，不要求所有项目必须安装nvcc或使用GPU。安装命令写入日志，环境导出只保留相关配置，避免凭据。

## 选择与失败处理

先根据项目要求和官方说明选可用安装路径，有合适预构建产物可优先使用；必要时在匹配工具链中构建。容器也要核镜像来源、准确版本/digest及实际宿主条件，不把存在Dockerfile当作一定可用。

失败时保存首个相关错误、完整日志、运行/构建环境、目标设备和已尝试方案。区分下载/认证、依赖解析、头文件/编译器、二进制/接口/设备兼容、资源不足等证据；不知道原因就写待调查，不断言某固定比例的失败都来自版本不匹配。

每次重试须有新依据，改变环境/方案后保留记录，不不断改版本直到import成功。超过批准成本、相同失败无新信息、需系统改动或影响研究条件时及时报告，不要求尝遍所有方案才上报。

## 替代不是默认等价

降框架版本、替换算子、混合精度实现或绕过依赖，可能改变计算、数值或比较。先说明为什么替代、变化和验证办法，再按已有授权与主文件影响规则处理；未知影响返回确认，科学设计变化交研究讨论。不因某依赖难安装就自动换算法。

名称/路径等适配也记录具体规则与证据，不能仅凭代码改动小就视为无影响。

## 验证安装结果

import只证明相应导入范围。必要扩展应以合法的最小真实调用检查目标设备/类型、输出结构和有依据的数值行为；若有适用的项目测试或可信参考，按当前版本调用并保存结果。没有合适参考则明确未知，不自行编造精度容差。

记录成功的构建/运行环境、实际包来源/版本、构建选项、检查代码与输入和日志。后续调用不同设备/精度/形状仍需核适用范围；不能用一项导入通过代表完整模型、训练或所有算子正确。
