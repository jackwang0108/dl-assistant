# 正式入口调查指引

本文件说明怎样从论文和仓库找出项目提供的正式入口，分析源码结构与调用关系，核对运行条件，并判断入口清单何时可以交给用户审阅。

供[运行手册 Step 2](workflow.md#step-2-调查全部正式入口提交入口调查报告)使用。从 Step 1 核对的仓库版本和用户目标出发。已有选型时，把已选版本、资产和实测待办也当作线索。用[入口调查报告模板](entrypoint-report-template.md)保存调查结果。

## 1. 从公开用法追到实际执行路径

1. **列出作者公开提供的操作。** 看 README 的快速开始、训练和评测说明，读论文的实验设置、附录和复现说明，再查同版本发布页的权重、配置和补充材料。每发现一项，记用途、出处、适用的代码或资产版本。有论文结果却没看到运行方式，也先记作待定位线索。
2. **展开包装命令。** 从文档命令找到 shell 脚本、Python 模块或已注册的命令行入口，顺着调用查工作目录、默认参数、环境变量和启动器。继续读配置继承与命令行覆盖，直到能指出实际执行函数和主要输出。比如文档写 `bash scripts/eval.sh`，打开脚本核它调用的评测模块和配置，再确认权重及验证划分从哪里取。默认值与用户需要的设置不同时，把差异写进记录。
3. **写到可以安排一次试跑。** 记录环境、设备、权重、数据及划分、配置和权限。用实际代码或文档说明最小输入、要跑到哪里、能观察什么。参数或资产版本还缺依据时，写明缺哪一项以及从哪里补查。候选命令及其来源随报告保存，实跑结果在执行阶段填写。

例如，追查仓库已给出的评测包装脚本时，可用以下命令定位启动器及参数，再打开匹配的目标文件读上下文。换用项目的实际路径。

```bash
sed -n '1,160p' scripts/eval.sh
rg -n 'python|torchrun|accelerate|--config|checkpoint|split' scripts/eval.sh
```

## 2. 分析源码结构与调用关系

先从仓库根目录的文件清单、包声明和已找到的入口看模块分工。再沿每个候选入口追踪实际调用。目录名只能提供线索，用脚本、配置和代码引用核实目录负责什么。

1. **画一份简短的结构图或写模块表。** 找出启动脚本、配置、数据读取与预处理、模型与权重加载、训练、推理、评测、测量和输出的实际位置。按仓库实际结构合并或增减模块。给每个关键模块写具体文件或符号，并标明哪些入口调用它。
2. **从入口追到本轮要验证的行为。** 沿着「命令与配置 → 实际执行路径 → 读取的资产 → 关键组件 → 输出」回读代码。在几个关键位置记 `文件:函数` 或配置键。训练重点追到 loader、前向、损失和优化器更新，评测重点追到划分读取、推理、样本统计和指标输出，其他实验重点追到参数分支、实际测量和产物。包入口或框架按配置动态选组件时，沿有效配置、导入和注册定义查到实际实现；暂时无法确定时注明要在实跑时核对哪一处。
3. **对比入口共用和分开的部分。** 标明哪些入口共用配置、加载器、模型或依赖，哪些在数据处理、运行模式、设备要求或输出上分开。共享函数也可能收到不同配置，须核实际传参再归并条件。把分析结果用于补查入口、确认资产需求和设计最小验证。

打开启动脚本后，用 `rg -n -F "$symbol" <实际源码目录>` 找函数、类或配置项的定义和引用，回读对应代码和调用处。在入口报告的「源码结构与共用模块」记录影响本轮准备的结构，在各入口详情保存自己的调用链。分析做到能解释入口读什么、调用什么、产出什么，以及哪些条件仍待核实。逐段讲解和算法细节留给 `code-reading`。

## 3. 从仓库反查公开说明漏掉的模式

从仓库根目录按实际项目结构查包的 CLI 声明、`scripts/`、`tools/`、`configs/`、示例及 CI。以下是用于定位线索的通用命令。按实际技术栈调整目录、扩展名和关键词。

```bash
rg --files --hidden -g '!.git/**' -g '!**/.git/**'
rg -ni --hidden -g '!**/.git/**' -g '*.md' -g '*.sh' -g '*.toml' -g '*.yaml' -g '*.yml' \
  'torchrun|accelerate launch|python(3)?[[:space:]]|project\.scripts|console_scripts|train|eval|infer|ablation|benchmark|preprocess'
rg -n -g '*.py' '__main__|ArgumentParser|hydra\.main' .
```

对每条新线索，回读实际文件并判断怎样纳入清单。

| 查到的情况 | 怎么记录 |
| --- | --- |
| 用户可用的训练、推理、评测、预处理或实验操作，有公开用法或仓库内可辨识的调用依据 | 登记正式入口，给出用途、实际调用路径和出处 |
| 同一脚本的两个模式使用不同执行路径，例如评测和轨迹采集 | 分别编号，写出选择模式的参数、各自条件和产物 |
| 同一路径下换模型规格、数据划分或其他配置 | 在同一入口下列相关配置变体，并注明它们带来的资产或资源差异 |
| 仅由其他入口调用的组件、单元测试或 CI 内部检查 | 记在对应入口的调用或核查范围里。若 CI 调用暴露了一个可独立使用的正式操作，追到实际命令再登记 |
| 论文提到实验，仓库只找到相关模块或不完整的调用线索 | 留在调查缺口，记已查位置、缺项及影响，待定位后再纳入清单 |

文档、配置和源码结论不一致时，保留各自的版本和位置，指出当前候选命令基于哪份证据。用源码和仓库实际参数查清运行路径，用论文或发布说明核实验用途和条件。

## 4. 交给用户审阅前检查

- **公开用法都有去处。** README、论文和发布页列出的操作已经对应到正式入口，或在调查缺口里说明查过哪些位置、缺什么、还可以去哪里补查。
- **源码关系有实际依据。** 知道启动、配置、关键组件和输出各在哪里，能指到几个决定运行条件的文件或函数。共用条件已回查调用和配置。未解析的动态分支写入待核项。
- **已定位入口足以安排验证。** 每项至少有用途、入口编号、候选命令及工作目录、环境和资产要求，以及最小输入、预期观察与当前未知。尚未查明的命令参数或资产写到具体字段，实跑状态随事实记录。
- **用户看得出优先级的依据。** 说明哪些入口共用环境和资产、哪些依赖额外资源、建议先跑哪项及其理由。若缺口可能改变范围、资产选择或顺序，在概览中指出它的影响，给出补查方案或需要用户决定的问题。

按模板保存 `entrypoint-report.md`，提交清单、调查缺口和建议顺序。收到用户反馈后补查并记录实际确认的清单与优先级。

## 示例 · 从论文附录补出轨迹入口

沿用[入口调查报告的 edge-vision 示例](entrypoint-report-template.md#完整填写示例--直接试跑论文仓库)。以下仓库、论文和命令均为虚构。

1. README「推理」「评测」「训练」分别给出 E01–E03。逐项回读对应的 `tools/` 脚本和配置，再用发布页 r1 核到 E01、E02 共用 Vision-S 权重。论文附录 A.2 还写了单张推理时采集写回量和实际运行的算子，README 没给启动命令。
2. 用 `rg -n 'trace|writeback' tools configs` 查轨迹线索。打开 `tools/measure.py`，找到选择 `trace` 模式的参数。将调用关系记为「`tools/measure.py` 的 `trace` 分支 → `configs/trace.yaml` 指定单张输入与 Vision-S r1 → 加载分类模型并执行推理 → 采集、保存轨迹」。和 E01 的 `tools/infer_one.py:main` 及单张配置对照后，有依据复用环境和权重。E04 额外要核目标设备的采集支持。将它作为独立入口，记录仓库根目录下的候选命令 `python tools/measure.py --mode trace --config configs/trace.yaml --image sample.jpg`。最小验证是用一张真实图片采集轨迹，检查写回量、实际算子及对应的单位和事件。
3. 附录同节还画了批量对照曲线。查过 README、测量脚本、轨迹配置和 CI，只定位到单张入口，批量配置和启动方式仍缺。把曲线对应的实验留在调查缺口，记下已查位置，建议继续查发布页的补充文件。这个缺口不影响已定位入口的初查审阅，若用户本轮希望复跑批量曲线，就优先补查。
4. 在报告开头建议先跑 E01，确认 E02 和 E04 共用的环境与权重。E02 还需验证集，E03 要另备训练划分。将 E01–E04 的详细记录和批量实验缺口交用户核对。
