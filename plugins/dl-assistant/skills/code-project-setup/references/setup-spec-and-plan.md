# 准备规格与执行计划编写指引

本文件说明怎样从已审阅的入口清单确定 setup 的交付与验收，再把它们拆成可以执行、检查和续做的任务。供[运行手册 Step 3](workflow.md#step-3-写准备规格和执行计划)使用。

先读开工核对结果和确认后的 `entrypoint-report.md`。有选型交接时，带入实际批准的组件、版本、必要条件和 setup 负责的实测待办。直接 clone 的项目，从用户目标和已经核到的仓库、论文及发布资料提取条件。使用[准备规格模板](setup-spec-template.md)和[执行计划模板](setup-plan-template.md)，两份一起交审。

## 1. 从入口清单写出四项交付

先按入口编号逐行列出「用途 → 环境与设备 → 数据 → 权重 → 实际命令和预期输出」。回看入口报告中的调用关系和配置，找出每项条件从哪里来。再归并真正共用的环境和资产，保留对版本、划分或运行模式有影响的差异。已定位的入口如暂缓，写清原因和续做条件。还没定位的公开用法留在待查项。

| 四项交付 | 写 spec 前查什么 | 怎样写清准备目标 |
| --- | --- | --- |
| 环境已配置 | 项目的锁文件、环境说明、镜像和实际机器记录。需要编译时核工具链、框架和扩展的约束 | 写选用的路线、版本、适用入口和依据，并给有依据的替代方案及采用条件。按实际所需检查导入、配置、设备和关键算子 |
| 数据已准备 | 入口使用的数据配置、实际 loader、发布页和划分清单 | 按入口记录来源、版本、划分、用途、访问条件和必要处理。写清原始与派生数据的关系，规定怎样核完整性、样本身份和实际读取 |
| 权重已准备（如适用） | 发布记录、模型配置和实际加载代码 | 写每份权重的模型、版本、配置和使用入口，以及怎样验文件和实际加载。入口从头训练、无需权重时注明 |
| 代码可以直接运行 | 入口报告的候选命令、配置路径和关键组件 | 明确每个入口的准备目标、执行条件及实跑范围。完整训练、全量性能复现或正式研究对照按实际任务安排和交接 |

环境、数据和权重各自明确复用或准备到什么状态，入口实跑检查这些条件能否一起工作。资源判断引用本机实测或发布文件大小等证据，分别标明已核实、估算和未知。失去关键依赖、权限或资源时，先判断哪些入口仍可独立准备。向用户说明影响及剩余选择。

## 2. 给每个入口写可判定的验收

按「**输入和配置 → 实际运行到哪里 → 观察什么 → 预期的依据 → 结果可以支持的范围**」填写。选择需要的环境、组件和真实入口检查。真实输入的最小试跑应覆盖这次关心的路径。例如，评测应观察实际参与统计的样本，测量应观察对应字段、单位和计时边界。通用的 loss 下降或指标非零无法独立作为验收依据。若没有适用的数值参考，写清可以验证的行为，以及还需记录的观察。

逐项标明必须保留的条件，例如权重与模型身份、标签映射、指标定义或目标设备。试跑缩小数据或步数时说明缩减范围和理由。可能改变实验行为的修复写明触发、影响、最小改法和复跑范围，交用户审阅后执行。已确定且在批准范围内的工程修复，写清如何验证。仍待核的风险写观察与决策条件。

## 3. 把验收拆成有依赖的执行任务

1. **按可检查的产出拆任务。** 环境可用、资产就绪、某入口检查完成分别有可交付证据。共用准备只做一次，关联全部受影响的入口。资产下载可以先进行，实际加载依赖相应环境就绪。哪些入口可单独继续，在任务依赖里写清。
2. **把候选命令核成计划可用的命令。** 从脚本、实际配置、包管理文件或发布说明取得参数。写完整工作目录、解释器或容器、命令、配置、输入和输出位置。需要在前置任务确定的值写明来源和启动条件。长任务直接写如何在目标机器上用 tmux 或调度器启动、查状态和续跑。命令示例见[运行手册的长任务小节](workflow.md#长任务启动与恢复)。
3. **每个任务都能判断完成。** 说明要看哪些文件、日志和结果，怎样对照 spec 中的验收条件。失败时写先查什么、允许怎样恢复、何时回审。按任务和入口编号保存实际结果。一个任务受阻时，按依赖继续可独立完成的工作。

交审前反查覆盖关系。Spec 的四项交付是否各有对应任务或适用说明？已确认清单里的每个入口是否对应验收和实跑任务，或明确记录暂缓？环境、资产、预期行为和允许改动是否有据可核？两份文件的范围、条件、资源与暂停点是否一致？计划的 Git 交接是否写明文件范围和合并目标？已批准版本和范围按 workflow 记录。

## 示例 · 从 edge-vision 入口报告写到执行任务

以下沿用[入口调查报告](entrypoint-report-template.md#完整填写示例--直接试跑论文仓库)的虚构项目。当前在 `/srv/research/edge-vision`，commit `a17c9d2`，目标机一张可用 GPU。用户确认先验证 E01、E02，再看 E03、E04。批量对照只有论文线索，先留待补查。

### 从调查发现写到 spec

E01 单张推理、E02 评测和 E04 轨迹采集使用同一运行时与 Vision-S r1。E02 还用 Vision-Val v1/val，E03 从头训练，要单独准备 Vision-Train v1/train。环境方案引用该版本的项目依赖文件和开工设备检查，拟建隔离环境，实测驱动、包导入及基本设备访问。单步显存和实际耗时留待实跑测量。

| 入口 | 写入规格的验收 |
| --- | --- |
| E01 单张推理 | 加载 Vision-S r1，使用真实图像，从正式入口得到可读分类输出，保存模型加载记录和输入身份 |
| E02 评测 | 以 Vision-Val v1/val 中指定的 17 个真实样本试跑，批大小 8，保持权重和现有指标实现。核参与统计的样本 ID 与清单逐项一致并得到指标输出。结果覆盖这份试跑清单 |
| E03 训练 | 读真实训练划分的一批样本，完成前向、损失与一次预期的参数更新，留日志和更新证据 |
| E04 轨迹测量 | 以单张真实输入和 Vision-S r1 实跑测量模式，保存写回量及实际算子字段、单位、事件和设备条件。采集支持待实测 |

### 从 spec 拆到 plan

先安排共用环境和所需资产，再按依赖逐项检查入口。下表是示例中四项交付和执行任务的对应关系。

Git 交接在计划中一并交审。修复、报告、配置和轻量验证证据在 `code/project-setup` 提交。本例的开工分支是 `main`，计划获准后在收尾时本地合回 `main` 并核验文件。

| 任务 | 对应交付与证据 | 入口与依赖 |
| --- | --- | --- |
| P01 准备隔离环境 | 环境。保存安装来源、实际解释器、导入和设备检查 | E01–E04，无 |
| P02 准备发布权重 | 权重。核 Vision-S r1 来源、完整性和实际加载 | E01、E02、E04，加载依赖 P01 |
| P03 实跑推理 | 可运行入口。保存真实输入、加载记录和预测 | E01，P01、P02 |
| P04 准备验证数据 | 数据。核 Vision-Val v1/val 版本、清单和 loader 读样 | E02，读样依赖 P01 |
| P05 实跑评测 | 可运行入口。比对 17 个样本 ID 和指标输出 | E02，P02、P03、P04 |
| P06 准备训练数据 | 数据。核 Vision-Train v1/train 版本、划分和 loader 读样 | E03，读样依赖 P01 |
| P07 实跑训练 | 可运行入口。保存真实训练批次与参数更新证据 | E03，P01、P06 |
| P08 实跑轨迹 | 可运行入口。保存字段、单位、事件及设备条件 | E04，P01、P02、P03 |

### 展开一个任务 · P05 实跑评测

- **前置条件。** 环境、权重和验证数据均已核实。试跑配置 `configs/setup/eval-smoke.yaml` 对应固定 17 样本清单，批大小 8，沿用仓库的指标实现和发布权重。
- **执行命令。** 在目标机的 `/srv/research/edge-vision` 下运行 `/srv/envs/edge-vision/bin/python -u tools/eval.py --config configs/setup/eval-smoke.yaml`。预计超过五分钟，用 workflow 示例的 `setup-dl-e02-eval-01` 会话启动，记录日志目录、会话和退出码。
- **完成条件与证据。** 保存实际配置、命令、日志、指标输出与参与计算的样本 ID。对照清单确认 17 项全部覆盖，将结果记入 `setup-report.md` 的 P05 和 E02 记录。
- **异常与回审。** 若输出只统计了 16 个样本，先对照清单、loader 日志、最终批次和评测配置。涉及调整样本统计或指标行为时，先回审最小修复，再用同一清单复跑并留原、新日志。全量参考结果后续由复现核查。
