# 仓库准备与入口验证运行手册

每一步写清执行什么命令、从输出检查什么、异常时走哪条分支、把证据记在哪里。

按 [SKILL 运行流程图](../SKILL.md#运行流程图)推进。下文的通用命令在实际执行机器上运行。项目专属命令从所查版本的文档、脚本、配置和已有记录中取得，将实际参数、工作目录和环境写入记录。

## Step 1 核对仓库、机器与已有记录

从用户已进入的仓库开始。先读项目约定，检查仓库根目录、分支、commit、用户改动以及已有进程。

```bash
git rev-parse --show-toplevel
git status --short --branch
git rev-parse HEAD
git diff --stat
git diff --cached --stat
git branch --list 'code/project-setup'
git worktree list
uname -sm
df -h .
command -v python conda docker tmux nvidia-smi
```

按实际平台追加探测。NVIDIA 机器可用 `nvidia-smi -L` 查设备，`nvidia-smi` 查驱动和占用。若已有项目环境，用该环境的 Python 核对版本和已装框架。计划使用集群时核对调度器及现有作业。空间检查在实际下载、解压、缓存和输出目录所在的盘上执行。读[日志和退出码](#长任务启动与恢复)确认已有任务，正在执行的同一任务继续监测。

优先读取用户指定的选型报告，其次检查项目的 `docs/baseline-survey/`。有多个可能的报告时核对仓库、版本和目标。与当前版本冲突时说明受影响处，重新核查相关依据后再安排执行。缺少选型报告时，从论文、仓库和发布资料核对运行要求。

| 选型资料 | 开工时怎么用 |
| --- | --- |
| `decision.status`、`decision.components`、批准条件 | 核对用户实际确认的版本、资产、角色及范围。旧报告可用 `decision.repo` 定位仓库，再核对缺失条件 |
| `requirements`、`research_fit`、`validation_targets` | 对照当前代码、配置和资产，记录必须满足的条件以及上游仅静态核查的部分 |
| `verification_tasks` | 逐项看负责人，setup 任务纳入本轮准备，复现及正式实验任务附原条件交接 |
| `recommendation` | 保留选择理由和替代项，实际选定范围以用户决定为依据 |

续做先读原目录的入口报告、spec、plan 和执行报告，从实际状态判断恢复位置。

| 现场状态 | 读什么、查什么 | 从哪里继续 |
| --- | --- | --- |
| 入口报告已写，清单待审阅 | 对照入口报告、用户反馈和 `git rev-parse HEAD` | Step 2 核对入口清单 |
| spec 和 plan 已批准，尚未执行 | 查批准记录、两份文件版本和 `git status --short --branch` | 条件一致时从 Step 4 执行。范围有变化时回 Step 3 |
| 下载、编译或试跑仍在运行 | 查执行报告里的会话名或作业 ID、日志与[退出码](#长任务启动与恢复) | 继续监测原任务，核对落地产物 |
| 资产文件在，完整性或加载未验证 | 对照来源与校验值，查真实 loader 或权重加载记录 | Step 4 补对应验证 |
| 入口曾通过，代码、环境或资产已有变化 | 对照旧命令、两版配置和 `git diff <旧提交>..HEAD` | 只复用条件一致且有证据的结果。补跑受影响检查，涉及批准范围变化时回 Step 3 |
| 入口验证结果已齐，文本产物尚未提交或已批准的合并未完成 | 核原报告、批准记录、setup 分支和目标分支的实际文件与提交 | 从 Step 6 补交接，复用条件一致的验证结果 |

**核对完先向用户汇报。** 说明当前仓库路径、分支和 commit、已有改动，目标机器和设备、可用环境及磁盘，找到的选型或准备记录、已有资产和正在运行的任务。指出发现的问题、可复用部分和准备从哪一步继续。新任务把开工事实写进入口报告，续做更新原执行报告。汇报后按当前范围继续，影响仓库选择、资源或批准范围的问题先解决。

## Step 2 调查全部正式入口，提交入口调查报告

按[正式入口调查指引](entrypoint-discovery.md)从 README、论文和发布说明追到实际执行路径，分析源码模块的分工和入口调用关系，再从包入口、脚本、配置和 CI 反查遗漏。覆盖训练、评测、推理、数据准备和其他正式实验。交审前逐项核对公开用法是否已定位或记录缺口，已定位入口是否写清候选命令、所需条件和最小验证方式。

按[入口调查报告模板](entrypoint-report-template.md)保存 `entrypoint-report.md`，连同建议顺序给用户看。对遗漏、用途疑问或资源差异先解释、补查并修改报告。范围和优先级明确后写准备方案。

## Step 3 写准备规格和执行计划

先根据已审阅的入口报告写[准备规格](setup-spec-template.md)，沿用入口编号确定本轮交付范围和验收标准，核对环境路线、数据、权重、资源及必须保持的条件。再按同一版规格写[执行计划](setup-plan-template.md)，把每项交付拆成有前置条件、实际命令和完成证据的任务。具体写法见[准备规格与执行计划编写指引](setup-spec-and-plan.md)。

交审前逐项核对。Spec 的环境、数据、权重和可运行入口是否都有计划任务或适用说明？每个入口是否有验收依据及对应任务，或明确为何暂缓？两份文件的资源、允许改动和回审条件是否一致？只提请用户决定会改变本轮范围、投入或执行条件的事项。

入口报告审阅确认入口清单和准备优先级。Spec 和 plan 审阅确认具体怎么做、怎样算通过、有哪些开销和改动。向用户同时提供两份文件路径，讲清后者的决定。两份均获确认后进入执行。记录实际答复、对应文件版本与批准范围。续做时先核对批准记录。范围、成本或研究条件有实质变化时，更新受影响的内容，再请用户确认。

计划写明 Git 交接。默认建议合回本轮开始前所在的项目分支（按实际分支名填写），与准备方案一并审阅。用户确认只交付 setup 分支时，按该决定提交即可。旧计划未约定合并时，照常完成本地提交，合并按用户已有授权处理。

## Step 4 建立或恢复 setup 分支，准备环境、权重和数据

### 工作分支

从已核对的起点创建本地分支。续做时，先用 `git log -5 --oneline code/project-setup` 与旧报告核对该分支，再切换。保留用户已有改动，若切换会影响现有工作先说明并解决；同名分支属于其他任务时另取名字。

```bash
# 首次准备
git switch -c code/project-setup
# 已确认是同一任务的续做
git switch code/project-setup
```

切换后用 `git status --short --branch` 和 `git rev-parse HEAD` 复核分支和起点，记录到执行报告。

### 环境与网络

从仓库环境文件、锁文件或官方镜像选已批准的安装路线。按[网络与镜像](../../dl-assistant/references/network-mirror.md)核下载源。访问失败时先区分网络、鉴权、限流和发布文件缺失，再处理具体原因。大安装或编译按下节托管。

以下是 Python 环境的通用检查。先将 `setup_python` 设为已选环境中 Python 的实际路径。容器内也在实际运行环境里执行。有 NVIDIA 编译需求时，另查 `nvcc --version`、`c++ --version`，用[编译型依赖](compile-deps.md)核对框架、编译工具、驱动和扩展版本。

```bash
"$setup_python" -V
"$setup_python" -c 'import sys; print(sys.executable)'
"$setup_python" -m pip check
# 项目使用 PyTorch 时
"$setup_python" -c 'import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())'
```

核实际解释器、依赖冲突、设备与项目要求是否一致。作者为本轮入口提供可启用的编译算子时，优先准备并启用它们。先做目标设备的最小调用，再在 Step 5 确认正式入口实际走到所选实现。遇到导入或算子错误，先定位第一次失败的命令与报错，再查实际框架、动态库或编译版本。执行报告留安装命令、出处、失败日志和复核结果。环境导出按实际工具选择，例如 `conda env export -n "$setup_env"`、锁文件或镜像标识。保存前去除密钥和私有鉴权参数。

### 权重

按[资产身份与校验](dataset-prep.md#1-核对资产身份再获取和校验)复用或下载指定版本，再按[权重身份与实际加载](dataset-prep.md#4-权重身份与实际加载)核项目实际取到的文件、模型配置和关键组件加载情况。需变更加载范围或映射且可能影响结果时回 Step 3。将来源、版本、路径、校验结果、已验证的配置和加载记录写入执行报告和机读记录。

### 数据

按[数据格式、预处理与划分](dataset-prep.md#2-数据格式预处理与划分)核正式数据身份、划分与预处理要求，按[项目实际读取检查](dataset-prep.md#3-用项目读取路径验证并排查空集合或缺样本)比对 loader 返回的样本与实际清单。分别记录文件校验、解包和转换结果、试跑清单及真实读取证据。

原始资产按原版本保留。格式适配记录输入输出路径和一致性检查。公开资产缺失时优先完成可用的准备动作；需要用户权限、指定资源或官方资产仍不可用时，写明已尝试的方式、缺项、受影响入口和续做动作。结果写入 `setup-report.md` 与 `setup.json`，按需用[数据集速览模板](dataset-report-template.md)展示真实样本。

### 长任务启动与恢复

预计超过 5 分钟、时长拿不准或重跑代价高的命令，在目标机器的仓库目录中用共享脚本启动。先用 `command -v tmux` 核工具；集群任务按调度器规则提交，记录作业 ID、输出路径和退出状态。tmux 会话名沿用 `setup-dl-<任务>-<尝试>`。在执行前按计划设置 `run_long` 为实际机器上 [run-long.sh](../../dl-assistant/scripts/run-long.sh) 的绝对路径，`session` 和 `log_dir` 指向本次尝试，`run_command` 写完整命令和显式环境入口。

```bash
bash "$run_long" "$session" "$log_dir" "$run_command"
tmux has-session -t "=$session"
tail -n 30 "$log_dir/$session.log"
cat "$log_dir/$session.EXIT_CODE"
```

启动后立即核对会话和实际日志。任务结束很快时，也可能直接写出退出码。活跃会话缺退出码时继续监测。会话消失且缺退出码时，从日志、进程和调度记录查中断原因，任务状态保留待核。退出码为零后仍要核资产完整性或运行结果。启动前先查同名会话和旧日志，重试使用独立尝试名保留原记录，从可验证的断点继续。把工作目录、命令、环境、会话名、日志与退出状态写入执行报告。其他平台细节见[共享长任务说明](../../dl-assistant/references/long-run-ops.md)。

示例在目标机器的 `edge-vision` 仓库内运行已确认的评测试跑。路径及命令来自示例计划。实际使用时换成本机、项目和已审配置的值。首轮启动时执行最后一行；SSH 重连后检查原会话及日志。

```bash
cd /srv/research/edge-vision
run_long=/srv/skills/dl-assistant/scripts/run-long.sh
session=setup-dl-e02-eval-01
log_dir=/srv/research/edge-vision/docs/code-project-setup/edge-vision-2026-11-24/logs
run_command='/srv/envs/edge-vision/bin/python -u tools/eval.py --config configs/setup/eval-smoke.yaml'
bash "$run_long" "$session" "$log_dir" "$run_command"
```

重连后，从执行报告取原会话名和日志目录，按以下命令检查。续跑前核对样本、权重和试跑配置未变。

```bash
tmux has-session -t "=$session"
test ! -f "$log_dir/$session.log" || tail -n 30 "$log_dir/$session.log"
test ! -f "$log_dir/$session.EXIT_CODE" || cat "$log_dir/$session.EXIT_CODE"
```

## Step 5 逐项实跑正式入口，复跑受影响的检查

按入口编号核对环境与配置、实际组件行为和真实输入与入口。选择各操作适用的检查。合成输入用于合适的组件检查，正式入口的最小试跑用符合要求的真实输入。先定预期行为与依据，再将实际命令、参数、日志、退出码、读数与判断范围写入执行报告。

| 入口 | 最少实际跑到哪里 | 执行报告里留什么证据 |
| --- | --- | --- |
| 训练 | 真实 loader 读批，完成前向、损失计算和一次预期的优化器更新。入口涉及恢复时按计划核读回 | 样本范围、损失与数值检查、更新的参数或步骤证据、保存或恢复记录 |
| 推理 | 指定权重加载后，用真实输入得到可用输出 | 权重和配置、输入标识、结果形状或格式、实际落盘位置 |
| 评测 | 用真实样本执行到指标统计及输出 | 预期与实际统计样本数、指标输入与输出、实际配置及协议。完整参考结果留给复现核对 |
| 预处理 | 真实输入经转换后，用目标读取路径打开产物 | 样本身份、数量、标签或结构、输入与输出路径 |
| 测量及其他实验入口 | 在计划条件下取得指定行为或字段 | 字段含义、单位、测量边界、实际设备与配置、原始结果和日志 |

按[组件行为与数值检查](numeric-sanity.md)为每项实际操作确定预期、依据和取证位置。分别记录命令退出状态、检查结果和入口验证范围。有资源测量任务时保留实际计时边界与设备条件。记录已有随机性设定和相关代码位置，原配置和试跑配置分别保存。

能在当前批准范围内处理的路径、依赖兼容或入口错误做最小修复，保存触发输入、diff、理由和复跑证据。漏载权重、样本漏算、改指标或精度等问题先查实。修理会改变运行或比较条件时回 Step 3。其他影响后续维护的问题记代码位置、触发例、影响和建议接手阶段。完成一项就同步报告和机读记录。

## Step 6 提交本轮产物，按计划合回并交接

按[准备报告与机读交接模板](setup-report-template.md)逐项对照入口调查报告，明确已通过、受阻、未验证和不适用。每个已通过入口的证据包括实际命令、工作目录、环境、代码版本和改动、输入配置、日志与产物。保留可重用的最小检查。报告写清受阻原因、已尝试方法和续做条件，关联原选型实测待办及后续责任。

逐条核对 `ready_commands` 是否与已跑命令、入口编号及执行范围一致。用户核对过的候选入口可能仍待实跑。小样本评测通过时，将实际命令、样本范围和配置记为小样本检查；当前下游若把 `ready_commands.eval` 当作完整评测入口，保留该字段待实际验证，并在报告提供小样本命令。用入口编号把调查报告、准备报告、日志和实际产物对应起来。

1. **逐路径核对交付文件。** 用 `git status --short --branch --untracked-files=all` 看新文件和改动，用 `git diff`、`git diff --cached` 同开工记录核对来源。将本轮的代码修复、`entrypoint-report.md`、`setup-spec.md`、`setup-plan.md`、`setup-report.md`、`setup.json`，以及实际用于复跑或核查的配置、脚本、脱敏环境导出和轻量文本证据纳入提交。已有源码修复提交时，继续处理后来新增或更新的报告和证据。逐一检查缺失的预期路径是否被忽略（`git check-ignore -v -- <路径>`）或在仓库外。对被忽略的文本按项目规则处理，外置材料在报告中给出实际位置和获取方式。权重、数据集、编译产物、缓存、大体积日志和含凭据的文件留在 Git 外，按需记录可访问的位置或脱敏证据。
2. **提交并检查 Git 中的文件。** 用 `git add -- <本轮路径>` 暂存本轮文件或用 `git add -p` 选取本轮改动。用 `git diff --cached --check -- <本轮路径>` 检查提交内容，用 `git diff --cached --name-status` 核对全部暂存项。暂存区只有本轮改动时直接提交。已有无关暂存项时，只有选定路径全部属于本轮、且工作区和暂存内容一致，才用 `git commit --only -m <消息> -- <本轮路径>`。同一文件混有用户改动时，先按项目约定隔离改动，无法隔离的路径说明阻塞。提交后用 `git rev-parse HEAD`、`git ls-tree -r --name-only HEAD -- <交付路径>` 和 `git status --short --untracked-files=all` 核对交付清单。用 `git show` 核对实际提交内容，再核原有的无关暂存项。续做时已有完整提交便沿用。提交失败时保留现场并说明实际阻塞。
3. **按已确认的目标本地合回。** 核对目标分支尚未包含的 setup 提交与改动，以及目标分支在哪个 worktree 检出。当前 worktree 有用户改动且目标分支未在别处检出时，可用独立 worktree 合并。能快进时用 `git merge --ff-only <setup 分支>`，已分叉时按项目约定执行合并。合并后核目标分支的实际 commit、交付文件和修复内容，并用 `git merge-base --is-ancestor <setup 提交> <目标分支>` 验证包含关系。项目采用 squash 时，核对目标提交的内容即可。目标分支另有改动影响已验证的代码、配置或入口时，复跑受影响检查或明确原证据适用的版本。目标未获批准、存在冲突或合并会影响用户现有改动时，保留 setup 分支提交并报告实际状态。远端推送按用户授权处理。
4. **交接可取回的版本。** 给出 setup 目录路径、setup 分支与交付 commit、合并状态及下游实际应使用的分支与 commit。报告和 `setup.json` 保留实际运行的代码版本与差异，收尾核实的交付 SHA 写在交接消息中。需要复现时转交已核验入口、资产配置、参考结果及待核条件。代码阅读可直接使用已准备的环境和入口。
