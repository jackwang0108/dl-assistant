# 从原始意见到可核对的回复

本文件说明怎样定位原意见和稿件、核查关切、分批交付改稿，以及根据实际回传核定回复。

## 1. 固定意见、稿件及规则

1. 从用户指定文件和已有回应记录开始。自己的论文优先用明确项目根，再核当前目录主 TeX 和 `_draft/`，或 `papers/` 里的候选。一个 PDF 可独立做意见处理。只有需要交改稿任务时才要有真实论文项目根。
2. 预审读取指定的 `problem-list.json`、`paper.sha256`、`completion` 和 `synthesis_status`，保留其全部问题 ID，再用范围选择本次处理项。真实审稿保存原意见文件及审稿人和条号；导师或合作者意见保留原文、时间或出处。用 `shasum -a 256 "$submitted_paper" "$comments_path"` 核对实际文件。修过的稿件另外登记为 `current_paper`。
3. 正式回复查本轮官方说明和平台字段，记录届次、轨道、规则范围、时限和时区。若尚未核清，先做内部草稿并列出待核项。详见[回复写作](rebuttal-writing.md)。
4. 依[状态模板](response-state-template.json)和[状态字段](response-record.md)保存已查材料、意见和本次范围。续做时先读上一次交接和现有工作记录，按稳定 ID 核已批准、已发送给写作端、已回传、已验证和仍未决的项目。

## 2. 拆分意见并核实际依据

保留原意见 ID 和原文。拆出可单独判断的关切，再定位被评论稿上受影响的句子、表格或公式。核稿件原文，再核实际配置、训练或评估数据、已有分析及重要前序工作。遇到相关工作争议时，记录查过什么及最近文献实际支持什么。意见提到图表时，直接看图表与表注，并与源数据或脚本对照。

先回答「原来认为怎样、实际看到什么、判断怎样变化」。分别说明意见是否成立、影响哪条主张、还有什么没查清。然后按[处理策略](fix-strategy.md)给推荐和可行替代。多个意见都问同一件事时可以共用行动，每个原关切仍有各自处理结果。

## 3. 成组确认并交付已批准的行动

先把相互影响的事项放在一起给用户看。逐组说明实际依据、推荐做法、可选替代、投入和作用。若一项要求增加解释，另一项建议删掉同段，标出冲突、先核影响再定取舍。正式回复有期限时按现有时间估算稿件、补证及复核，保留尚不可承诺的事项。

每项行动给稳定 ID、位置、要求、关闭判据、依赖和批准依据。补证写明要回答的比较，实验设计由 writing-paper 负责。核心科学问题仍待回答时，另交 iterate，附受影响主张和实际依据。当前已就绪的改稿批次可先交。将对应状态设为 `handoff`，用下方命令生成 `revision-brief.json`。

## 4. 接收改稿结果并核冲突

1. 收到 [revision-result.json](../../writing-paper/references/templates/revision-result-template.json) 后，核其引用的原 brief 路径及 SHA-256、回应任务和行动 ID。对应查看改后稿件、实际位置、改动和核查证据。碰到补实验，回查使用的结果包、运行条件和实际结论。
2. 把回传作为 `revision_result` 来源，关联对应行动的 `outputs`。核其确有对应行动的完成记录，再按关闭判据核对实际证据，把核查登记为 `verification`。两项齐备后才标为 `verified`，并解锁依赖它的行动。实际改动已结束但还没验，留 `completed`。有缺项则记录进度、原因及待做项。
3. 对同一主张、复用数字、图表和其他回复逐项核影响。比如表 2 改了预算口径，摘要、表注和说「公平比较」的其他回复要一起检查。最终稿版本晚于某次回传时，保留原回传，重新打开最终稿核对该改动和关闭判据。按[当前稿核查记录](response-record.md#分批改稿后的当前稿核查)记下仍然保留、已变更或缺失，使用核到的最终位置写回复。

## 5. 输出并核最终回复

按目标要求用原意见、直接答复、实际改动或限制组织文本。检查每个所选关切、稿件版本、数字、实际改动位置、规则范围和字数。可以按内容生成不同阶段，用新目录区分保存：

```bash
python3 "$skill_dir/scripts/check_response.py" \
  --record "$response_dir/response-state.json" \
  --output-dir "$response_dir/handoffs/handoff-1"
```

状态文件的 `stage` 定义当前阶段，目录名按实际阶段与版本选择。0 表示当前阶段的记录检查通过，1 表示内容或引用错误，2 表示用法错误，3 表示草稿或部分完成。只有 `handoff` 阶段向写作端交批准行动。回复定稿后将回复、对应稿件和未决项交到用户指定的下一环节。

## 示例：表 2 的训练预算和跨设备结论

R2 同时问表 2 是否同预算，以及收益能否外推第二台设备。保留 R2 原意见，拆为「预算口径」与「适用范围」。先核原稿、运行配置和附录。发现两组步数与样本量一致，稿件漏写；第二台设备只有本方法数据。

- **方案。** 建立行动 `clarify-budget`，在表 2 脚注和实验设置补实际步数及样本量。关闭判据要求稿件与两组实际配置一致。若第二台设备只影响外推，在全文按用户同意范围收窄表述。若跨设备效果是核心贡献，带已有证据交 iterate。
- **改稿交接。** 两个获批的写作行动进入同一 brief。写作端先回传预算行动及完成版的表注和设置段。范围调整若仍待确认，留在回传的未完成项。
- **回复。** 后一批若只修改摘要，保留预算行动的初次回传，再从最终稿核对表 2 注释及设置段并记录新页码。确认预算说明仍在后，可写「表 2 注释和实验设置已补充两组训练预算」。第二台设备仍缺基线时，明确当前数据不支持该设备内的性能差值。
