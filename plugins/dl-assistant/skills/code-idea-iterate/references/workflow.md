# 根据实验证据推进研究的运行手册

每一步写清依据从哪里取、什么观察会改变判断、结果记在哪里。按 [SKILL 的流程图](../SKILL.md#运行流程图)推进。研究判断以实际问题、证据和批准范围为准。

## Step 1 恢复问题、版本和任务

先按[会话恢复说明](../../dl-assistant/references/session-recovery.md)核当前仓库、代码版本和运行现场。从用户指定的本轮结论或已知版本开始，检查实际任务及仍运行的作业。新会话可先用实际仓库中的命令定位记录：

```bash
git rev-parse --show-toplevel
git status --short --branch
git log -1 --oneline
rg --files docs/research -g execution-conclusion.json -g execution-conclusion.md -g claims.json -g index.json
```

文件列表用于定位。确认研究项目后，读取 `docs/research/PROJECT_CONTEXT.md`，了解长期研究问题、采用的基线及资料位置。再用用户指定的轮次、实际记录里的版本与代码、设计及运行来源确定这次正在讨论哪一轮。背景文件暂缺时，从本轮研究说明和已有上游记录补齐判断所需的信息。

| 从哪里读 | 核什么 |
| --- | --- |
| 本轮 `execution-conclusion.json`、`execution-conclusion.md` | 读本轮状态、实际观察、`measurement_quality`、`evidence_updates`、独立核查范围和 `handoff.remaining_tasks` |
| `research-spec.md`、`research-plan.md`、`claims.json` | 还原本轮科学问题、假设与可区分预测，核批准设计、当前命题与留下的证据 |
| `experiments/index.json`、对应 `meta.json`、运行和原始产物 | 由观察定位实际 run、基准、分组、统计和偏差。核失败、受阻和未跑事项会影响哪项判断 |
| 上轮和历史记录 | 从 `docs/research/research-rounds.json` 查上一研究轮次、实际代码起点和决定引用，再读相关的诊断及反向证据 |
| 论文或后期补实验返回的材料 | 核论文版本、受影响的实际主张或段落、新证据及相关实现。区分原判断与当前待重评内容 |

| 当前现场 | 怎么继续 |
| --- | --- |
| 上轮完成或部分完成，关键读数及来源可取得 | 选本次决定最依赖的一条观察，按 Step 2 回查对应 run、测量和对照。缺项单独记 |
| 只有报告或核查结论，关键运行记录暂缺 | 记实际已读范围，定位缺的是输入、配置、日志、原始读数还是统计依据。可以讨论已有材料所支持的范围 |
| 仍有任务在运行，或目前只取得部分结果 | 记录实际运行状态和观察截至位置。说明预计到手的结果会改变哪个决定，先推进已有证据可以支持的讨论 |

向用户简报当前问题、上轮实际试了什么、这次接着判断什么。

## Step 2 核证据并向用户解释

1. **沿一条观察追到底。** 在结论里取观察 ID、任务、实验和 run。对照台账和 `meta.json` 看哪些组完成、哪些重试或恢复。再读获批设计、实际配置、数据或权重身份、测量输出与相关代码。分析按实际重复对象，分开处理失败记录和已有可用读数。
2. **核观察与原先预测的关系。** 需要深入调查时，先按[证据复核与原因调查指引](autopsy-guide.md)选择检查。逐项写主要读数、比较组与实际条件，注明是否能直接比较。找最强替代解释和最不支持当前判断的证据。只需核已有数据时，可用相同纳入与聚合规则复算，记录数据版本、脚本或命令、单位、结果和限制。需要展开时按[调查记录模板](autopsy-template.md)保存所查的材料及发现。
3. **核跨规模和数据来源。** 比较 reduced 与目标条件时，优先取同一个改动对同一个基线的成对结果，核关键现象、样本、训练阶段和测量是否保留。有效观察只支持对应条件。用 W&B 时，按[共同记录](../../wandb/references/experiment-records.md)先从台账列出实际应核的尝试，再查对应实例、run、字段及 step 范围。记录未同步、缺页或抽样限制，有本地证据时按实际来源使用。
4. **先给用户讲清，再讨论去向。** 用一句话介绍问题为什么重要，说明原先预期、真实设置、实际观察、证据改变了什么和仍有哪些解释。方向不熟悉时先补必要背景或一项具体对照例子。再根据用户关心的问题展开图表、源码和实验细节。对话方式参考[研究讨论](research-dialogue.md)。

| 观察到什么 | 怎样描述和继续 |
| --- | --- |
| 运行失败，核心读数缺失 | 先查失败范围及尚可使用的观测，明确需要恢复哪项证据才能判断命题 |
| 数据有效，但变量同时变化 | 描述实际配置比较及范围，列能产生同一观察的解释，找能分开的对照 |
| 同条件的观察与预测相反 | 核执行、测量和适用边界，保留反向结果。证据影响到哪项研究判断由用户与 iterate 讨论 |
| 新证据和原判断只在条件上不同 | 分别记真实条件与预测范围。需要重新定命题时，保留历史和理由 |

将一次完整核对记成「原先预测 → 实测与条件 → 判断变化 → 最强替代解释 → 仍缺什么」。例如：

| 要核的内容 | edge-vision 的一条证据链 |
| --- | --- |
| 原先预测 | C1 预期在实际算子实现固定时，改变写回量会改变延迟。核研究说明、configuration-comparison 设计和命题的实际条件 |
| 实测与条件 | 从 `execution-conclusion.json` 的 OBS-02 找到 `exp-configuration-comparison` 的 `baseline-01` 与 `combined-01`，回查各自命令、生效配置和轨迹。正式计时均关闭轨迹，同设备、输入、预热与同步边界。配对读数为 12.6 和 10.8 ms，见该实验的 `analysis/latency-comparison.json` |
| 判断变化 | 组合低 1.8 ms，支持所测配置的结果。C1 仍为 `insufficient_evidence`，引用 `executions/configuration-comparison/execution-result-review.md` 的 C1 核查 |
| 最强替代解释 | 两组实际算子发生切换。运行时实现的变化也可能造成同方向的延迟差 |
| 仍缺什么 | 核现有几个组里有没有实际算子相同、写回量不同的配对。若没有，再判断目标条件下能否构造该对照 |

核对时若报告、独立核查和原始材料不一致，分别写各自引用的版本、run、指标定义及实际范围。先用运行记录和原始数据确认读数及条件，再核差异会不会改变对命题的判断。可以复算时保留方法和结果。尚不能解决时，给受影响的主张和最能区分原因的一项补查。保留原核查及后续修订的理由。

异常需要看运行时状态时，先用[断点诊断判断](autopsy-guide.md#判断是否需要断点诊断)把问题落到一条可观察的分支、变量或调用路径。优先复用 execution 已留下的诊断证据。需要新运行时，在 Step 3 写清检查、条件及可区分的结果，再按 Step 4 和 Step 5 确认并交 execution。收到观察后回到本步，说明它改变了哪项判断，以及是否还需要正式测量。

## Step 3 形成并比较下一步建议

### 选出最影响决定的未知

从 Step 2 已核实的「原先预测 → 实际观察 → 判断变化」出发，把观察和可能解释分开。沿用此前在可比条件下已核实的认识，保留反例和边界。用问句写出关键未知，再问「知道答案后，我会改变哪个决定？」不同答案都导向同一行动时，降低这项未知的优先级。新假设可以来自异常、重复规律、跨条件差异、理论推理或文献冲突。

| 当前未知 | 先查什么 | 什么结果会改变决定 |
| --- | --- | --- |
| 实现或测量是否可信 | 核实际配置、日志和代码路径。必要时设计已知答案测试或独立读数核查 | 发现偏差就先修正测量。局部核查通过只支持所查条件 |
| 现象是否稳定 | 核独立重复和条件差异。需要新重复时，提前写样本范围、重复规则和停止点 | 确认现象会重现，或确定它只在什么条件下出现 |
| 哪个解释更符合观察 | 找解释会做出不同预测的条件、干预或测量 | 若有效读数只符合其中一个预测，更新相应判断。若两者都符合，保留两种解释 |
| 原预测有反例，或范围可能更窄 | 核反例是否满足原条件，找结论可能随之变化的条件 | 写清放弃、修订或收窄什么，以及调整后还能回答什么 |
| 结果成立，但研究价值不清 | 用[论文检索](../../paper-search/SKILL.md)核最近工作的问题、条件和实际结果，记录版本、已读位置与限制 | 写清成功后多回答什么科学问题。新增不足时，讨论收窄问题、换问题或停止 |

### 把未知转成可做的检查

1. **写出能区分解释的预测。** 列各解释的成立条件、支持与反对证据。写明「在条件 X 下改变 Y，解释 A 和 B 分别预测读数 Z 怎样变化」。若都预测主指标改善，就找预测不同的条件或中间量，同时考虑两者能否共同起作用。
2. **核对照能否成立。** 写要改变和保持的条件、读数来源与单位。先查已有数据能否配对。新对照要在实际运行中核实保持条件。多个变量必须一起变时，考虑加对照、交叉比较或独立测量，并写明仍有何限制。
3. **预先写清怎么解释。** 覆盖符合预测、与预测相反、变化小到无法辨认、对照或测量无效的情况。写每种结果会更新哪项判断及下一步。判据可依据已有重复的波动、测量精度或有实际意义的效应。依据不足时，先核测量质量。
4. **找最小可行检查。** 先说明已有记录、代码和配置能查到哪里、什么发现足以改变设计。需要新运行时，在方案里写所需设备、读数、验收和停止点，确认后交 execution。关键信息还不清楚时回 Step 2 补材料。

证据指向具体机制时，沿数据、表示、融合、监督、优化或运行路径找干预点。写清改哪一处、为什么会改变预期中间量、是否能接入基线、最早从什么信号发现设计问题，以及额外改变的条件怎么控制。有相关先例时，核原文是否解决同一问题、结果依赖哪些条件、当前能否满足。缺少先例时，写清推理和最薄弱的前提。

探索性分析写明问题、观察范围、分析方式、预算和停止点，并记录新假设从哪些观察和筛选中产生。预先检验在取证前登记预测、对照、判据和解释范围，变动时记录时间与原因。复用产生假设的数据时，交代用过哪些数据、从多少条件或指标中发现结果，以及在哪些样本或条件下还需要独立确认。

### 推荐行动并起草决定记录

Agent 主动提出推荐，写清它能减少的未知、最强反对理由、成本更低的可行备选，以及什么证据会改变建议。用现有运行或实际资源估投入，未知时说明先查什么才能估。只有一个合理行动时可以直接推荐，并交代其他行动为什么暂缓。用同一套证据、可行性和成本标准评估用户提出的想法。

用能说明目的且本轮唯一的 slug 命名决定目录。按[下一步决定模板](next-step-decision-template.md)起草 `docs/research/v<N>-<slug>/decisions/<决定-slug>/next-step-decision.md`。对应原先预测、实际观察和判断变化，附上能定位到实验、运行或原文的出处。记录最强替代解释、关键未知、推荐与备选、改变建议的条件和停止点。用户决定先写「待确认」。

### 示例 · edge-vision

基线 12.6 ms，组合 10.8 ms。写回量与实际算子同时变化，已有四组记录也找不到同算子、不同写回量的配对，C1 仍缺机制证据。先查 `runtime/dispatch.py:select_kernel` 的固定入口、回退路径和现有运行记录。若还需在目标输入下确认分派，先申请最小核查，核完即停。确认能固定实际算子并保留目标条件后，再设计写回量对照。正式计时关闭已知会影响读数的轨迹采集，并用独立轨迹核对实际算子和写回差异。如果固定算子改变了要研究的场景，就重审测量方式或收窄问题。

首次复查写入 v1 的 `decisions/check-existing-traces/`。如果用户批准在 v1 补采原比较中缺失的轨迹，在 v1 追加 plan 修订，交 execution 将结果写进 v1 的新执行批次。若用户之后决定为固定分派开 v2，把决定写进 v1 的 `decisions/approve-fixed-dispatch-check/`，将正式方案保存到 `docs/research/v2-edge-vision/` 并登记轮次。v2 的 plan 引用该决定。[填写示例](next-step-decision-template.md#填写示例--edge-vision)

## Step 4 与用户确定下一步

先说明「现有证据支持什么、我建议下一步做什么、为什么值得、哪种结果会让我改建议」。讨论结束后，更新同一份 `next-step-decision.md`。记下用户实际选了什么、批准了哪些工作、哪些还待决定。再写要带回什么证据、做到哪里汇报，以及需要什么条件才能继续。仍未选定时保留「待确认」，并写清卡在哪个问题。

| 用户考虑的去向 | 应先回答的问题 |
| --- | --- |
| 继续取证、修改方法或修订假设 | 最值得解决的未知是什么？哪项对照能改变判断？可行的范围与成本是多少？ |
| 调整研究问题或重新选题 | 现有证据使原问题的哪部分不再合适？新问题值得做的依据是什么？需要从新方向起步时交 idea-find |
| 准备写作 | 实际回答了哪个科学问题、发现了什么、最强替代解释是什么、适用条件在哪里、相对最接近工作新增了什么？剩余工作会不会改变核心主张？ |
| 暂停或停止 | 已经学到什么、为什么现在不继续、什么新证据或资源到位后可以恢复？ |

### 写作前逐项核对候选主张

| 要核什么 | 写到什么程度 |
| --- | --- |
| 证据支撑哪一句话 | 给候选主张、对应观察、实际条件及适用边界。核这句话回答了研究问题的哪部分 |
| 最强替代解释 | 写仍能产生同样观察的解释，以及是否影响候选主张 |
| 相对已有工作新增什么 | 核最接近工作的实际结果、设置与来源。写当前新增的事实、条件或解释；资料不足时写需要查哪篇、哪一部分 |
| 缺失结果会改变哪一部分 | 说明缺的是成立所必需的核心证据，还是界定适用范围的补充证据。给补证成本和可收窄的表述 |

在 edge-vision 中，「组合在这一设备和输入上更快」已有配置比较证据。「加速来自减少写回」仍缺固定算子的隔离对照。配置收益本身是否构成值得写的发现，还要对照最接近工作是否已报告同类结果、当前多回答了哪个问题。若核心主张取决于未取得的结果，讨论补证或缩小主张。截稿和资源用于安排工作量。用户决定准备写作后进入 Step 6。

## Step 5 准备并交接取证任务

先区分三种去向。用已有记录复算或核配置时，由 iterate 完成，在本轮决定目录保存结果。需要重新运行或取得新读数时，由 iterate 写取证设计，execution 执行。如果仍在回答本轮的问题，例如补采缺失组或继续查同一个疑点，把获批任务加入本轮 plan 的新修订并交 execution 执行新批次。用户确认建立新研究轮次时，再创建新轮目录并登记轮次。

1. **先写草案供审阅。** 用 [研究说明模板](../../dl-assistant/references/spec-template.md)写研究什么、为什么值得、成功后能主张什么。用[取证方案模板](../../dl-assistant/references/plan-template.md)及[编写原则](../../dl-assistant/references/plan-writing-principles.md)写这轮要弄清什么、怎样取证和不同结果怎么解释。对照、读数、条件、投入和停止点写到能审阅。内容尚待确认时可放入决定目录的 `drafts/`。
2. **一起交用户看决定。** 说明相对上轮的改变、依据和关键对照。一次审阅可确认两份文件，记录实际批准版本与范围。仅批准准备时，在研究说明里写清能确认的准备条件及科学判断还缺什么，在取证方案里写任务、验收、资源和停止点，标明待确认的正式工作及其启动条件。
3. **核对命题快照。** 按[共享论点模板](../../dl-assistant/references/claims-template.json)保留历史证据、适用范围和改判依据。命题语义不变沿用 ID，发生实质变化时新分配 ID 并写来源。核 spec 的研究重点、plan 的实际获批任务及快照中的相关命题是否对齐。只核准备条件时，写明它限制哪些后续推断。
4. **选择同轮补证或新轮交接。** 同轮补证沿用原目录，保留原批准 plan 和实际运行记录。用户确认开新轮时，按[研究轮次登记与 Git 交接](../../dl-assistant/references/research-rounds.md)核 `main` 上的实际起点并建立对应目录。研究上的上一轮依据证据来源记录。
5. **保存本次交付。** 新轮将获批的 `research-spec.md`、`research-plan.md` 和 `claims.json` 直接放进相应轮次目录，在 `docs/research/research-rounds.json` 追加条目。按[轮次索引模板](../../dl-assistant/references/research-rounds-template.json)记录轮次 ID、用途、目录、上一研究轮次、实际起点 commit 和批准决定路径。决定留在提供证据的轮次，链接本次获批方案和任务。无论同轮还是新轮，plan 都引用实际决定与批准修订，交给 execution 时指出第一项可执行任务和停止点。提交及远端操作按项目约定和已有授权。

## Step 6 保存写作、暂停、停止或新起点的决定

- **准备写作。** 用户确认后写 `docs/research/paper-package.md`，在本次决定记录中链接交付路径。从科学问题和主要发现组织材料，每项主张注明证据、关键比较、适用边界、替代解释、相对最接近工作的新增和剩余缺口。引用实际代码、配置及运行。需要补证的内容写到可明确区分核心研究缺口和可在现有论证内规划的补充实验。把材料及可取得的代码和证据位置交 writing-paper。
- **暂停或停止。** 保存实际决定、已完成记录、仍运行或受阻的任务、已有证据、未知和可恢复条件；按实际进度更新研究记录。
- **从新起点研究。** 保留本轮学到的事实、原问题为什么调整及可继续用的材料，再交 idea-find 明确新问题。

不论去向，都在 `next-step-decision.md` 引用实际证据和用户决定。交写作时逐条核主张、条件和原始证据能相互定位，注明仍未补齐的核心缺口。暂停时写可恢复的具体条件，例如取得完整轨迹、确认可用设备或用户重新批准某项投入。遇到新的论文结果或后期反馈触及核心主张时，用实际版本和新证据重新讨论受影响的范围。
