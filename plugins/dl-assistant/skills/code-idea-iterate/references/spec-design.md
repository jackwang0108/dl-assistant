# 下版方案生成操作手册

> iterate 写 spec（v2+）时的核心手册：怎么从「诊断结论」走到「一个有依据且值得验证的候选方案」。
> 这是整个 iterate 里创造发生的地方——诊断（Step 5）告诉你问题出在哪，本手册告诉你怎么生成解法。
> 对话手法（怎么把候选摆给用户、共同打磨）见 `research-dialogue.md`；本手册管**生成什么**。

## Step A：起点盘点（先整理已有证据）

动手生成方案前，把三样东西摆到明处：

1. **诊断结论**：这版要解决什么——Step 5 的版型判断（方法需要改进 / 机制前提不成立 / 调整总论点）+ 支撑它的分析证据。**上版方法版本未达预期时，诊断结论（判断问题属于哪个层次 + 定位证据 + 待核查的设计选择）是第一输入**——归层为"设计选择错"时，方案生成的主轴是修正实现位置（换层位 / 换接入位置），不是推翻机制。方案必须直接回应诊断，不回应诊断的方案是无的放矢。
2. **仍待验证或已获支持的子论点**：claims.json 里还活着的子论点（active / supported）——方案是在它们的基础上走，不是推倒重来（除非调整总论点的版本）。
3. **历次验证对机制的认识**：沿版本链把前几版 `00-from-previous-version.md` 的「裁决意味着什么」逐条提出来——这是本项目独有的机制理解（「高频进了残差但被淹没」「X 组件在小目标上才起作用」），是方案生成最有价值的弹药。别每次从零想。

## Step B：缺口陈述（从诊断反推机制层缺什么）

把诊断结论翻译成**机制级的缺口陈述**。这是最关键的一步翻译：

- 差：「性能差 2%」——这是现象，不是缺口，生成不了方案。
- 好：「高频信息进了残差但被主干特征淹没，残差支路缺乏门控」——机制级、可作用（actionable），方案自然浮现（加门控 / 改融合方式 / 分开监督）。

判据：缺口陈述必须指向一个**可以动手改的机制位置**——方法版本未达预期经诊断并判断问题所属层次时，缺口陈述必须回扣诊断定位（归"设计选择错" → 缺口就是那个定错的设计自由度，如"实现位置选在中间层而信号在晚期层"）。写不出机制级缺口 → 说明证据不够，回 Step 5 就地诊断（L1/L2 probe），别硬写方案。

## Step B.5：先征集用户的想法（先听用户的初步想法，再谈生成）

写明待解决的问题后，生成候选前先听取用户的原始想法：

- **摆什么**：诊断结论 + 机制级缺口陈述 + 历次验证对机制的认识的压缩摘要（各一两句）。这些是**具体要回答的问题**，不是候选答案——不许夹带 agent 自己想的机制方向（夹带 = 先给候选方案再征求用户想法，征集作废）。
- **怎么问**：明确邀请半成品——"缺口就是这个。你直觉上想怎么补？半句话、一个类比、一个'我就觉得哪里不对'都行。"对话手法细节见 `research-dialogue.md`「先征集用户的想法」节。
- **怎么收**：用户的想法逐条记下（原话级别，别当场扩写成方案），作为一等候选进 Step C（来源标「用户」）。
- **用户暂无想法时继续**：用户说"没有，你来"→ 直接进 Step C，由 agent 补充候选。征集在确认点 4 之前进行，不新增确认点。

> 为什么必须先收后生成：agent 候选一旦先摆出来，讨论议程就被锚在 agent 的先验里——agent 的候选本质上是范式内的"补丁式"采样，真正带来质的飞跃的跳跃历来来自用户的经验直觉。顺序反了，用户就只剩否决权。

## Step C：候选生成（从缺口推出 2-3 个候选机制）

候选是**推出来的，不是憋出来的**。按下面的链条走，每个缺口推出 2-3 个候选。

### C.1 推导链：缺口分解 → 干预点 → 机制类

1. **缺口分解**：缺口发生在信息流的哪个位置？常见位置：输入侧（数据 / 特征构造）、表示侧（主干提的特征缺什么）、融合侧（多源信息怎么汇合）、监督侧（loss / 训练信号）、优化侧（训练动态）。
2. **列干预点**：同一个缺口通常有**多个可动手的位置**。例：「高频被残差淹没」——可以在融合侧改（门控 / 改融合方式）、在监督侧改（给高频支路单独 loss）、在表示侧改（让主干保留更多高频）。每个干预点是一类解法。
3. **每个干预点想机制类**：这个位置上有哪些机制可用？（融合侧：门控 / 注意力加权 / 解耦后分路 / 分级融合……）

### C.2 候选的来源优先级：用户当场提出的想法 > 历次验证积累的机制认识 > 四手法

**第一来源是 Step B.5 收上来的用户当场提出的想法**——用户想法作为一等候选直接进池（标来源「用户」），agent 的活是细化它、压力测试它（先例三问、撞车检查照做——否证对用户候选同样适用，这是防谄媚护栏），不是拿自己的候选跟它抢位置。第二来源是 Step A 盘出的**历次验证对机制的认识**——逐条问「这条直觉能推出什么改法」。例：「X 组件只在小目标上起作用」→「给小目标单独通路 / 分尺度监督」；「高频进了残差但被淹没」→「残差支路加门控」。前两者推不出来的角度，agent 才用四手法补位——agent 自产候选标「补丁候选」，角色是对照材料和兜底，不预设为主角：

1. **迁移**：别的领域 / 任务遇到同类缺口是怎么解的？（注意力机制从 NLP 迁到 CV 就是这一类）
2. **组合**：两个已知机制拼起来能不能互补？（A 补缺口的上游、B 补下游）
3. **反转**：把假设反过来会怎样？（我们一直在「加」信息——「减」信息 / 约束信息会不会才是对的？）
4. **简化**：是不是组件太多互相干扰？去掉某个组件反而 work 也是答案——删代码持平也是赢。

### C.3 每个候选写五样

- **来源逻辑**：为什么这个机制能补这个缺口（推理链，不是「因为 SOTA 这么做」；来自直觉库的注明是哪条直觉推的）
- **关键思路**：用什么机制、怎么接入（角度级，不写公式 / 架构细节）
- **预期工作原理**：补上缺口后，**哪个中间量应该发生什么可观测的变化**（如「高频支路的梯度占比应从 ~2% 升到 ~15%」）——这直接长成后面的诊断实验，候选和实验咬合
- **机制先例**：哪篇论文用过类似机制解决过同类缺口（paper-search 查，给 URL）。先例要过**三问**：它解决的是同一个缺口吗？它 work 的前提条件是什么？我们的 setting 满足那个前提吗？三问有任一答不上，先例的支撑力降一档，标清
- **风险**：写**最可能的失败原因**（具体到机制，不是「可能不 work」——如「如果淹没是因为主干梯度量级大两个数量级，门控也救不了」）+ **怎么最早发现**（哪个便宜实验 / 分析能最早暴露——直接写入 spec §4 失败解读表）。这些失败原因作为初步排查项：实际原因大概率不在清单上，清单的价值是给 Step 5 诊断提供第一批排查方向

### C.4 多样性要求 + 覆盖检查

- **本质不同**:2-3 个候选必须是不同干预点 / 不同机制家族——不是一个想法的三个变种，否则用户没有选择。
- **覆盖检查**：生成完过一遍——C.1 列出的主要干预点是否都有候选覆盖？漏了某个干预点，是没想出机制还是判断它不可行？不可行就把理由写出来（这也是信息）。
- **标明有哪些依据**：没有先例、纯推理支撑的候选标「纯猜测」——让用户知道每个候选方案的不确定性。

### C.5 完整示例

缺口：「高频信息进了残差但被主干特征淹没，残差支路缺乏门控」（诊断：方法需要改进——abs_hf 显示高频有用）。

> **候选 A：残差支路加门控（融合侧）**
> - 来源逻辑：直觉「高频被淹没」直接推出——淹没 = 融合时权重失衡，门控让网络学「什么时候该听支路的」
> - 关键思路：支路输出乘一个可学标量 / 通道门（初值小，让训练自己放大）
> - 预期工作原理：门控值应从接近 0 稳定上升；支路特征的相对能量占比升高
> - 机制先例：Highway Network / gMLP 的 gating（URL）——三问：同是「支路被主干淹没」类缺口；前提是门控初值和 lr 匹配；我们 setting 满足（可验）
> - 风险：可能的失败原因是 门控饱和在 0（支路被彻底关掉，看起来 work 其实是绕过了）→ 最早发现：训练早期打印门控值曲线（几乎零成本）
>
> **候选 B：高频支路单独监督（监督侧）**
> - 来源逻辑：四手法之反转——不指望融合时「不被淹没」，直接给支路自己的训练信号，逼它学出可用表示
> - 关键思路：支路输出接一个轻量头直接预测高频残差目标，辅助 loss
> - 预期工作原理：支路中间特征对高频目标的线性可探性（probe）上升；主任务指标随辅助 loss 权重爬升出现拐点
> - 机制先例：deep supervision 类工作（URL）——三问：缺口同类（支路信号弱）；前提是存在可定义的高频监督目标；FFT 能量比可构造，满足
> - 风险：可能的失败原因是 辅助任务和主任务梯度冲突，两头都学不好 → 最早发现：先只训辅助头 100 step 看 loss 降不降（smoke 级）
>
> **覆盖检查**：表示侧（让主干自己保留高频）未覆盖——判断不可行：换主干 = 换 baseline，违背单变量纪律，写明理由。

**纪律**：候选是角度 / 思路，不是完整方案；这一步**不做完整文献验证**（选定后再验）；候选数量够了就停，不穷举。

## Step D：用户排除 + 逐个深挖（不是四选一）

按 `research-dialogue.md` 的格式向用户展示候选方案概要。请用户排除明显不适合的方案，保留的候选在逐个细化后全部写入 spec，通过实验比较。

对每个保留的候选逐个深挖：

- 机制细化：从「思路」落到「具体怎么做」（公式 / 架构 / 数据流的草图级描述）
- 正经验证：paper-search 查这个具体做法有没有被做过（撞车检查）、先例里的坑
- 和 baseline 的兼容性：接入点、热路径、实现成本初判

深挖后才进 spec；被划掉的候选留一句话在 from-previous 附录「否决的备选方案」（以后可能回来捡）。

**数量纪律**：保留的候选一般 2-4 个。可及早发现失败的实验便宜（reduced + 最早观察到失败信号），比较多个候选方案才划算；一个都没划掉 = 排除法没执行，回 Step C.4 检查是不是候选全是同一想法的变种。

## Step E：写入文件成 spec

保留的方案按 `dl-assistant/references/spec-template.md` 写入文件，五处要写实：

1. **§0 当前子论点「为什么检验这个子论点」**：一句话回扣诊断（「C2 判方法需要改进——高频有用但被淹没，本版改融合机制」），详见 00-from-previous。
2. **§0 候选方案节**：每个保留的方案落三样——**检验什么假设 / 为什么值得试（来源逻辑+先例三问）/ 可能的失败原因及最早可观测的信号**。Step C 五要素里的「预期工作原理」不落 spec，随方案进 plan 的方案设计节（它长成实验，是怎么验的一部分）。
3. **§3 novelty 边界**：最近邻工作一句话区别（「与 X 的区别不是 A、是 B」）+ **增量查新结果**（领域在动，写 §3 前对核心创新点做一次 paper-search 增量查新——被 preempt 越早知道越好）。多个方案时 novelty 按方案逐个写。
4. **单变量声明**（落进 plan）：比较多个候选方案的「变量」是机制选择本身，各方案是这个变量的不同取值——声明写的是「本版只动机制选择这一轴，其余（数据 / schedule / lr / 其他组件）全冻结」。
5. **§4 失败解读表**：**按方案组织**——每个方案从它的「可能的失败原因和最早可观测的信号」长出解读条目（哪个实验、什么信号、命中支持哪种解读 + 可能的原因类别和下一步检查）；再从「预期工作原理」长出成立判据。**开跑前登记各项解读。** 观察到相应信号时启动对应分析和诊断，子论点状态按 Step 5 的规则决定。

## 反模式

- **跳过缺口陈述直接给方案**：「性能差 → 试试加注意力」——没有机制级推理，方案是碰运气。
- **只有一个候选**：只给一个候选等于没给用户判断权；真只有一个合理候选时，把「为什么不走其他路」写出来。
- **候选全是同一想法的变种**：三个候选同一个干预点、只是细节不同——用户没有真选择。多样性要求见 Step C.4。
- **候选写成完整方案**：这步给角度，不给工程设计——工程设计是 plan 的活。
- **无视累积直觉**：每版从零想方案，前几版花钱买来的机制理解全浪费。
- **把 spec 写成 plan**：spec 定「攻什么、凭什么」（稳定层），具体设计选择和实验矩阵是 plan 的活，别混。
